# Grill Loop — 인터뷰 운용 가이드

SKILL.md의 다섯 메타 룰 중 (2) 깊이 우선 분기 탐색과 (5) shared understanding 자가 점검의 **실제 운용 패턴**을 모아둔 가이드. 본문이 헤매지 않도록 구체 예시와 점검 질문 풀을 분리해둔다.

---

## 1. 분기 탐색 패턴

### 1.1 분기 신호 식별

다음 중 하나라도 답변에 등장하면 **분기 발견 신호**로 본다 — 그 자리서 깊이 우선으로 풀고 다음 카테고리로 넘어가지 않는다.

| 신호 | 예시 답변 | 펼쳐야 할 트리 |
|------|----------|---------------|
| 기능 단어 + 확정 | "결제도 있어요", "알림도" | 결제 수단·정산·환불·영수증 / 채널·트리거·구독 |
| 외부 의존 등장 | "Stripe 쓸 거예요" | 가격 모델·웹훅·환불·통화·세금 |
| 사용자 역할 추가 | "관리자도 있어요" | 권한 매트릭스·승인 플로우·감사 로그 |
| 데이터 동작 명시 | "이력 남겨야 해요" | 보관 기간·소프트 삭제·열람 권한·법적 의무 |
| 모호한 정도 표현 | "많아질 수 있어요" | 예상 규모·스케일링 트리거·비용 한도 |

### 1.2 깊이 우선 펼치는 방법

분기를 만나면 **3단계 깊이까지** 한 호흡에 펼친다. 더 깊어지면 사용자가 피로해지므로, 3단계 이후의 후속 결정은 `[TBD]`로 표시 후 후속 논의를 약속한다.

예시 — "결제도 있어요" 분기:

```
Lv1: 결제 수단? [카드(권장)/계좌이체/간편결제 다중]
  Lv2-A 카드:
    - PG사? [Toss(권장)/Iamport/스트라이프]
    - 분할 결제? [없음(권장)/3·6개월]
    - Lv3: 카드사 프로모션 [TBD]
  Lv2-B 환불:
    - 가능 기간? [구매 후 7일(권장)/30일/없음]
    - 부분 환불? [지원/미지원(권장)]
    - Lv3: 정산 시 환불 처리 방식 [TBD]
```

3단계 깊이 안에서 결정된 항목만 SRS에 박힌다. `[TBD]`는 6.2 미결 사항에 정확히 기록한다.

### 1.3 분기 푼 뒤 복귀

분기를 푼 뒤 **반드시 원래 카테고리로 명시적 복귀**한다 — 사용자에게 알린다:

> "결제 분기 정리 완료(7개 결정, TBD 2개). 다시 기능 목록으로 돌아갑니다 — '검색', '대시보드' 외에 더 있는 기능이 있을까요?"

복귀 신호를 안 주면 인터뷰가 트리 안에서 길을 잃는다.

## 2. shared understanding 자가 점검 게이트 운용

4.5단계에서 5단계로 넘어가기 전, 다음 점검을 수행한다. 미통과 항목이 있으면 인터뷰로 되돌아간다.

### 2.1 점검 항목과 발견 방법

| 점검 항목 | 발견 방법 | 미통과 시 액션 |
|----------|----------|---------------|
| 비가역 결정 미결 | 0단계 식별 목록과 대조 | 결정 또는 `[TBD]` 명시 |
| "적당히/알아서" 답변 | 인터뷰 트랜스크립트에서 검색 | 권장 답 재제시 후 동의/반대 받기 |
| 미해결 분기 | 펼친 트리 중 답이 비어있는 노드 | 해당 노드 다시 묻기 |
| 우선순위 불명 FR | FR 항목 순회, "우선순위" 필드 확인 | 필수/권장/선택 결정 |
| 측정 기준 없는 NFR | NFR 항목 순회, "측정 기준" 필드 확인 | 구체 수치 결정 또는 `[TBD]` |
| 입력/출력/예외 미작성 FR | FR 형식 필드 누락 검사 | 누락 필드 채우기 |

### 2.2 게이트 보고 형식

게이트 통과 결과를 사용자에게 **한 줄 요약**으로 알린다 — 게이트의 존재가 사용자에게 보여야 신뢰가 생긴다.

> 예 (통과): "shared understanding 점검: 비가역 결정 4건 결정 완료, "적당히" 답변 0건, 미해결 분기 0건, 우선순위 불명 0건, 측정 기준 없는 NFR 0건 → 5단계 진행."

> 예 (미통과): "shared understanding 점검: NFR-003(가용성)에 측정 기준이 비어있고, 결제 환불 부분환불 여부가 미결입니다. 두 항목을 확정한 뒤 문서를 만들겠습니다."

### 2.3 게이트를 우회하는 경우

사용자가 명시적으로 "지금 다 못 정해, 일단 만들어"라고 요청하면, 게이트를 우회할 수 있다. 단:
- 모든 미통과 항목을 `[TBD]`로 자동 변환
- 6.2 미결 사항 섹션에 표 형태로 기록
- 6단계 리뷰에서 TBD 건수를 강조하여 보고

게이트 우회는 사용자의 명시적 요청이 있을 때만이다. AI가 임의로 우회하지 않는다.

## 3. 권장 답변(룰 3) 운영 가이드

### 3.1 권장 우선순위

권장 답의 근거는 다음 순서로 평가한다:

1. **코드베이스에서 이미 쓰이는 패턴** — 새 기능이 기존 패턴과 충돌하면 비용이 큼
2. **`references/interview-guide.md`의 NFR 기본값 표** — 규모(소·중·대)별 검증된 출발점
3. **같은 도메인의 모범 사례** — 결제 시 PCI-DSS, 의료 시 HIPAA 등 도메인 표준
4. **위 어느 것에도 해당 없음** — 권장 없이 옵션만 제시 (룰 1)

### 3.2 선택지형 질문 라벨 표기

권장이 있는 옵션은 라벨에 `(권장)` 접미사, description에 1줄 이유:

```
질문: "API 인증 방식은?"
옵션 1: "JWT (권장)" — description: "코드베이스가 이미 stateless API라 토큰 인증과 잘 맞음"
옵션 2: "세션 쿠키" — description: "서버 상태 필요, 모바일 앱과 호환성 떨어짐"
옵션 3: "OAuth2 (외부 IdP)" — description: "외부 사용자 통합 시 적합하나 초기 비용 큼"
```

권장 근거가 약하면 `(권장)` 표기를 빼고 옵션만 나열한다. 추천을 억지로 만들면 사용자가 잘못된 안전감을 갖게 된다.

### 3.3 NFR 기본값 표 인용 화법

NFR 인터뷰에서는 `references/interview-guide.md`의 표를 직접 인용한다:

> "응답 시간 기준입니다. interview-guide의 규모별 표 기준으로 스타트업 웹 서비스는 **500ms 이내(권장)**, 200ms 이내(엄격), 1초 이내(여유)로 분류됩니다. 어느 수준이 맞을까요?"

표를 직접 보여주면 사용자가 자신의 규모를 비교 판단할 수 있다.

## 4. 비가역 결정(룰 4) 우선순위 표

0단계에서 식별된 비가역 결정 후보들의 일반적 우선순위 — 도메인에 따라 가중치 조정.

| 비가역도 | 결정 항목 | 변경 비용 |
|---------|----------|----------|
| 매우 높음 | 데이터 모델 핵심 엔티티(주문/사용자/계정) | 마이그레이션 + 다운타임 |
| 매우 높음 | 인증/인가 방식 | 클라이언트 전체 영향 |
| 높음 | 외부 의존성(PG사·메시지 브로커·SaaS) | 마이그레이션 + 계약 종료 |
| 높음 | API 버저닝 정책 | 클라이언트 호환성 |
| 중간 | 모듈 경계·서비스 분리 | 코드 이동 + 배포 파이프라인 |
| 중간 | 캐싱 전략·동기/비동기 통신 | 코드 + 운영 정책 |
| 낮음 | FR 우선순위 | 일정 조정만 |
| 낮음 | 화면 레이아웃·라벨 텍스트 | 프론트엔드 수정 |

**매우 높음**과 **높음** 항목은 1~4단계 어느 단계에서 다루든 다른 결정보다 더 깊은 인터뷰를 받는다.

## 5. 자연스러운 짝 패턴 (룰 1 — `[추론값]` 사용)

사용자가 1개 기능을 언급했을 때, **도메인 표준에서 자연스럽게 함께 다루는 짝**이 명백하면 `[추론값]` 마커로 추가한다. 모르는 영역까지 추론하면 룰 1 위반이다 — 카탈로그에 있는 것만 사용한다.

### 5.1 CRUD 짝

사용자가 `[X 생성]`만 언급 → 일반적으로 `[X 조회]`·`[X 수정]`·`[X 삭제]`도 함께 다룬다. 단, 사용자가 명시적으로 "생성만"이라고 한 경우 제외.

| 사용자 언급 | 자연 짝 | 비고 |
|---|---|---|
| 게시글 작성 | 조회·수정·삭제·목록 페이지네이션 | 페이지네이션 기본 20개/페이지가 표준 |
| 회원 가입 | 로그인·로그아웃·비밀번호 재설정·탈퇴 | 보안 표준 짝 |
| 주문 생성 | 조회·취소·환불·이력 조회 | 결제 도메인 표준 |
| 알림 발송 | 사용자별 끄기/켜기 설정·알림함 조회 | UX 표준 |
| 신고 접수 | 운영자 검토·제재 적용·결과 통보 | 처리 워크플로우 표준 |

### 5.2 인증·인가 짝

JWT/세션 도입이 결정되면 자동 짝:
- 토큰 만료·갱신 정책 (`[권장값]` — 액세스 15분/리프레시 7일이 일반)
- 미인증 401 / 권한 부족 403 응답 분리
- 시크릿 보관 위치 (`[TBD]` — 사용자 선호 영역)

### 5.3 결제 짝

PG 연동이 결정되면 자동 짝:
- 멱등성 키 적용 (`[권장값]` — 표준 패턴, PG 콜백 중복 방지)
- 웹훅 서명 검증 (`[권장값]` — 보안 표준)
- 부분 환불 지원 여부 (`[TBD]` — 사용자 정책 영역)
- 영수증/세금계산서 발행 책임 (`[TBD]` — 사내 ERP 등 외부 의존)

### 5.4 알림 짝

알림 도입이 결정되면 자동 짝:
- 채널 4종(이메일·SMS·푸시·인앱) 중 일부 (`[권장값]`)
- DND·사용자 설정 끄기/켜기 (`[추론값]` — UX 표준)
- 발송 실패 재시도 정책 (`[TBD]` — 사용자 결정)

### 5.5 자연 짝이 아닌 경우

다음은 **자연 짝이 아니다** — `[TBD]`로 둔다. 사용자가 명시적으로 결정해야 한다.
- 비즈니스 정책 (요금제, 환급률 공식, 회원 등급 정책)
- 외부 의존 선택 (PG사 종류, 메시지 브로커, SaaS)
- 화면 레이아웃·UX 디테일
- 컴플라이언스 결정 (GDPR 적용 여부, 데이터 보관 기간)

판단이 애매하면 `[TBD]`가 안전하다 — 사용자가 한 번 더 검토하는 비용이 잘못된 추론값보다 작다.

## 6. 비대화형 환경 폴백 (선택지형 질문 도구 사용 불가 시)

평가·자동화 환경에서 인터뷰형 도구를 못 쓰면 인터뷰 자체가 불가능하다. 이때 `[권장값]` 마커가 폴백 도구가 된다.

### 6.1 폴백 동작

1. 0단계에서 비가역 결정 후보를 식별한 뒤, 각 결정의 권장답을 `interview-guide.md` 또는 코드베이스에서 가져온다
2. 본문에 `[권장값] X — 사용자 동의 대기` 형태로 박는다
3. 6.4 일람표에 자동 등록 (위치·값·근거·결정 상태)
4. 4.5단계 자가 점검 게이트는 **"비대화형 폴백 모드"**로 통과 처리. 단 산출물 첫 페이지에 "이 SRS는 비대화형 폴백 모드로 생성됨 — 6.4 일람표를 검토하여 동의/수정 결정이 필요" 명시.

### 6.2 권장답이 없는 영역

비즈니스 정책·외부 의존 선택 같은 영역은 `[권장값]`을 만들지 않는다. 그대로 `[TBD]`. 폴백 모드라도 모르는 영역은 추론하지 않는다.

### 6.3 사용자 검토 흐름

폴백 모드 산출물을 받은 사용자는:
1. 6.4 일람표를 먼저 본다 → 모든 추론·권장 항목을 일괄 검토
2. 동의 항목 → 마커 제거, 그대로 확정
3. 수정 항목 → 본문 해당 위치 직접 수정 + 6.4에서 제거
4. 잘못된 항목 → 마커를 `[TBD]`로 변경, 6.2로 이전

이 흐름이 인터뷰 한 라운드를 대체한다 — 폴백 모드의 핵심 가치는 "AI가 만든 1차 초안을 사용자가 빠르게 정제"하는 데 있다.
