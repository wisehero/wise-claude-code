# Spec Writer

대화형 인터뷰를 통해 시스템 요구사항을 수집하고, IEEE 830 표준 기반의 SRS(Software Requirements Specification) 문서를 마크다운 파일로 생성하는 스킬.

## Codex 실행 환경 지침

- 기존 코드 탐색은 `rg --files`, `rg -n`, `sed -n`을 우선 사용한다.
- 선택지형 질문 도구가 현재 세션에 없으면 짧은 일반 질문으로 대체한다. 한 번에 1~3개 질문만 던진다.
- 파일 저장은 사용자가 명시적으로 요청하거나 저장 위치에 합의한 경우에만 수행한다.
- `Read`, `Grep`, `Glob`, `Write`, `AskUserQuestion` 같은 Claude Code 도구명은 개념적 단계로 해석한다.

## 핵심 원칙

이 스킬의 목적은 **팀이 공유할 수 있고, 빠진 결정이 없는 요구사항 문서를 만드는 것**이다. 좋은 SRS는 "빠진 요구사항"을 조기에 발견하여 개발 중 재작업과 비싼 실수를 줄여준다. 인터뷰의 깊이가 문서의 가치를 결정한다.

다음 다섯 가지 메타 룰이 인터뷰 자세를 규정한다. 카테고리를 채우는 일보다 이 룰을 지키는 일이 먼저다.

### (1) 명시적 표시 없이 채우지 않는다

사용자가 명시하지 않은 항목은 **셋 중 하나로 처리**한다. AI가 임의로 채우되 사용자에게 안 알리는 행위는 절대 금지 — 잘못된 합의가 가장 비싼 실수다.

| 마커 | 사용 조건 | 산출물 표기 |
|---|---|---|
| **`[추론값]`** | 사용자가 1개 기능을 언급했고, 도메인 표준에서 **자연스러운 짝**(CRUD의 조회/수정/삭제, 인증의 회원가입/로그인 등)이 명백 | `[추론값] X — 근거: 1줄` + 6.4 일람표 등록 |
| **`[권장값]`** | 코드베이스 패턴 또는 도메인 표준에서 권장이 **명백**(예: NFR 규모별 기본값, 보안 표준) | `[권장값] X — 사용자 동의 대기` + 6.4 일람표 등록 |
| **`[TBD]`** | 위 둘에 해당 없거나, 결정에 사용자 선호·전략적 판단이 필요한 경우 | `[TBD]` + 6.2 미결사항 등록 |

`[추론값]`·`[권장값]`은 **추측이 아니라 투명한 추론**이다. 추론 근거를 1줄로 적고 6.4 섹션에 자동 등록하면, 사용자가 한눈에 보고 동의·수정·제거 결정을 빠르게 할 수 있다. 모르는 영역을 추론값으로 박는 건 룰 위반이다 — 자연 짝 패턴은 `references/grill-loop.md` 5절 참조.

선택지형 질문 도구를 사용할 수 없는 환경에서도 이 3명칭 체계가 그대로 작동한다. 폴백 패턴은 `references/grill-loop.md` 6절 참조.

이 룰은 인터뷰부터 5단계 문서 생성까지 전 단계에 적용된다.

### (2) 분기를 발견하면 깊이 우선으로 푼다

답변에서 새 분기(예: 사용자가 "결제도 있어요"라고 답함)가 발견되면, **다음 카테고리로 넘어가기 전에 그 분기의 의존 결정을 모두 푼다** (PG사 → 결제 수단 → 정산 → 환불 → 영수증). 4단계 카테고리는 진행 순서가 아니라 **누락 방지용 체크리스트**로 쓴다.

설계 트리는 의존성을 가진다. 결제 PG사를 결정하지 않으면 환불 정책 질문이 무의미해진다. 분기를 끝까지 푼 뒤 원래 카테고리로 복귀한다. 분기 탐색 패턴은 `references/grill-loop.md` 참조.

### (3) 모든 질문에 권장 답변과 이유를 함께 제시한다

선택지형 질문을 만들 때, 도메인 표준이나 코드베이스 분석에서 명백한 답이 있는 질문은 **첫 번째 옵션 라벨에 `(권장)`을 붙이고**, 설명에 추천 이유를 1줄 명시한다. 사용자가 매번 0부터 판단하면 결정 피로가 누적되어 인터뷰 후반의 답변 품질이 떨어진다.

권장 근거는 (a) 코드베이스에서 이미 쓰이는 패턴, (b) `references/interview-guide.md`의 NFR 기본값 표, (c) 같은 도메인의 일반 모범 사례 순으로 우선한다. 권장이 없으면 그냥 옵션만 제시한다 — 추천을 억지로 만들면 룰 (1)을 위반하게 된다.

### (4) 비가역적 결정을 먼저 다룬다

데이터 모델, 인증/인가 방식, 외부 의존성(PG사·메시지 브로커 등) 선택, API 버저닝 정책 같은 결정은 **나중에 되돌리려면 마이그레이션 비용이 크다.** 반대로 FR-027의 우선순위나 화면 레이아웃은 나중에 바꾸기 쉽다.

0단계에서 비가역 결정 후보를 먼저 표면화하고, 그 결정이 있어야 풀리는 후속 결정들을 이어 푼다. 시간 자원을 균등 배분하지 말고 비가역도에 가중치를 둔다.

### (5) shared understanding에 도달했을 때만 문서를 생성한다

5단계(문서 생성) 직전에 **자가 점검 게이트**를 통과해야 한다 — 남은 모호함이 있는가, "적당히/알아서"로 답한 항목이 있는가, 분기로 발견했지만 안 푼 결정이 있는가. 게이트를 통과하지 못하면 인터뷰로 되돌아간다. 4단계가 끝났다는 사실만으로 문서를 만들지 않는다.

### 보조 원칙

- **요구사항 ID**: `FR-001`, `NFR-001` 형식. 팀원 간 커뮤니케이션에서 "그 기능"이 아닌 "FR-012"로 지칭하면 모호함이 사라진다.
- **측정 가능한 NFR**: "빨라야 한다"가 아니라 "응답 시간 200ms 이하"처럼 구체적 수치. 사용자가 모호하게 답하면 구체 선택지를 제시한다 (룰 3).
- **코드베이스 우선 탐색**: 작업 디렉토리에 기존 코드가 있으면, 사용자에게 묻기 전에 코드를 읽어 답할 수 있는 것(기술 스택, 모듈 구조, 기존 패턴)은 답을 가져온다. 사용자에게는 **선호와 판단이 필요한 질문만** 던진다.
- **스코프 가드**: 1단계에서 합의한 범위(포함/제외)를 벗어나는 새 기능 요청이 들어오면 현재 SRS에 추가하지 않고 별도 SRS로 안내한다. 반대로 범위 안에서 예상 밖 이슈(컴플라이언스·보안 요건 등)가 발견되면 (A) 새 섹션 추가 (B) 기존 섹션 병합 (C) `[TBD]` 중 사용자가 선택하게 한다.

## 워크플로우

```
요청 입력
    ↓
[0단계] 코드베이스 탐색 & 비가역 결정 사전 표면화
    ↓
[1단계] 프로젝트 개요 인터뷰
    ↓
[2단계] 기능 요구사항 인터뷰 (분기 발견 시 깊이 우선)
    ↓
[3단계] 비기능 요구사항 & 제약조건
    ↓
[4단계] 인터페이스 & 외부 시스템
    ↓
[4.5단계] shared understanding 자가 점검 게이트
    ↓ (통과)

    ↓
[6단계] 리뷰 & 보완
```

단계 번호는 **체크리스트 라벨**이다 — 인터뷰 도중 분기가 열리면 다음 단계로 직진하지 않고 깊이 우선으로 분기를 푼 뒤 복귀한다 (룰 2).

## When to Use / When NOT to Use

**사용한다:**
- 새 시스템·기능의 요구사항을 팀 공유 문서로 정리해야 할 때
- 기능 목록, 범위, 액터, 비기능 요구사항, 외부 인터페이스가 아직 대화로 정리되어야 할 때
- 기존 기획서나 회의록을 SRS 형식으로 재구성해야 할 때

**사용하지 않는다:**
- 이미 구현된 코드의 API 문서나 Javadoc/JSDoc을 생성하는 요청
- 회의록 요약, 일반 기획서, PRD 카피라이팅처럼 SRS 산출물이 아닌 요청
- 사용자가 바로 구현을 원하고 요구사항 인터뷰를 원하지 않는 요청

## 상세 단계

### 0단계: 코드베이스 탐색 & 비가역 결정 사전 표면화

작업 디렉토리에 기존 코드가 있으면 `rg --files`/`rg -n`/파일 읽기로 다음을 빠르게 파악한다 — 사용자에게 묻지 않고 답할 수 있는 항목이다.
- 언어·프레임워크·주요 라이브러리
- 모듈/패키지 구조
- 인증 방식 (JWT/세션/OAuth 등)
- DB 종류·ORM
- 외부 API 연동 흔적

코드를 읽은 뒤, **비가역 결정 후보를 먼저 식별**한다. 이번 SRS에서 새로 결정해야 할 비가역 항목 목록을 만든다. 예:
- 데이터 모델의 핵심 엔티티 정의 (변경 시 마이그레이션 필요)
- 인증/인가 방식 (변경 시 클라이언트 영향)
- 외부 의존성 선택 (PG사·메시지 브로커·SaaS)
- API 버저닝 정책 (변경 시 클라이언트 호환성)

이 목록은 1~4단계 어느 단계에서 다루든, **균등 분량이 아닌 더 깊은 인터뷰**를 받는다.

신규 프로젝트라 코드베이스가 없으면 0단계는 비가역 결정 후보 식별만 수행한다.

---

### 1단계: 프로젝트 개요 인터뷰

시스템의 큰 그림을 파악한다. 사용 가능한 경우 선택지형 질문을 활용하고, 없으면 짧은 일반 질문으로 대체한다 — 룰 (3)에 따라 첫 옵션에 `(권장)`을 붙일 수 있는 경우 명시한다.

핵심 질문:
- **시스템 이름과 한 줄 설명**
- **핵심 사용자(액터)** — 일반 사용자, 관리자, 외부 시스템
- **해결하려는 문제** — 왜 이 시스템이 필요한가
- **프로젝트 범위** — 이번 버전 포함/제외

사용자가 이미 상세 설명을 제공했다면 중복 질문하지 않고 확인만 한다.

---

### 2단계: 기능 요구사항 인터뷰

시스템이 **무엇을 해야 하는지** 구체화한다. `references/interview-guide.md`의 도메인별 심화 질문을 활용한다 (인증/인가, 데이터 관리, 검색, 알림, 결제).

핵심 질문:
- **핵심 기능 목록** (우선순위와 함께)
- **각 기능의 입력 → 처리 → 출력 흐름**
- **예외 상황** — 실패 시 어떻게 처리하는지
- **데이터 요구사항**

**분기 깊이 우선 적용 예**: 사용자가 "결제도 있어요"라고 답하면, 다음 기능으로 넘어가지 않고 결제 분기를 다 푼다 — PG사? → 카드/계좌이체/간편결제? → 정산 주기? → 환불 정책? → 부분 환불? → 영수증/세금계산서?. 분기를 다 푼 뒤 원래 기능 목록으로 복귀한다.

각 기능은 **다음 형식**을 빠짐없이 따른다 (`references/srs-template.md`와 정확히 동일):

```
#### FR-XXX: [기능 제목]

- **설명**: [기능이 무엇을 하는지]
- **선행 조건**: [이 기능이 실행되기 위한 조건]

**입력 데이터:**

| 필드명 | 타입 | 필수 여부 | 검증 규칙 | 설명 |
|--------|------|-----------|-----------|------|

**기본 흐름:**

1. [동작 1]
2. [동작 2]

**출력 데이터:**

| 필드명 | 타입 | 설명 |
|--------|------|------|

**예외 흐름:**

| 조건 | HTTP 상태 | 에러 코드 | 설명 |
|------|-----------|-----------|------|

- **후행 조건**: [기능 완료 후 시스템 상태]
- **우선순위**: 필수 / 권장 / 선택
```

**모든 FR 항목**이 이 형식을 따른다. 일부만 다른 형식으로 작성하지 않는다.

기능이 10개를 넘으면 도메인별로 그룹핑한다. 핵심 기능부터 시작하고 점진적으로 확장한다.

---

### 3단계: 비기능 요구사항 & 제약조건 인터뷰

시스템이 **어떻게 동작해야 하는지**의 품질 속성을 정의한다.

핵심 질문:
- **성능** — 동시 사용자 수, 응답 시간 목표, 처리량
- **보안** — 인증/인가, 데이터 암호화, 감사 로그
- **가용성** — 가동률, 장애 복구 시간(RTO/RPO)
- **확장성** — 예상 성장률, 스케일링 전략
- **기술 제약** — 기술 스택, 호환성, 규제/컴플라이언스

비기능 요구사항은 반드시 **측정 기준**을 포함한다. 사용자가 "빨랐으면 좋겠어요" 같이 답하면, `interview-guide.md`의 규모별 기본값 표를 인용하여 권장 답을 함께 제시한다. 예:

> "API 응답 시간 기준입니다. 비슷한 규모의 스타트업 웹 서비스 기준으로 **500ms 이내(권장)**, 200ms 이내(엄격), 1초 이내(여유) 중 어느 수준이 맞을까요? 사용자가 즉시 반응을 느끼는 임계는 보통 200~500ms입니다."

권장이 명백하지 않으면 옵션만 제시한다 (룰 1, 추측 금지).

---

### 4단계: 인터페이스 & 외부 시스템 인터뷰

시스템의 경계와 외부 연동을 정의한다.

핵심 질문:
- **사용자 인터페이스** — 웹/모바일/데스크톱, 주요 화면
- **외부 시스템 연동** — API, 서드파티 서비스
- **데이터 인터페이스** — 가져오기/내보내기 형식, 마이그레이션
- **통신 프로토콜** — REST, gRPC, WebSocket, 메시지 큐

외부 시스템이 없는 단순 프로젝트는 이 단계를 간소화한다.

---

### 4.5단계: shared understanding 자가 점검 게이트

5단계로 직진하지 않는다. 다음 점검 질문에 모두 "통과"가 나와야 5단계로 간다.

| 점검 항목 | 통과 기준 |
|----------|----------|
| 비가역 결정 (0단계 식별 목록) | 모두 결정 완료 또는 명시적 `[TBD]`/`[권장값]` |
| 사용자가 "적당히/알아서"로 답한 항목 | 모두 `[추론값]`/`[권장값]`/`[TBD]` 중 하나로 명시 처리 (임의 채움 0건) |
| 깊이 우선 분기 중 미해결 | 0건 |
| 우선순위 불명 FR | 0건 |
| 측정 기준 없는 NFR | 0건 |
| 6.4 일람표 무근거 항목 | 모든 `[추론값]`·`[권장값]`에 1줄 근거 |

미통과 항목이 있으면 사용자에게 다시 묻고 결정 또는 `[TBD]` 처리한다. **이 게이트의 존재 자체를 사용자에게 알리고**, 통과 결과를 한 줄로 보고한 뒤 5단계로 진입한다.

> 예: "shared understanding 점검 결과: 비가역 결정 4건 모두 결정 완료, TBD 2건(결제 영수증 양식, 다국어 지원 여부), 측정 기준 없는 NFR 0건. 문서 생성으로 진행하겠습니다."

자가 점검 상세 패턴은 `references/grill-loop.md` 참조.

### 5단계: SRS 문서 생성 & 파일 저장

인터뷰에서 수집한 내용을 바탕으로 SRS 문서를 생성한다. **`references/srs-template.md`의 구조와 형식을 그대로 따른다** — 섹션 순서, 테이블 형식, 항목 배치를 임의로 변경하지 않는다. IEEE 830 구조:
- 1장 개요: 목적, 시스템 설명(포함/제외 명시), 용어 정의, 참고 자료
- 2장 전체 설명: 시스템 관점, 사용자 특성, 제약조건, 가정 및 의존성
- 3장 기능 요구사항: FR-ID별 설명/선행조건/입력데이터/기본흐름/출력데이터/예외흐름/후행조건/우선순위
- 4장 비기능 요구사항: NFR-ID별. 성능과 보안은 기본 포함하되, 나머지 카테고리는 도메인 특성에 맞게 선택
- 5장 인터페이스: UI, 외부 시스템, REST API 요약, 데이터 인터페이스, 도메인 이벤트(선택)
- 6장 부록: 우선순위 요약, 미결 사항(TBD), AI 추론·권장 일람표, 변경 이력

최종 SRS는 아래 섹션 순서와 핵심 항목을 그대로 포함한다. 해당사항이 없는 섹션은 "해당 없음"으로 표기하고, 아직 결정되지 않은 값은 `[TBD]`로 둔다.

문서 생성 시 유의사항:
- **목차를 반드시 포함한다.** 문서 상단(메타 정보 바로 아래)에 마크다운 앵커 링크 기반의 목차를 생성한다. 대분류(1~6)뿐 아니라 **하위 섹션(1.1, 3.1 등)까지 포함**하여 실제 작성된 섹션에 맞게 조정한다. 3장은 기능 그룹명, 4장은 NFR 카테고리명을 목차에 반영한다.
- 사용자가 명시한 내용은 그대로 포함한다. 명시하지 않은 항목은 `[추론값]`·`[권장값]`·`[TBD]` 중 하나로 명시 처리한다 (룰 1). 임의로 채우되 사용자에게 안 알리는 행위 금지.
- `[추론값]`·`[권장값]`을 사용한 모든 항목은 6.4 AI 추론·권장 일람표에 1줄 근거와 함께 등록한다.
- 인터뷰에서 명확하지 않았고 권장이 없는 항목은 `[TBD]`로 표시하고 6.2에 등록한다.
- 각 요구사항에 우선순위를 부여한다 (필수 / 권장 / 선택).

파일 저장:

- 저장 위치: 현재 작업 디렉토리 (사용자가 별도 경로를 지정하면 해당 경로에 저장)

### 6단계: 리뷰 & 보완

생성된 문서의 핵심 통계를 요약하고 사용자에게 리뷰를 요청한다.

요약 항목:
- 기능 요구사항 N건 (필수 N / 권장 N / 선택 N)
- 비기능 요구사항 N건
- TBD 항목 N건 (후속 논의 필요)
- 인터페이스 정의 N건
- 비가역 결정 N건 (0단계 식별, 4.5단계 통과)

사용자가 수정을 요청하면 해당 섹션만 업데이트하고 파일을 다시 저장한다. 전체 인터뷰를 반복할 필요는 없다.

## Troubleshooting

**사용자가 비기능 요구사항을 모르겠다고 할 때**
- 원인: NFR은 경험이 없으면 감이 안 오는 영역
- 해결: 룰 (3) 적용 — `interview-guide.md`의 규모별 기본값 표를 인용하여 권장 답을 제시. 예: "스타트업 웹 서비스 기준으로 응답 시간 500ms, 가동률 99.5%, 동시 접속 100명을 권장합니다 — 이대로 갈까요?"

**요구사항이 너무 많아 문서가 길어지는 경우**
- 원인: 대규모 시스템이거나 지나치게 상세한 수준
- 해결: 핵심 기능(MVP)을 1차 문서로, 나머지는 "향후 고려사항" 섹션으로 분리

**기존 기획 문서가 이미 있는 경우**
- 원인: 회의록·기획서가 있는데 SRS 형식으로 변환 필요
- 해결: 기존 문서 내용 파악 후 부족한 부분만 추가 인터뷰로 보완

**사용자가 "그냥 알아서"로 답할 때**
- 원인: 결정 피로 또는 도메인 지식 부족
- 해결: 3명칭 마커로 처리 — 자연 짝(CRUD 등)은 `[추론값]`, 도메인 표준이 명백하면 `[권장값]`, 그 외는 `[TBD]`. 모두 6.4 일람표에 등록되므로 사용자가 한눈에 검토 가능. 임의 채움은 절대 금지.

**사용자가 1개 기능만 언급한 경우 (예: "할 일 만들고 완료 체크")**
- 원인: 사용자가 핵심만 말함. CRUD의 자연 짝(조회·수정·삭제)이 있는지 판단 필요
- 해결: 자연 짝이 명백하면 `[추론값]`으로 추가 + 6.4에 "CRUD 짝 패턴"으로 근거 명시. 사용자는 검토 후 제거하거나 동의. 자연 짝 카탈로그는 `references/grill-loop.md` 5절 참조.

**비대화형 환경에서 분기 깊이를 못 채우는 경우**
- 원인: 선택지형 질문 도구 사용 불가로 권장답 동의를 받을 수 없음
- 해결: 권장답을 `[권장값]` 마커로 본문에 박고 6.4 일람표에 등록. 사용자가 산출물 리뷰 시 일람표만 훑으면 동의/수정 결정 가능. 폴백 패턴은 `references/grill-loop.md` 6절 참조.
