# Study Helper

노션에 정리한 기술 학습 노트를 검수하여, AI투(AI 냄새) 제거 · 오타 수정 · 팩트체크를 수행하고 검수 리포트를 제공하는 스킬.

## 핵심 원칙

이 스킬의 목적은 학습 노트의 **정확성과 가독성을 높이는 것**이다. 노트의 구조나 흐름은 건드리지 않는다 — 학습자가 자기 방식으로 정리한 구조를 바꾸면 본인의 학습 맥락이 깨지기 때문이다.

보완 제안은 **1~3개 이내**로 제한한다. 너무 많은 보완을 제안하면 "내 노트가 부족하다"는 인상을 줄 수 있고, 검수 리포트의 핵심(오류 수정)에서 초점이 벗어난다.

과거 버전 설명은 노트에 이미 언급된 경우에만 간략히 보완한다. 학습자가 다루지 않은 레거시 내용을 새로 추가하면 노트의 목적과 범위를 벗어난다.

팩트체크 수정 제안에는 반드시 참고 소스(공식 문서 등)를 포함한다. 근거 없는 수정 제안은 오히려 혼란을 줄 수 있다.

## 의존 스킬

이 스킬은 아래 두 스킬을 활용한다. 없으면 해당 단계를 건너뛴다. 괄호 안은 이 스킬이 기대하는 **최소 버전**이다 — 의존 스킬이 major 버전 업그레이드되어 API가 변경되면 본 스킬의 호환성을 재검토해야 한다.

- **`/humanizer-korean`** (>= 3.0.0): AI투 제거 + 오타 수정 (2단계). audit/rewrite 두 가지 모드 API에 의존.
- **`/external-context`** (>= 1.2.0): 웹 검색 기반 팩트체크 (3단계). `Agent(subagent_type="docs-researcher", ...)` 디스패치 형식과 `### 충돌 · 전환 · 차이 지점` 섹션을 포함한 통합 출력 포맷에 의존.

## 워크플로우

```
노션 페이지 이름 또는 로컬 md 경로 입력
    ↓
[1단계] 원본 내용 가져오기 (Notion 도구 또는 Read)
    ↓
[2단계] /humanizer-korean — AI투 제거 + 오타 수정
    ↓
[3단계] /external-context — 팩트체크 (웹 검색 기반)
    ↓
[4단계] 검수 리포트 생성
    ↓
[5단계] 출력 모드 선택:
         - 터미널 출력 (기본)
         - 파일 저장 (요청 시)
         - 원본 직접 수정 (요청 시, 노션 페이지 업데이트 또는 로컬 md Edit)
```

## 상세 단계

### 1단계: 원본 내용 가져오기

사용자로부터 **노션 페이지 이름** 또는 **로컬 md 파일 경로**를 입력받는다.

**노션 페이지인 경우:**
1. Notion 검색 도구(`notion-search`)로 해당 페이지를 찾는다.
2. Notion fetch 도구(`notion-fetch`)로 페이지 전체 내용을 가져온다.
3. **페이지를 찾지 못한 경우**: 유사한 이름의 페이지 목록을 제시하고 사용자에게 선택을 요청한다.

**로컬 md 파일인 경우:**
1. `Read` 도구로 파일 전체를 읽는다.
2. 파일이 존재하지 않으면 사용자에게 경로를 재확인한다.

어느 경우든 원본 내용을 기억해두고, 이후 수정 사항 비교(변경 전 / 변경 후)에 사용한다.

---

### 2단계: AI투 제거 + 오타 수정 (/humanizer-korean)

`/humanizer-korean` 스킬을 호출하여 다음을 수행한다. **호출 모드는 5단계 출력 경로에 따라 갈린다**:

- **터미널 출력 / 파일 저장 모드** → `audit` 모드로 호출한다. 수정안(원본/수정안/이유)만 받아 리포트에 싣는다.
- **원본 직접 수정 모드** → `rewrite` 모드로 호출한다. 실제 교정된 문자열이 필요하며, 이 결과가 Edit 호출의 `new_string`으로 그대로 쓰인다.

수행 항목:

- **AI투 제거**: 과도한 구조화, 뻔한 서론/결론, 불필요한 강조 등 AI가 작성한 티가 나는 표현을 자연스러운 문체로 수정
- **오타 수정**: 맞춤법, 띄어쓰기, 오탈자 교정

수정된 결과를 기억해두고, 이후 리포트 생성에 사용한다.

**변경 사항 추적**: 수정된 부분마다 아래 정보를 기록한다:

- 원본 텍스트
- 수정된 텍스트
- 수정 유형 (AI투 / 오타)
- 수정 이유 (간결하게)

**humanizer-korean 호출 실패 시**: 사용자에게 실패를 알리고, AI투/오타 수정 없이 팩트체크 단계로 넘어간다. 리포트의 "AI투 제거 & 오타 수정" 섹션에 "humanizer-korean 호출 실패로 미수행"을 명시한다.

---

### 3단계: 팩트체크 (/external-context)

`/external-context` 스킬을 호출하여 기술적 사실관계를 검증한다. 학습 노트의 정확성이 핵심이므로, 시간을 들여 꼼꼼히 검증한다. 핵심 기술 개념을 대충 넘기지 않고, 공식 문서까지 확인하여 신뢰할 수 있는 검증 결과를 제공한다.

#### 쿼리 전달 방식

`/external-context`는 내부적으로 쿼리를 2-5개 facet으로 분해해 `docs-researcher` 서브에이전트를 병렬 호출한다. 따라서 다음 원칙을 따른다:

- **노트에서 검증이 필요한 기술 주장 3-5개를 추려** 하나의 정리된 쿼리로 전달한다. 검증 대상이 너무 많으면 주제별로 묶어 여러 번 호출한다.
- 쿼리에는 "팩트체크 모드"임을 명시한다 — 즉, 노트의 원본 주장을 함께 전달하고 "이 주장이 현재 최신 안정 버전 기준으로 정확한지 공식 문서로 확인해달라"는 지시를 포함한다.
- 서브에이전트가 반환한 출처 URL과 버전 정보를 리포트의 "근거" 필드에 그대로 싣는다.

#### 검증 대상

- 프레임워크/라이브러리의 동작 방식 설명
- API 사용법, 메서드 시그니처
- 아키텍처 패턴, 디자인 패턴의 정의와 적용 방식
- 설정값, 기본값, 기본 동작
- 버전별 차이점이나 변경 사항

#### 버전 기준 원칙

> **현재 시점에서 실용적인 버전만 다룬다.**

- 검증 기준은 **현재 널리 사용되는 최신 안정 버전**(Latest Stable)이다.
- 과거 버전은 **해당 내용이 이미 노트에 언급된 경우에만** 간략히 보완한다.
  - 예: "Spring Boot 2.x에서는 이랬지만 3.x에서 변경됨" 정도의 한 줄 언급
- 노트에 없는 레거시 내용을 새로 추가하지 않는다.

#### 팩트체크 결과 기록

각 검증 항목마다:

- 원본 내용 (요약)
- 검증 결과: 정확 / 부분 수정 필요 / 오류
- 근거 (참고 소스 URL 포함)
- 수정 제안 (필요한 경우)

**external-context 호출 실패 시**: 사용자에게 실패를 알리고, 팩트체크 없이 리포트를 생성한다. 리포트의 "팩트체크 결과" 섹션에 "external-context 호출 실패로 미수행"을 명시한다.

### 4단계: 검수 리포트 생성

`references/report-template.md`를 참조하여 검수 리포트를 구성한다. 템플릿 구조는 아래와 같다 — 섹션 순서와 테이블 컬럼을 그대로 따른다:

1. **요약** — 한 블록: `AI투 수정: N건 / 오타 수정: N건 / 팩트체크 항목: N건 (정확 N / 부분수정 N / 오류 N)`.
2. **AI투 제거 & 오타 수정** — 수정 목록 테이블 `# | 유형 | 원본 | 수정 | 이유` 뒤에 선택적으로 "수정된 전문" 블록.
3. **팩트체크 결과** — `정확한 내용`, `부분 수정 필요`, `오류` 3개 하위 섹션. 각 항목은 `원본 / 수정 제안 / 이유 / 참고(URL)` 4필드.
4. **보완 제안** — 1~3개 bullet.

**섹션 분리 기준**: 팩트의 오류·부분수정은 **팩트체크 결과** 섹션에만 기록한다. **보완 제안** 섹션에는 원본에 오류가 없지만 한 줄 추가하면 이해가 풍부해지는 내용만 올린다. 이 분리를 지키면 "내 노트에 뭐가 틀렸나"와 "뭘 더 넣으면 좋을까"를 학습자가 한눈에 구분할 수 있다.

**수정된 전문 포함 휴리스틱**: 원본이 200줄 이하이면 수정된 전문을 통째로 싣는다. 200줄을 넘으면 변경이 발생한 블록 단위 diff만 싣고, 나머지 블록은 생략하거나 "변경 없음"으로 표기한다 — 터미널이 전문 덤프로 도배되는 것을 막기 위함이다.

**직접 수정 모드의 추가 섹션**: 원본 직접 수정 경로(5단계의 세 번째 출력 모드)에서는 위 리포트 뒤에 템플릿 부록의 **직접 수정 프리뷰 모드** 섹션을 이어붙인다. 구조는 아래와 같이 인라인으로 복제한다:

- **적용 예정 변경 목록** — `# | 유형 | 대상(before) | 적용 후(after) | 근거` 5컬럼 테이블. `유형`에는 `AI투 / 오타 / 팩트` 중 하나를 표기하고, `대상`과 `적용 후`는 Edit 호출 시 그대로 `old_string`/`new_string`으로 쓸 수 있는 원문 스니펫으로 구성한다.
- **확인 응답 프로토콜** — 사용자에게 세 가지 응답 경로를 제시: `진행` (전체 적용), `1, 3, 6만 진행` 같은 **번호 선별**, `취소` (편집 중단).

---

### 5단계: 출력

사용자의 요청에 따라 세 가지 출력 모드 중 하나를 선택한다. 명시가 없으면 **터미널 출력**이 기본이다.

- **터미널 출력 (기본)**: 리포트 내용을 터미널에 바로 출력한다. 원본은 건드리지 않는다.
- **파일 저장**: 사용자가 별도로 요청한 경우에만 별도 `.md` 파일로 저장한다. 파일명은 `검수리포트_[페이지제목]_YYYYMMDD.md` 형식을 따른다. 원본은 건드리지 않는다.
- **원본 직접 수정**: "그냥 고쳐줘", "노션 페이지에 반영해줘", "파일 직접 수정해줘" 같이 **사용자가 명시적으로 요청한 경우에만** 원본을 직접 업데이트한다. 이 경로는 되돌리기 어려우므로 아래 3단계 안전장치를 반드시 거친다:
  - **① 프리뷰 생성**: 4단계에서 설명한 "직접 수정 프리뷰 모드" 부록(적용 예정 변경 목록 + 확인 응답 프로토콜)을 리포트 뒤에 이어붙여 먼저 출력한다. `Edit` / `notion-update-page`는 이 시점에 호출하지 않는다.
  - **② 확인 대기**: 사용자의 명시적 응답을 기다린다.
    - `진행` → 목록의 모든 변경을 순서대로 적용한다.
    - `1, 3, 6만 진행` 같은 번호 선별 → 지정 번호만 적용하고 나머지는 버린다.
    - `취소` → 어떤 편집도 수행하지 않고 종료한다.
    - "응", "오케이", "좋아" 같은 모호한 동의는 **전체 승인으로 해석하지 않는다**. 사용자에게 위 세 가지 중 하나를 다시 요청한다 — 되돌리기 어려운 경로이므로 명시적 키워드 매칭이 안전성을 높인다.
  - **③ 편집 적용**:
    - **노션 페이지**: `notion-update-page`로 변경 섹션만 교체한다. 전체 재작성은 피한다.
    - **로컬 md 파일**: 프리뷰 목록의 각 항목마다 `Edit`을 한 번씩 호출해 부분 수정한다. `before` 스니펫이 파일 안에 **여러 번 등장하는 경우에만** `replace_all`을 쓰고, 유일하면 기본 `Edit`을 쓴다 — 의도치 않은 전역 치환을 막기 위함이다.
    - 원본의 섹션 순서와 구조는 건드리지 않는다.
  - **변경 로그**: 편집 후 적용 요약(적용 N건 / 스킵 N건 / 실패 N건)을 터미널에 출력한다.

## Examples

### 예시 1: 기본 사용

```
사용자: "Spring MVC 정리한 노션 페이지 검수해줘"
동작:
  1. "Spring MVC" 키워드로 노션 검색 → 페이지 fetch
  2. /humanizer-korean으로 AI투 제거 + 오타 수정
  3. /external-context로 팩트체크
  4. 터미널에 리포트 출력
```

### 예시 2: 파일 저장 요청

```
사용자: "JPA 학습 노트 검수하고 파일로 저장해줘"
동작:
  1~4단계 동일
  5. 검수리포트_JPA_20260312.md 파일로 저장
```

### 예시 3: 페이지명이 모호한 경우

```
사용자: "Redis 정리한 거 검수 좀"
동작:
  1. "Redis" 검색 → 유사 페이지 3개 발견
  2. 사용자에게 목록 제시: "Redis 캐싱 전략", "Redis Pub/Sub", "Redis 자료구조"
  3. 사용자 선택 후 진행
```

### 예시 4: 원본 노션 페이지 직접 수정

## Troubleshooting

**노션 페이지가 너무 긴 경우**
- 원인: Notion fetch 도구의 응답 크기 제한
- 해결: 페이지를 섹션별로 나누어 검수하겠다고 사용자에게 안내 후, 주요 섹션부터 순차 처리

**동일 이름 페이지가 여러 개인 경우**
- 원인: 노션 워크스페이스에 같은 제목의 페이지 존재
- 해결: 검색 결과에 상위 페이지(부모) 경로를 함께 표시하여 구분

**humanizer-korean이나 external-context 스킬을 찾을 수 없는 경우**
- 원인: 해당 스킬이 설치되지 않았거나 비활성 상태
- 해결: 사용자에게 필요한 스킬 설치를 안내하고, 해당 단계를 건너뛰어 가능한 범위까지 리포트 생성
