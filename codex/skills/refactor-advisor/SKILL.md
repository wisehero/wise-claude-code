# Refactor Advisor

**Java/Spring 전용** 스킬이다. `.java` 파일만 대상으로 하며, 코드 스멜·SOLID 위반·디자인 패턴 적용 기회를 식별하고 구체적 대안 코드와 트레이드오프를 제시한다. 다른 언어 파일이 들어오면 Step 2의 **언어 사전 체크**에서 즉시 종료한다 (아래 Troubleshooting 참조) — 잘못된 언어에 Java 이디엄 진단을 내리는 것보다 명시적 거부가 안전하다.

## Codex 실행 환경 지침

- 파일 목록 탐색은 `rg --files`, 내용 검색은 `rg -n`, 부분 읽기는 `sed -n`을 우선 사용한다.
- 파일 수정은 Codex의 파일 편집 도구를 사용하고, 이 스킬의 프리뷰/확인 프로토콜을 먼저 거친다.
- `Read`, `Grep`, `Glob`, `Edit` 같은 Claude Code 도구명은 개념적 단계로 해석한다.

대원칙: **코드는 읽기 쉽고 이해하기 쉬워야 한다.** 모든 리팩토링 제안은 이 원칙에 부합하는지를 기준으로 판단한다.

## 분석 워크플로우

### Step 1: 대상과 모드 파악

사용자 요청에서 두 가지를 확인한다:

**분석 대상:**
- 단일 클래스: 해당 클래스와 직접 의존성 분석
- 패키지: 핵심 클래스(가장 많이 참조되거나 가장 큰 클래스)를 먼저 식별 → 깊이 분석 → 나머지 클래스는 관계 중심으로 분석
- 파일 경로: 해당 파일 중심으로 분석

지정이 없으면 사용자에게 분석 대상을 물어본다.

**동작 모드:**
- **"분석해줘", "봐줘"**: 리포트만 제시 (기본값). 파일 편집 도구를 호출하지 않는다. 리포트의 "대안 A/B"에는 리팩토링 후 코드 예시를 포함하되, 파일 자체는 수정하지 않는다 — 분석 모드와 적용 모드의 차이는 산출물 내용이 아니라 편집 적용 여부다.
- **"리팩토링 해줘", "개선해줘", "정리해줘"**: Step 6까지 리포트를 만든 뒤 Step 7(사용자 확인 및 적용) 경로로 진입한다.
- **"바로 적용해줘"**: 리포트 전문은 생략할 수 있지만 Step 7의 **확인 응답 프로토콜은 반드시 거친다** — Critical 이슈만 골라 프리뷰를 1회 제시하고 사용자의 명시적 응답을 받은 뒤에야 적용한다. 완전 자동 적용은 되돌리기 비용이 커서 허용하지 않는다.

### Step 2: 코드 읽기 및 구조 파악

**언어 사전 체크 (가장 먼저 수행)**: 대상 파일의 확장자와 내용을 확인한다. `.java` 파일이 아니거나 Java 구문이 아니면 **즉시 스킬을 종료하고** 아래 안내를 사용자에게 출력한다 — smell-catalog과 pattern-guide가 Java/Spring 이디엄으로만 작성되어 있어 다른 언어에 적용하면 잘못된 진단(예: PHP 코드에 `@Autowired` 제거 권장)이 나오기 때문이다:

> 이 스킬은 **Java/Spring 전용**입니다. 감지된 언어/확장자: `<감지된 것>`. 현재 이 레포에는 해당 언어를 위한 전용 리팩토링 스킬이 없으므로 수동 진행을 권장드립니다. 향후 `refactor-advisor-<언어>` 같은 파생 스킬이 만들어지면 그쪽을 사용하세요.

Java 파일로 확인되면 아래 항목을 파악한다:

- 클래스 계층 구조 및 인터페이스 관계
- 의존성 주입 구조 (생성자 주입 권장, 필드/Setter 주입은 스멜로 기록)
- 메서드별 역할과 복잡도
- 레이어 간 책임 분리 상태
- **Spring 기반 여부** 확인 — 순수 Java 라이브러리(Android, CLI 등)라면 "Spring 특화" 카테고리는 건너뛰고 리포트 서두에 그 사실을 명시한다 (Troubleshooting 참조)
- **기존 테스트 존재 여부** 확인 — 테스트가 없는 코드를 리팩토링할 때는 반드시 경고한다

### Step 3: 코드 스멜 탐지

`references/smell-catalog.md`의 카탈로그를 기준으로 문제를 식별한다. 주요 카테고리:
- **메서드 수준**: Long Method, Parameter Overload, Flag Argument 등
- **클래스 수준**: God Class, Feature Envy, Data Class 등
- **구조 수준**: 중복 코드, Shotgun Surgery, 순환 의존성 등
- **Spring 특화**: Controller 비대화, 빈 스코프 오용, 예외 처리 부재 등

**Sibling 스킬 경계**: 이 스킬은 **구조적 관점**(책임 분리·레이어 위반·타입 모델링)에만 집중한다. 아래 축에 해당하는 이슈는 리포트에 목록화만 하고 상세 분석·개선안 제시는 해당 스킬로 핸드오프한다 — "연관 스킬 안내" 섹션에 이관 안내를 명시한다:

- **트랜잭션 경계의 성능 영향** (커넥션 점유·락 경합) → performance-profiler
- **DB 쿼리 수/형태** (N+1, bulk 연산 누락) → performance-profiler
- **외부 호출 동기성** (동기 이메일·SMS·API 호출) → performance-profiler
- **테스트 작성 자체** — 이 스킬은 safety net 부재만 경고하고 실제 테스트는 작성하지 않는다 → junit-test-writer

**하이브리드 처리 원칙**: 같은 파일에 구조·성능 이슈가 섞여 있으면 구조 이슈는 본 스킬이 대안까지 제시하고, 성능 이슈는 "연관 스킬 안내" 섹션에 표로 목록화만 한 뒤 performance-profiler로 넘긴다. 상대 스킬 트리거어("성능 이슈 분석해줘" 같은)가 들어오면 리포트 서두에 "나는 구조 전담이지만 구조 이슈도 같이 있으니 이 부분만 다루고 나머지는 성능 스킬로 이관한다"를 한 줄로 명시하고 진행한다.

### Step 4: SOLID 원칙 검토

각 원칙 위반 여부를 검토한다:
- **SRP**: 이 클래스가 변경되어야 하는 이유가 하나인가?
- **OCP**: 새로운 케이스 추가 시 기존 코드를 수정해야 하는가?
- **LSP**: 하위 타입이 상위 타입의 계약을 깨뜨리는가?
- **ISP**: 클라이언트가 사용하지 않는 메서드에 의존하는가?
- **DIP**: 상위 모듈이 하위 모듈의 구체 타입에 의존하는가?

### Step 5: 디자인 패턴 적용 기회 식별

`references/pattern-guide.md`를 참고하여 패턴 적용이 자연스러운 지점을 찾는다. 패턴을 위한 패턴은 제안하지 않는다. 코드가 더 읽기 어려워지면 패턴을 적용하지 않는 것이 낫다.

### Step 6: 리포트 작성

분석 결과를 아래 "산출물 템플릿" 구조로 제시한다. 분석 모드는 여기서 종료한다. 리팩토링/바로 적용 모드는 Step 7로 이어진다.

### Step 7: 사용자 확인 및 적용 ("리팩토링 해줘"/"바로 적용해줘" 모드 전용)

원본을 바꾸는 경로는 되돌리기 어려우므로 아래 4단계 안전장치를 반드시 거친다. 파일 편집은 **③ 편집 적용** 단계에서만 일어난다.

#### ① 프리뷰 생성

Step 6의 리포트 뒤에 **적용 예정 변경 목록** 테이블을 이어붙여 먼저 출력한다. 컬럼은 아래와 같이 인라인 복제한다:

| #   | 이슈 (우선순위 #) | 대상 (before)               | 적용 후 (after)             | 심각도   |
| --- | ----------------- | --------------------------- | --------------------------- | -------- |
| 1   | 필드 주입 전환 (#3) | `@Autowired private Dep x;` | `private final Dep x;`      | Critical |
| 2   | 트랜잭션 경계 (#1)  | `public Order createOrder`  | `@Transactional public ...` | Critical |

- `대상`과 `적용 후`는 파일 편집 시 그대로 찾기/바꾸기에 쓸 수 있는 원문 스니펫이어야 한다 — 프리뷰가 실행 계획 역할까지 겸한다.
- `우선순위 #`는 리포트의 `리팩토링 우선순위` 테이블 순번과 동일하게 유지한다. 사용자가 "3번만 적용" 같은 선별 요청을 할 때 추적이 쉬워진다.

#### ② 확인 응답 프로토콜

프리뷰 뒤에 사용자에게 아래 네 가지 응답 경로를 명시적으로 제시한다:

- **`진행`** — 목록의 모든 변경을 순서대로 적용.
- **`Critical만`** — 심각도가 Critical인 항목만 적용.
- **`1, 3, 6만 진행`** 같은 **번호 선별** — 지정 번호만 적용하고 나머지는 버린다.
- **`취소`** — 어떤 편집도 수행하지 않고 종료.

"응", "오케이", "좋아" 같은 모호한 동의는 **전체 승인으로 해석하지 않는다**. 되돌리기 어려운 경로이므로 위 네 경로 중 하나의 명시적 키워드를 다시 요청한다.

**테스트 부재 시 추가 경고**: Step 2에서 `기존 테스트 없음`으로 판단된 경우, 프리뷰 직후에 한 번 더 경고한다 — "safety net 없이 진행하시겠습니까? `junit-test-writer`로 characterization test부터 만드는 걸 권장합니다." 사용자가 이 경고를 듣고도 `진행`을 택하면 적용한다.

#### ③ 편집 적용

- 프리뷰 목록의 각 항목마다 Codex 파일 편집 도구로 부분 수정한다. 프리뷰의 `대상` 스니펫을 찾고 `적용 후` 스니펫으로 바꾼다.
- `대상` 스니펫이 파일 안에 **여러 번 등장하는 경우에만** 전역 치환을 쓴다. 의도치 않은 전역 치환을 막기 위함이다.
- 원본 파일의 임포트 문·패키지 선언·섹션 순서는 건드리지 않는다.

#### ④ 적용 후 요약

편집이 끝나면 적용 요약을 채팅에 출력한다:
- 적용 N건 / 스킵 N건 / 실패 N건
- 실패가 있으면 실패한 이슈 번호와 원인(예: "before 스니펫이 파일에서 찾을 수 없음 — 이전 편집과 충돌")을 기재
- 리팩토링 후에도 테스트가 없다면 `junit-test-writer` 호출을 다시 한 번 권장

    TargetClass --> DepB : 주입
    TargetClass ..> ValueObject : 사용
​```

## 리팩토링 우선순위

우선순위는 **위험도 × 빈도 × (4 − 난이도)** 로 계산한다. 각 축을 상(3)/중(2)/하(1) 3단계로 매기고, 난이도는 역수로 반영하여 "쉬운데 위험한 것"이 먼저 오도록 한다. 동점은 **선행 조건이 있는 이슈**가 먼저다 (예: 생성자 주입이 테스트 작성보다 선행).

| 순위 | 이슈 | 심각도 | 위험도 | 빈도 | 난이도 | 종합점수 | 테스트 필요 |
|------|------|--------|--------|------|--------|----------|-------------|
| 1 | 생성자 주입 전환 | Critical | 중(2) | 상(3) | 하(1) | 18 | 기존 유지 가능 |
| 2 | `@Transactional` 추가 | Critical | 상(3) | 상(3) | 중(2) | 18 | 작성 필요 |

## 연관 스킬 안내
- 성능 관점 분석이 필요하면: "성능 분석해줘"로 performance-profiler 활용
- 리팩토링 후 테스트가 필요하면: "테스트 코드 작성해줘"로 junit-test-writer 활용

## 예시 시나리오

**사용자**: "OrderService 리팩토링 해줘"

**행동**:
1. OrderService.java 읽기
2. 의존성 클래스(OrderRepository, PaymentService 등) 확인
3. 테스트 파일(OrderServiceTest.java) 존재 여부 확인
4. 스멜 탐지 → SOLID 검토 → 패턴 기회 식별
5. 리포트 제시
6. 사용자 확인 후 코드 적용

**사용자**: "com.example.order 패키지 코드 품질 분석해줘"

**행동**:
1. 패키지 내 모든 클래스 목록 확인
2. 가장 큰 클래스, 가장 많이 참조되는 클래스 식별 → 우선 분석
3. 클래스 간 의존 관계 Mermaid 다이어그램 작성
4. 패키지 수준 이슈(순환 의존성, 레이어 위반) 중점 분석
5. 리포트만 제시 (분석 모드)

## 심각도 기준

| 심각도 | 기준 | 예시 |
|--------|------|------|
| **Critical** | 버그 위험, 데이터 정합성 문제 | 트랜잭션 없는 복합 쓰기, 동시성 문제 |
| **Major** | 가독성 심각 저하, 유지보수 비용 높음 | God Class, 200줄 메서드, 순환 의존성 |
| **Minor** | 소소한 개선 기회 | 네이밍 개선, 불필요한 주석 |

## 제안 원칙

- 모든 리팩토링은 **왜** 필요한지 설명한다. "이렇게 하는 게 맞다"가 아니라 "이렇게 하면 ~할 때 코드를 더 쉽게 이해/수정할 수 있다"로 설명한다.
- 대안이 여러 개일 때는 각각의 트레이드오프를 명시하고 맥락에 맞는 것을 권장한다. 정답이 명백한 경우(예: 필드 주입 → 생성자 주입, `Optional.orElse(null)` → `orElseThrow`)에는 대안 B를 생략하고 단일안만 제시해도 된다 — 존재하지 않는 트레이드오프를 억지로 만드는 것이 더 해롭다.
- 과도한 추상화를 경계한다. 세 줄 중복이 한 번의 추상화보다 나을 수 있다.
- 리팩토링 우선순위는 **위험도 x 빈도 x 난이도(역수)** 로 판단한다.
- 기존 테스트가 없으면 리팩토링 전 테스트 작성을 권장하고, junit-test-writer 스킬과의 연계를 안내한다.

## Troubleshooting

**Java가 아닌 파일이 입력된 경우 (PHP, Python, JavaScript, Go, Ruby 등)**
- 원인: 사용자가 다른 언어 파일을 직접 지정했거나, 언어를 명시하지 않고 "내 Laravel 프로젝트 리팩토링해줘" 같은 요청을 보낸 경우
- 해결: **Step 2의 언어 사전 체크에서 즉시 종료한다.** smell-catalog과 pattern-guide가 Java/Spring 이디엄 전용이므로 다른 언어에 적용하면 잘못된 제안이 나온다 (예: PHP 코드에 `@Autowired` 제거 권장, Python 코드에 `Optional.orElseThrow()` 권장). 사용자에게 "이 스킬은 Java/Spring 전용입니다"를 분명히 알리고 수동 진행을 권장한다. 향후 `refactor-advisor-php`, `refactor-advisor-python` 같은 파생 스킬이 만들어지면 그쪽으로 리다이렉트.

**`.java` 파일이지만 Spring을 쓰지 않는 순수 Java 라이브러리인 경우 (Android, CLI, 라이브러리 모듈)**
- 원인: JVM 생태계지만 Spring 기반이 아니라 `@Service`·`@Autowired`·`@Transactional` 같은 Spring 어노테이션이 없다
- 해결: **스킬을 계속 진행하되 범위를 축소한다.** Step 3의 "메서드/클래스/구조 수준" 스멜 탐지와 Step 4의 SOLID 검토는 Java 공통 원칙이므로 그대로 적용 가능하다. "Spring 특화" 카테고리(Controller 비대화·빈 스코프 오용·`@Transactional` 부재 등)는 건너뛴다. 리포트 서두에 "Spring 기반이 아니어서 Spring 특화 카테고리는 분석에서 제외했다"를 한 줄 명시해 사용자가 혼란하지 않도록 한다.

**Kotlin/Spring 프로젝트인 경우**
- 원인: JVM + Spring 생태계지만 Kotlin은 이디엄이 Java와 다르다 (data class, sealed class, `val` 불변, scope function, nullable 타입, `?.` / `?:` 등). 현재 smell-catalog과 pattern-guide는 Kotlin 이디엄을 다루지 않는다
- 해결: **기본적으로 거절한다** — 언어 사전 체크에서 `.kt` 확장자를 Java 아님으로 판정해 종료한다. 사용자가 "그래도 구조 분석만이라도 해줘"라고 명시적으로 요청하면, 공통 원칙(SOLID, God Class, Long Method)만 적용하고 Kotlin 특유의 관용구(예: Java의 `Optional` 대신 Kotlin의 nullable)는 건드리지 않겠다는 단서를 붙여 진행한다. 안전한 기본값은 수동 진행 권장.
