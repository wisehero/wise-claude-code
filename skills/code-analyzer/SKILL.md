# Code Analyzer

코드베이스의 구조를 파악하고 비즈니스 로직을 이해하기 쉽게 설명하는 스킬. 언어에 무관하게 동작하며, mermaid 다이어그램을 포함한 분석 리포트를 제공한다.

## When to Use

다음 같은 요청에 반드시 사용한다:

- **코드베이스 구조 파악** — "이 프로젝트 어떻게 되어있어?", "아키텍처 분석"
- **비즈니스 로직 이해** — "결제 흐름이 어떻게 동작하는지", "이 기능 뭐하는 거야"
- **온보딩용 레거시 코드 파악** — 처음 보는 모듈을 이해해야 할 때
- **PR 리뷰 전 컨텍스트 확보** — 변경 대상 주변 코드를 이해해야 리뷰가 가능할 때

## When NOT to Use

다음 경우는 다른 스킬이 더 적합하므로 이 스킬을 호출하지 않는다:

- **코드 품질 평가/개선 제안** → `refactor-advisor` 사용. 이 스킬은 분석만 하고 "좋다/나쁘다"를 판단하지 않는다.
- **성능 병목 분석** → `performance-profiler` 사용
- **테스트 코드 작성** → `junit-test-writer` 사용
- **단일 파일 단순 읽기** → `Read` 도구로 충분하다. 분석 리포트까지 필요 없는 요청에 스킬을 호출하는 것은 과잉이다.

## 핵심 원칙

1. **실제 이름을 보존한다.** 다이어그램과 자연어 설명 모두에서 실제 클래스명, 메서드명, 모듈명을 그대로 쓴다. 추상화된 이름("ServiceClass", "HelperMethod")은 금지 — 리포트를 읽고 실제 코드로 찾아갈 수 없게 된다.
2. **진입점에서 시작해 필요한 만큼만 읽는다.** 범위 내 모든 파일을 무작정 Read하지 않는다. 진입점을 먼저 식별한 뒤 import/require 그래프를 따라가며 선택적으로 읽는다. 분석 깊이 기준(1단계)을 초과하는 순간 사용자에게 범위 축소를 제안한다.

## 상세 단계

### 1단계: 분석 범위 확정

사용자의 요청에서 분석 대상을 파악한다.

**범위가 명확한 경우** — 바로 2단계로 진행:
- "src/auth 모듈 분석해줘" → `src/auth/` 디렉토리
- "UserService.java 코드 분석" → 해당 파일 + 직접 의존 파일
- "로그인 기능 코드 분석해줘" → 로그인 관련 파일을 탐색하여 특정

**범위가 애매한 경우** — 역질문으로 확정:
- "코드 분석해줘" → "어떤 파일이나 모듈을 분석할까요? 또는 특정 기능(예: 로그인, 결제)이 있으면 알려주세요."
- "이 프로젝트 분석해줘" → "전체 아키텍처 개요를 원하시나요, 아니면 특정 모듈을 깊이 보고 싶으신가요?"

범위 확정 후, 분석 대상의 언어와 프레임워크를 파일 확장자 및 설정 파일(package.json, build.gradle, pom.xml, composer.json 등)로 자동 감지한다.

#### 언어별 힌트 파일 로드

특정 언어/프레임워크가 감지되면, `references/` 하위의 힌트 파일을 먼저 Read한 뒤 2단계로 진행한다. 힌트 파일에는 해당 언어의 진입점 패턴, 레이어 구조, Grep 치트시트, 분석 시 주의점이 정리되어 있다.

| 감지 조건 | 로드할 힌트 파일 |
|---|---|
| `composer.json` 또는 `artisan` 또는 `.php` 파일 5개 이상 | `references/php-hints.md` (PHP 5.6 / PHP 8.3 + Laravel 10) |

해당 언어의 힌트 파일이 없으면 힌트 Read를 건너뛰고 바로 2단계로 진행한다.

#### 분석 깊이 기준

범위 내 파일 수에 따라 분석 깊이를 조절한다:

- **10개 이하**: 모든 파일을 읽고 상세 분석
- **11~30개**: 진입점 + 핵심 서비스/모델 중심으로 분석. 유틸리티, 설정 파일은 목록만 정리
- **30개 초과**: 사용자에게 범위 축소를 제안. "이 모듈에 파일이 많아서, 핵심 기능 위주로 분석할까요? 아니면 특정 레이어(controller/service/repository)를 선택해주세요."

---

### 2단계: 코드 탐색 및 구조 파악

아래 순서를 정확히 따른다. 각 단계의 도구 호출은 구체적이어야 하며, 가능한 호출은 **한 메시지에서 병렬로** 실행한다.

1. **디렉토리 트리 파악 (단일 호출)**
   - `Glob("{범위}/**/*")` 한 번으로 파일 목록 확보
   - 예: `Glob("src/auth/**/*")`

2. **심볼 + 의존성 병렬 탐색 (한 메시지에서 두 Grep 병렬 호출)**
   - 심볼 보유 파일 찾기: `Grep(pattern="class |function |def |func ", path="{범위}", output_mode="files_with_matches")`
   - 의존성 엣지 수집: `Grep(pattern="import |require\\(|#include|from .* import", path="{범위}", output_mode="content", -n=true)`
   - 두 호출을 순차적으로 내지 말고 반드시 병렬 실행하여 라운드트립을 절반으로 줄인다

3. **진입점부터 선별적 Read**
   - 진입점 후보: `main`, `index`, `App`, `*Controller`, `*Application` 등. 설정 파일(`package.json` scripts, `build.gradle` tasks)에서 entry를 확인할 수도 있다.
   - 진입점 파일을 먼저 Read한 뒤, 2단계에서 수집한 import 그래프를 따라 **호출되는 파일만** 추가 Read
   - 유틸리티/설정 파일은 Read하지 않고 Grep 결과만으로 목록화

4. **계층 식별**
   - controller → service → repository 같은 레이어 구분을 기록
   - 레이어가 불분명한 구조는 "분류 없음"으로 남기고 임의 분류를 강제하지 않는다

**토큰 효율 규칙**: Read 횟수가 1단계의 분석 깊이 기준(10/11-30/30+)을 초과하면 더 읽지 말고 사용자에게 범위 축소를 제안한다.

---

### 3단계: 비즈니스 로직 분석

코드가 "무엇을 하는지"를 자연어로 설명한다.

각 주요 기능에 대해:
- **목적**: 이 기능이 해결하는 문제가 무엇인지
- **흐름**: 입력 → 처리 과정 → 출력을 단계별로 설명
- **핵심 규칙**: 조건 분기, 유효성 검증, 비즈니스 규칙을 명시
- **데이터 흐름**: 어떤 데이터가 어디서 생성되고 어디로 전달되는지

설명은 개발자가 아닌 사람도 이해할 수 있을 정도로 자연스럽게 작성하되, 코드 레벨의 정확성은 유지한다. 기술 용어를 쓸 때는 해당 코드에서 실제 사용하는 이름(클래스명, 메서드명)을 함께 언급하여 코드와 설명을 연결한다.

각 주요 기능의 핵심 메서드 본문까지 Read하여 비즈니스 규칙(조건 분기, 검증 로직, 예외 처리)을 실제 코드에서 직접 확인한다. 메서드 시그니처만 보고 추측해서 작성하지 않는다.

---

### 4단계: 다이어그램 생성

분석 결과를 시각화한다. 모든 다이어그램은 mermaid 문법으로 작성한다.

#### 의존성 다이어그램

구성 요소 간 의존 관계를 `graph TD`로 표현한다.
- 노드: 클래스, 모듈, 또는 주요 함수
- 화살표: 의존 방향 (A가 B를 사용하면 A → B)
- 외부 의존성(DB, API, 라이브러리)은 구분하여 표시

#### 시퀀스 다이어그램

주요 기능별로 객체 간 상호작용을 `sequenceDiagram`으로 표현한다.
- 하나의 기능 흐름(예: 주문 생성, 로그인 처리)을 하나의 시퀀스 다이어그램으로
- participant는 실제 코드의 클래스/모듈명을 사용
- 요청(->>) / 응답(-->>)을 구분
- 분기가 있으면 alt/else 블록 활용

시퀀스 다이어그램은 분석 범위 내 주요 기능마다 각각 작성한다.

---

### 5단계: 리포트 출력

리포트는 아래 4개 섹션을 **이 순서 그대로** 포함해야 한다. 완전한 예시는 `references/report-template.md`에 있지만, 아래 인라인 명세가 우선한다.

**리포트 상단 — YAML frontmatter**

```yaml
---
analyzed_at: YYYY-MM-DD
scope: [분석 범위 경로]
language: [감지된 언어/프레임워크]
---
```

**섹션 1: 구조 개요**
- 핵심 구성 요소 테이블 (컬럼 3개 고정): `| 구성 요소 | 경로 | 역할 |`
- 의존성 다이어그램 1개: mermaid `graph TD`. 노드명은 실제 클래스/모듈명, 외부 의존성(DB, 외부 API)은 별도 스타일로 구분
- 호출 흐름 순번 목록: 진입점부터 최종 호출 대상까지 `1. → 2. → 3.` 형식

**섹션 2: 비즈니스 로직 분석**
- 주요 기능마다 4개 소항목을 **반드시 모두** 포함 — 생략·추가 금지:
  - **목적**: 이 기능이 해결하는 문제
  - **흐름**: 입력 → 처리 → 출력
  - **핵심 규칙**: 조건 분기, 검증, 비즈니스 규칙
  - **데이터 흐름**: 어떤 데이터가 어디서 생성되고 어디로 전달되는지
- 기능명은 코드에서 실제 쓰는 이름 (예: `PaymentService.processPayment`)

**섹션 3: 시퀀스 다이어그램**
- 주요 기능마다 `sequenceDiagram` 1개
- `participant`는 실제 클래스/모듈명 (`Client`, `Service` 같은 추상명 금지)
- 요청 `->>`와 응답 `-->>`를 구분
- 분기는 `alt/else` 블록 사용

**섹션 4: 참고 사항**
- 순환 의존성, 사용되지 않는 심볼, 추가 분석이 필요한 지점 등 특이사항만 기록
- 특이사항이 없으면 이 섹션을 생략해도 된다

**출력 방식**
- 기본: 터미널에 리포트 직접 출력
- 사용자가 파일 저장을 요청한 경우: `분석리포트_[대상명]_YYYYMMDD.md` 형식으로 저장

## Examples

### 예시 1: 특정 모듈 분석

```
사용자: "src/auth 모듈 분석해줘"
동작:
  1. src/auth/ 디렉토리 범위 확정
  2. Glob("src/auth/**/*")로 파일 목록 확인 → AuthController, AuthService, TokenProvider 등 식별
  3. 진입점(AuthController)부터 Read → import 따라가며 AuthService → TokenProvider 순서로 탐색
  4. 로그인/회원가입/토큰갱신 비즈니스 로직 설명
  5. 의존성 다이어그램 + 로그인 시퀀스 다이어그램 생성
  6. 터미널에 리포트 출력
```

### 예시 2: 특정 기능 분석

```
사용자: "결제 기능 코드가 어떻게 동작하는지 분석해줘"
동작:
  1. Grep("Payment|Order|결제")로 관련 파일 탐색 → PaymentController, OrderService 등 발견
  2. 범위 확정 후 구조 파악
  3. 결제 흐름을 자연어로 설명
  4. 결제 처리 시퀀스 다이어그램 생성
  5. 터미널 출력
```

### 예시 3: 범위가 모호한 요청 (대화형)

```
사용자: "이 프로젝트 코드 분석해줘"

     주요 디렉토리로는 src/auth, src/payment, src/user가 있습니다."

    [3-5단계 진행 후 리포트 출력]
```

  1~5단계 동일

## Troubleshooting

**분석 대상 파일이 너무 많은 경우**
- 원인: 프로젝트 전체 또는 대규모 모듈 지정
- 해결: 분석 깊이 기준(1단계)에 따라 범위를 좁히자고 제안. "이 모듈에 파일이 50개 이상인데, 핵심 기능 위주로 분석할까요?"

**언어/프레임워크를 자동 감지하지 못한 경우**
- 원인: 설정 파일 부재 또는 비표준 구조
- 해결: 사용자에게 언어와 프레임워크를 직접 확인

**mermaid 다이어그램이 너무 복잡한 경우**
- 원인: 구성 요소가 너무 많아 다이어그램 가독성 저하
- 해결: 핵심 구성 요소만 포함하고, 세부 사항은 별도 다이어그램으로 분리. 노드가 15개를 초과하면 레이어별로 분리된 다이어그램을 만든다.

**진입점을 찾을 수 없는 경우**
- 원인: `main`/`index`/`App`/`*Controller` 네이밍을 따르지 않는 프로젝트
- 해결: 설정 파일에서 entry 지정을 먼저 확인 — `package.json`의 `scripts.start`/`main`, `build.gradle`의 `mainClass`, `pom.xml`의 `<mainClass>`, `pyproject.toml`의 `scripts`. 설정 파일에도 없으면 사용자에게 "이 프로젝트의 진입점 파일을 알려주세요"라고 질문.

**순환 의존성이 발견된 경우**
- 원인: 모듈 간 A → B → A 형태의 순환 참조
- 해결: 의존성 다이어그램에 점선 화살표(`A -.->|순환| B`)로 표시하고, 섹션 4(참고 사항)에 "순환 의존성: A ↔ B — 진입점 판단 주의" 명시. 분석과 평가를 섞지 않는 원칙에 따라 "이건 나쁜 설계다"라고 쓰지는 않는다 — 사실만 기록한다.
