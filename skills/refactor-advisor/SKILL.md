# Refactor Advisor

Java/Spring 코드를 분석하여 리팩토링 기회를 식별하고, 구체적인 대안 코드와 트레이드오프를 제시하는 스킬.

대원칙: **코드는 읽기 쉽고 이해하기 쉬워야 한다.** 모든 리팩토링 제안은 이 원칙에 부합하는지를 기준으로 판단한다.

## 분석 워크플로우

### Step 1: 대상과 모드 파악

사용자 요청에서 두 가지를 확인한다:

**분석 대상:**
- 단일 클래스: 해당 클래스와 직접 의존성 분석
- 패키지: 핵심 클래스(가장 많이 참조되거나 가장 큰 클래스)를 먼저 식별 → 깊이 분석 → 나머지 클래스는 관계 중심으로 분석
- 파일 경로: 해당 파일 중심으로 분석

지정이 없으면 사용자에게 분석 대상을 물어본다.

**동작 모드:**
- "분석해줘", "봐줘": 리포트만 제시 (기본값)
- "리팩토링 해줘", "개선해줘", "정리해줘": 리포트 제시 후 사용자 확인을 받고 코드 적용
- "바로 적용해줘": 리포트 없이 바로 코드 수정 (Critical 이슈만)

### Step 2: 코드 읽기 및 구조 파악

대상 코드를 읽고 다음을 파악한다:
- 클래스 계층 구조 및 인터페이스 관계
- 의존성 주입 구조 (생성자 주입 권장, 필드/Setter 주입은 스멜로 기록)
- 메서드별 역할과 복잡도
- 레이어 간 책임 분리 상태
- **기존 테스트 존재 여부** 확인 — 테스트가 없는 코드를 리팩토링할 때는 반드시 경고한다

### Step 3: 코드 스멜 탐지

`references/smell-catalog.md`의 카탈로그를 기준으로 문제를 식별한다. 주요 카테고리:
- **메서드 수준**: Long Method, Parameter Overload, Flag Argument 등
- **클래스 수준**: God Class, Feature Envy, Data Class 등
- **구조 수준**: 중복 코드, Shotgun Surgery, 순환 의존성 등
- **Spring 특화**: Controller 비대화, 빈 스코프 오용, 예외 처리 부재 등

트랜잭션 관련 이슈는 **구조적 관점**(책임 분리, 레이어 위반)에서만 다룬다. 성능 관점의 트랜잭션 분석은 performance-profiler 스킬의 영역이다.

### Step 4: SOLID 원칙 검토

각 원칙 위반 여부를 검토한다:
- **SRP**: 이 클래스가 변경되어야 하는 이유가 하나인가?
- **OCP**: 새로운 케이스 추가 시 기존 코드를 수정해야 하는가?
- **LSP**: 하위 타입이 상위 타입의 계약을 깨뜨리는가?
- **ISP**: 클라이언트가 사용하지 않는 메서드에 의존하는가?
- **DIP**: 상위 모듈이 하위 모듈의 구체 타입에 의존하는가?

### Step 5: 디자인 패턴 적용 기회 식별

`references/pattern-guide.md`를 참고하여 패턴 적용이 자연스러운 지점을 찾는다. 패턴을 위한 패턴은 제안하지 않는다. 코드가 더 읽기 어려워지면 패턴을 적용하지 않는 것이 낫다.

### Step 6: 리포트 작성

분석 결과를 아래 구조로 제시한다.

## 산출물 템플릿

```markdown
# [대상] 리팩토링 분석

## 요약
- **분석 대상**: (파일/클래스/패키지 경로)
- **심각도 분포**: Critical N개 / Major N개 / Minor N개
- **테스트 커버리지**: 있음/없음 (없으면 "리팩토링 전 테스트 작성 권장" 경고)
- **핵심 개선 포인트**: (가장 중요한 1-2가지)

## 의존성 구조

(Mermaid classDiagram으로 클래스 간 의존 관계 시각화)

## 발견 사항

### [심각도] 이슈 제목
- **위치**: `패키지.클래스#메서드` (파일:라인)
- **카테고리**: 코드 스멜 / SOLID 위반 / 패턴 적용 기회
- **문제**: 무엇이 문제이고 왜 문제인지
- **영향**: 이 상태가 지속되면 어떤 문제가 생기는지

**현재 코드:**
(문제가 되는 코드 발췌)

**대안 A: [접근법 이름]**
(리팩토링된 코드)
- 장점: ...
- 단점: ...

**대안 B: [접근법 이름]** (해당 시)
(다른 접근의 리팩토링 코드)
- 장점: ...
- 단점: ...

**권장**: 대안 A/B, 이유: ...

| 순위 | 이슈 | 심각도 | 난이도 | 영향 범위 | 테스트 필요 |
|------|------|--------|--------|-----------|-------------|

- 성능 관점 분석이 필요하면: "성능 분석해줘"로 performance-profiler 활용
- 리팩토링 후 테스트가 필요하면: "테스트 코드 작성해줘"로 junit-test-writer 활용
```

## 예시 시나리오

**사용자**: "OrderService 리팩토링 해줘"

**행동**:
1. OrderService.java 읽기
2. 의존성 클래스(OrderRepository, PaymentService 등) 확인
3. 테스트 파일(OrderServiceTest.java) 존재 여부 확인
4. 스멜 탐지 → SOLID 검토 → 패턴 기회 식별
5. 리포트 제시
6. 사용자 확인 후 코드 적용

**사용자**: "com.example.order 패키지 코드 품질 분석해줘"

**행동**:
1. 패키지 내 모든 클래스 목록 확인
2. 가장 큰 클래스, 가장 많이 참조되는 클래스 식별 → 우선 분석
3. 클래스 간 의존 관계 Mermaid 다이어그램 작성
4. 패키지 수준 이슈(순환 의존성, 레이어 위반) 중점 분석
5. 리포트만 제시 (분석 모드)

## 심각도 기준

| 심각도 | 기준 | 예시 |
|--------|------|------|
| **Critical** | 버그 위험, 데이터 정합성 문제 | 트랜잭션 없는 복합 쓰기, 동시성 문제 |
| **Major** | 가독성 심각 저하, 유지보수 비용 높음 | God Class, 200줄 메서드, 순환 의존성 |
| **Minor** | 소소한 개선 기회 | 네이밍 개선, 불필요한 주석 |

## 제안 원칙

- 모든 리팩토링은 **왜** 필요한지 설명한다. "이렇게 하는 게 맞다"가 아니라 "이렇게 하면 ~할 때 코드를 더 쉽게 이해/수정할 수 있다"로 설명한다.
- 대안이 여러 개일 때는 각각의 트레이드오프를 명시하고 맥락에 맞는 것을 권장한다.
- 과도한 추상화를 경계한다. 세 줄 중복이 한 번의 추상화보다 나을 수 있다.
- 리팩토링 우선순위는 **위험도 x 빈도 x 난이도(역수)** 로 판단한다.
- 기존 테스트가 없으면 리팩토링 전 테스트 작성을 권장하고, junit-test-writer 스킬과의 연계를 안내한다.
