# Refactor Advisor

Java/Spring 코드를 분석하여 리팩토링 기회를 식별하고, 구체적인 대안 코드와 트레이드오프를 제시하는 스킬.

대원칙: **코드는 읽기 쉽고 이해하기 쉬워야 한다.** 모든 리팩토링 제안은 이 원칙에 부합하는지를 기준으로 판단한다.

## 분석 워크플로우

### 1. 대상 파악

사용자가 지정한 파일/클래스/패키지를 확인한다:
- 단일 클래스: 해당 클래스와 직접 의존성 분석
- 패키지: 패키지 내 모든 클래스의 관계와 책임 분석
- 파일 경로: 해당 파일 중심으로 분석

지정이 없으면 사용자에게 분석 대상을 물어본다.

### 2. 코드 읽기 및 구조 파악

대상 코드를 읽고 구조를 파악한다:
- 클래스 계층 구조 및 인터페이스 관계
- 의존성 주입 구조 (생성자, 필드, Setter)
- 메서드별 역할과 복잡도
- 트랜잭션 경계 (`@Transactional` 위치와 전파 설정)
- 레이어 간 책임 분리 상태

### 3. 코드 스멜 탐지

아래 카테고리별로 문제를 식별한다:

#### 메서드 수준
| 스멜 | 징후 |
|------|------|
| Long Method | 한 메서드가 여러 추상화 수준의 작업을 수행 |
| Parameter Overload | 파라미터 3개 초과, 특히 같은 타입 연속 |
| Flag Argument | boolean 파라미터로 분기하는 메서드 |
| 복잡한 조건문 | 중첩 if/else, 긴 조건 체인 |
| 부수효과 숨김 | 메서드명에 드러나지 않는 상태 변경 |

#### 클래스 수준
| 스멜 | 징후 |
|------|------|
| God Class | 너무 많은 책임, 필드 10개 이상, 메서드 15개 이상 |
| Feature Envy | 다른 객체의 데이터를 지나치게 사용 |
| Data Class | getter/setter만 있고 행위가 없는 클래스 |
| Inappropriate Intimacy | 두 클래스가 서로의 내부를 과도하게 참조 |
| Middle Man | 위임만 하는 클래스 |

#### 구조 수준
| 스멜 | 징후 |
|------|------|
| 중복 코드 | 유사한 로직이 여러 곳에 산재 |
| Shotgun Surgery | 하나의 변경이 여러 클래스 수정을 요구 |
| Divergent Change | 하나의 클래스가 여러 이유로 변경 |
| 순환 의존성 | 패키지/클래스 간 순환 참조 |

#### Spring 특화
| 스멜 | 징후 |
|------|------|
| 트랜잭션 경계 오류 | Service가 아닌 곳에 @Transactional, 불필요한 전파 설정 |
| Controller 비대화 | Controller에 비즈니스 로직 존재 |
| Repository 로직 누수 | Service에서 직접 쿼리 조합 |
| 빈 스코프 오용 | Singleton에 상태 저장, Prototype 오용 |
| 예외 처리 부재/과잉 | catch로 삼키기, 무분별한 throws |

### 4. SOLID 원칙 검토

각 원칙 위반 여부를 검토한다:

- **SRP**: 이 클래스가 변경되어야 하는 이유가 하나인가?
- **OCP**: 새로운 케이스 추가 시 기존 코드를 수정해야 하는가?
- **LSP**: 하위 타입이 상위 타입의 계약을 깨뜨리는가?
- **ISP**: 클라이언트가 사용하지 않는 메서드에 의존하는가?
- **DIP**: 상위 모듈이 하위 모듈의 구체 타입에 의존하는가?

### 5. 디자인 패턴 적용 기회 식별

코드 구조에서 패턴 적용이 자연스러운 지점을 찾는다:
- 복잡한 분기 → Strategy / State
- 객체 생성 로직 복잡 → Factory / Builder
- 여러 단계 처리 → Template Method / Chain of Responsibility
- 이벤트 기반 처리 → Observer / Event
- 부가 기능 추가 → Decorator

패턴을 위한 패턴은 제안하지 않는다. 코드가 더 읽기 어려워지면 패턴을 적용하지 않는 것이 낫다.

## 산출물 구조

분석 결과를 아래 형식으로 제시한다:

```markdown
# [대상] 리팩토링 분석

## 요약
- **분석 대상**: (파일/클래스/패키지 경로)
- **심각도 분포**: Critical N개 / Major N개 / Minor N개
- **핵심 개선 포인트**: (가장 중요한 1-2가지)

## 발견 사항

### [심각도] 이슈 제목
- **위치**: `패키지.클래스#메서드` (파일:라인)
- **문제**: 무엇이 문제이고 왜 문제인지 설명
- **영향**: 이 상태가 지속되면 어떤 문제가 생기는지

**현재 코드:**
(문제가 되는 코드 발췌)

**대안 A: [접근법 이름]**
(리팩토링된 코드)
- 장점: ...
- 단점: ...

**대안 B: [접근법 이름]** (해당 시)
(다른 접근의 리팩토링 코드)
- 장점: ...
- 단점: ...

**권장**: 대안 A/B, 이유: ...

---

(다음 이슈 반복)

## 리팩토링 우선순위

| 순위 | 이슈 | 심각도 | 난이도 | 영향 범위 |
|------|------|--------|--------|-----------|
| 1 | ... | Critical | 낮음 | 넓음 |
| 2 | ... | Major | 중간 | 보통 |

## 트랜잭션 경계 분석 (해당 시)

현재 트랜잭션 구조와 개선안을 별도로 정리한다:
- 트랜잭션 범위가 넓은 메서드
- 읽기 전용 분리 가능한 메서드
- 전파 설정 개선 포인트
```

## 심각도 기준

| 심각도 | 기준 |
|--------|------|
| **Critical** | 버그 위험, 데이터 정합성 문제, 트랜잭션 오류 |
| **Major** | 가독성 심각 저하, 유지보수 비용 높음, 확장 어려움 |
| **Minor** | 컨벤션 불일치, 소소한 개선 기회 |

## 제안 원칙

- 모든 리팩토링은 **왜** 필요한지 설명한다. "이렇게 하는 게 맞다"가 아니라 "이렇게 하면 ~할 때 코드를 더 쉽게 이해/수정할 수 있다"로 설명한다.
- 대안이 여러 개일 때는 각각의 트레이드오프를 명시하고 맥락에 맞는 것을 권장한다.
- 과도한 추상화를 경계한다. 세 줄 중복이 한 번의 추상화보다 나을 수 있다.
- 리팩토링 우선순위는 **위험도 x 빈도 x 난이도(역수)** 로 판단한다.
- 기존 테스트가 있는지 확인하고, 테스트 없이 리팩토링하는 위험을 언급한다.
