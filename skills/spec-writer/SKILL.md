# Spec Writer

대화형 인터뷰를 통해 시스템 요구사항을 수집하고, IEEE 830 표준 기반의 SRS(Software Requirements Specification) 문서를 마크다운 파일로 생성하는 스킬.

## 핵심 원칙

이 스킬의 목적은 **팀이 공유할 수 있는 명확한 요구사항 문서를 만드는 것**이다. 인터뷰 과정에서 사용자가 미처 생각하지 못한 부분을 자연스럽게 끌어내는 것이 핵심이다 — 좋은 SRS는 "빠진 요구사항"을 조기에 발견하여 개발 중 재작업을 줄여주기 때문이다.

인터뷰는 **4단계로 나눠서** 진행한다. 한 번에 모든 걸 물으면 사용자가 압도당하고, 앞선 답변이 뒤의 질문에 영향을 미치는 경우가 많기 때문이다. 각 단계에서 2~4개의 핵심 질문만 던지고, 답변을 바탕으로 후속 질문을 조정한다.

요구사항 ID는 **`FR-001`, `NFR-001` 형식**으로 부여한다. 팀원 간 커뮤니케이션에서 "그 기능"이 아닌 "FR-012"로 지칭하면 모호함이 사라진다.

비기능 요구사항에는 **측정 가능한 기준**을 포함한다. "빨라야 한다"가 아니라 "응답 시간 200ms 이하"처럼 구체적으로 명시해야 테스트 가능하고 팀 간 합의가 명확해진다.

## 상세 단계

### 1단계: 프로젝트 개요 인터뷰

시스템의 큰 그림을 파악한다. 모든 인터뷰 단계에서 `AskUserQuestion` 도구를 적극 활용하여 클릭 가능한 선택지를 제공한다 — 사용자가 타이핑 없이 빠르게 응답할 수 있고, 선택지를 보며 미처 생각하지 못한 항목을 떠올리는 효과도 있다.

핵심 질문:
- **시스템 이름과 한 줄 설명** — 이 시스템이 무엇인지
- **핵심 사용자(액터)** — 누가 이 시스템을 사용하는지 (예: 일반 사용자, 관리자, 외부 시스템)
- **해결하려는 문제** — 이 시스템이 왜 필요한지
- **프로젝트 범위** — 이번 버전에서 다루는 것과 다루지 않는 것

사용자가 이미 상세한 설명을 제공했다면 중복 질문하지 않는다. 대화 맥락에서 이미 답변된 내용은 확인만 하고 넘어간다.

---

### 2단계: 기능 요구사항 인터뷰

시스템이 **무엇을 해야 하는지**를 구체화한다. `references/interview-guide.md`를 참조하여 도메인별 맞춤 질문을 활용한다:
- 1단계 추가 질문: 웹서비스/모바일/백오피스/API별 도메인 특화 질문
- 2단계 심화 질문: 인증/인가, 데이터 관리, 검색, 알림, 결제 영역
- 3단계 기본값 표: 규모별 성능·가용성 수치, 보안 체크리스트
- 4단계 확인 사항: REST API, 메시지큐, 데이터베이스 인터페이스

핵심 질문:
- **핵심 기능 목록** — 시스템의 주요 기능을 우선순위와 함께 나열
- **각 기능의 상세 시나리오** — 입력 → 처리 → 출력 흐름
- **예외 상황** — 실패 시 어떻게 처리하는지
- **데이터 요구사항** — 어떤 데이터를 저장하고 관리하는지

각 기능은 `references/srs-template.md`의 FR 형식을 **정확히** 따른다:

```
#### FR-XXX: [기능 제목]

- **설명**: [기능이 무엇을 하는지]
- **선행 조건**: [이 기능이 실행되기 위한 조건]

**입력 데이터:**

| 필드명 | 타입 | 필수 여부 | 검증 규칙 | 설명 |
|--------|------|-----------|-----------|------|

**기본 흐름:**

1. [동작 1]
2. [동작 2]

**출력 데이터:**

| 필드명 | 타입 | 설명 |
|--------|------|------|

**예외 흐름:**

| 조건 | HTTP 상태 | 에러 코드 | 설명 |
|------|-----------|-----------|------|

- **후행 조건**: [기능 완료 후 시스템 상태]
- **우선순위**: 필수 / 권장 / 선택
```

모든 FR 항목은 이 형식을 빠짐없이 따른다. 일부 FR만 다른 형식으로 작성하면 안 된다.

기능이 10개를 넘으면 도메인별로 그룹핑하여 정리한다. 사용자가 한 번에 모든 기능을 말하기 어려울 수 있으므로, 핵심 기능부터 시작하고 점진적으로 확장한다.

---

### 3단계: 비기능 요구사항 & 제약조건 인터뷰

시스템이 **어떻게 동작해야 하는지**의 품질 속성을 정의한다.

핵심 질문:
- **성능** — 동시 사용자 수, 응답 시간 목표, 처리량
- **보안** — 인증/인가 방식, 데이터 암호화, 감사 로그
- **가용성** — 목표 가동률, 장애 복구 시간(RTO/RPO)
- **확장성** — 예상 성장률, 스케일링 전략
- **기술 제약** — 사용할 기술 스택, 호환성 요구사항, 규제/컴플라이언스

비기능 요구사항에는 반드시 **측정 기준**을 포함하도록 유도한다. 사용자가 모호하게 답변하면 구체적인 수치를 제안하여 선택하게 한다. 예를 들어 "빨랐으면 좋겠어요"라는 답변에는 "API 응답 시간 기준으로 200ms, 500ms, 1초 중 어떤 수준을 목표로 할까요?"처럼 선택지를 제시한다.

---

### 4단계: 인터페이스 & 외부 시스템 인터뷰

시스템의 경계와 외부 연동을 정의한다.

핵심 질문:
- **사용자 인터페이스** — 웹/모바일/데스크톱, 주요 화면 구성
- **외부 시스템 연동** — 연동할 API, 서드파티 서비스, 데이터베이스
- **데이터 인터페이스** — 가져오기/내보내기 형식, 데이터 마이그레이션
- **통신 인터페이스** — 프로토콜(REST, gRPC, WebSocket 등), 메시지 큐

외부 시스템이 없는 단순한 프로젝트라면 이 단계를 간소화한다. 모든 시스템이 복잡한 연동을 가질 필요는 없다.

---

### 5단계: SRS 문서 생성 & 파일 저장

인터뷰에서 수집한 내용을 바탕으로 SRS 문서를 생성한다. **`references/srs-template.md`의 구조와 형식을 그대로 따른다** — 섹션 순서, 테이블 형식, 항목 배치를 임의로 변경하지 않는다. IEEE 830 구조:
- 1장 개요: 목적, 시스템 설명, 용어 정의, 참고 자료
- 2장 전체 설명: 시스템 관점, 사용자 특성, 제약조건, 가정 및 의존성
- 3장 기능 요구사항: FR-ID별 설명/선행조건/기본흐름/예외흐름/우선순위
- 4장 비기능 요구사항: NFR-ID별 성능/보안/가용성/확장성/유지보수성
- 5장 인터페이스: UI, 외부 시스템 연동, 데이터 인터페이스
- 6장 부록: 우선순위 요약, 미결 사항(TBD), 변경 이력

문서 생성 시 유의사항:
- **목차를 반드시 포함한다.** 문서 상단(메타 정보 바로 아래)에 마크다운 앵커 링크 기반의 목차를 생성한다. 템플릿의 목차 섹션을 참조하되, 실제 작성된 섹션에 맞게 조정한다. 목차가 없으면 문서가 길어졌을 때 탐색이 어려워진다.
- 인터뷰에서 나온 내용만 포함한다. 추측으로 요구사항을 추가하지 않는다.
- 인터뷰에서 명확하지 않았던 항목은 `[TBD]`로 표시하여 후속 논의가 필요함을 명시한다.
- 각 요구사항에 우선순위를 부여한다 (필수 / 권장 / 선택).

파일 저장:
- 파일명: `SRS_[SystemName]_YYYYMMDD.md` (시스템 이름은 영문으로 변환하여 인코딩 문제를 방지한다. 예: "온라인 도서관" → `SRS_OnlineLibrary_20260313.md`)
- 저장 위치: 현재 작업 디렉토리 (사용자가 별도 경로를 지정하면 해당 경로에 저장)

---

### 6단계: 리뷰 & 보완

생성된 문서의 핵심 통계를 요약하고 사용자에게 리뷰를 요청한다.

요약 항목:
- 기능 요구사항 N건 (필수 N / 권장 N / 선택 N)
- 비기능 요구사항 N건
- TBD 항목 N건 (후속 논의 필요)
- 인터페이스 정의 N건

사용자가 수정을 요청하면 해당 섹션만 업데이트하고 파일을 다시 저장한다. 전체 인터뷰를 반복할 필요는 없다.

## Examples

### 예시 1: 기본 사용

```
사용자: "우리 팀 프로젝트 SRS 좀 만들어줘. 온라인 도서관 시스템이야"
동작:
  1. 프로젝트 개요 인터뷰 (사용자, 목적, 범위)
  2. 기능 요구사항 인터뷰 (도서 검색, 대출/반납, 회원 관리 등)
  3. 비기능 요구사항 인터뷰 (성능, 보안)
  4. 인터페이스 인터뷰 (웹 UI, 외부 도서 API 연동)
  5. SRS_OnlineLibrary_20260312.md 파일 저장
  6. 요약 제시 및 리뷰
```

### 예시 2: 상세 설명을 이미 제공한 경우

```
사용자: "결제 시스템 요구사항 정리해줘. Spring Boot + PostgreSQL 쓸 거고,
        PG사 연동이 필요하고, 초당 100건 처리해야 해"
동작:
  1. 이미 답변된 내용(기술 스택, 외부 연동, 성능 목표) 확인
  2. 부족한 부분만 추가 질문 (사용자, 기능 상세, 보안 등)
  3. 나머지 단계 진행
```

### 예시 3: 간단한 프로젝트

```
사용자: "사이드 프로젝트 스펙 정리하고 싶어. 할 일 관리 앱이야"
동작:
  1. 간단한 프로젝트임을 감지 → 인터뷰를 간소화
  2. 핵심 기능과 기본 비기능 요구사항 중심으로 진행
  3. 인터페이스/외부 시스템 단계는 필요한 경우에만
```

## Troubleshooting

**사용자가 비기능 요구사항을 모르겠다고 할 때**
- 원인: 비기능 요구사항은 경험이 없으면 감이 안 오는 영역
- 해결: 일반적인 기본값을 제안하고 선택하게 한다. 예: "웹 서비스 기준으로 응답 시간 500ms, 가동률 99.5%, 동시 접속 100명 정도를 기본으로 잡을까요?"

**요구사항이 너무 많아 문서가 길어지는 경우**
- 원인: 대규모 시스템이거나 지나치게 상세한 수준
- 해결: 핵심 기능(MVP) 위주로 1차 문서를 작성하고, 나머지는 "향후 고려사항" 섹션으로 분리

**기존 기획 문서가 이미 있는 경우**
- 원인: 회의록, 기획서 등 기존 자료가 있는데 SRS 형식으로 변환이 필요
- 해결: 기존 문서 내용을 파악한 뒤, 부족한 부분만 추가 인터뷰로 보완하여 SRS를 생성
