# Parallax

코드베이스 내부의 사실 확인성 질문에 대해 **두 개의 독립적인 시각**(Claude / Codex CLI)으로 리서치하고, **제3의 격리된 채점자**(Explore 서브에이전트)가 라벨 익명화 상태로 채점하여 수렴하는 스킬. 시차(視差)로 깊이를 가늠하듯, 두 시각의 차이와 합의로 답의 신뢰도를 가늠한다.

## When to Use

다음 같은 요청에 반드시 사용한다:

- **명시적 cross-check 요청** — "교차 검증해줘", "두 번 확인해줘", "Claude랑 Codex 둘 다 봐줘"
- **인용 근거의 정확도가 중요할 때** — "이 동작의 정확한 근거 코드는?", "~ 처리는 정확히 어디에서?"
- **단일 LLM 답변에 확신이 부족할 때** — 같은 질문을 두 번째 LLM이 독립적으로 답하게 해 일치 여부를 본다
- **질문이 코드베이스 내부 사실 확인성일 때** — "~ 로직이 어떻게 구현되어 있어?", "~ 분기 조건이 정확히 뭐야?"

> **명시적 호출 경로**: auto-trigger가 발화하지 않을 때는 `/parallax <질문>` 슬래시 커맨드로 강제 호출한다. skill-creator eval에서 cross-check 의도 쿼리의 약 절반은 Claude가 자체 처리하는 쪽으로 기울어 auto-trigger가 누락되는 것이 확인됨 — 명시 호출 경로를 통해 누락을 우회한다.

## When NOT to Use

다음 경우는 다른 스킬이 더 적합하므로 이 스킬을 호출하지 않는다:

- **이미 수행한 작업의 2차 의견** → `/codex-review` 슬래시 커맨드 사용. parallax는 *리서치 질문*이 입력이고, codex-review는 *완료된 작업*이 입력이다.
- **코드베이스 전반의 구조·아키텍처 분석** → `code-analyzer` 사용. parallax는 좁고 구체적인 사실 확인성 질문 전용이다.
- **외부 라이브러리·프레임워크 사용법 / 일반론** → 이 스킬은 **외부 문서를 보지 않는다**. 코드베이스 내부에 답이 없는 질문은 거절하고 다른 도구를 안내한다.
- **단순 단일 파일 읽기** → `Read` 도구로 충분. cross-check 비용을 감수할 가치가 없다.
- **코드 수정·리팩토링·테스트 작성** → 각각 `refactor-advisor`, `junit-test-writer` 등을 사용. parallax는 분석·답변만 하고 파일을 수정하지 않는다.

## 핵심 원칙

1. **두 답변은 독립적으로 생성한다.** Codex에게 Claude의 답을 보여주지 않는다. 시각이 오염되면 cross-check의 의미가 사라진다.
2. **답변자와 채점자는 분리된다.** 메인 Claude는 답변만 하고, Step 5의 채점은 `Task` 툴로 호출하는 **Explore 서브에이전트**가 격리된 컨텍스트에서 수행한다. Self-grading bias를 구조적으로 차단한다.
3. **채점은 라벨 익명화 상태에서 진행한다.** Step 4.5에서 두 답변을 무작위로 "답변 A / 답변 B"로 매핑하고, 채점자는 어느 쪽이 Claude/Codex 답인지 모른 채 채점한다. 라벨 가리기를 의지가 아니라 메커니즘으로 강제한다.
4. **인용 정확성은 mechanical하게 검증한다.** Step 4에서 모든 인용을 정규식으로 파싱하고 `sed`로 실제 줄을 추출해 존재성을 자동 확인한다. LLM은 "줄 내용 ↔ 답변 주장의 연결성"만 판단한다.
5. **모든 주장은 코드 인용으로 뒷받침한다.** 양측 모두 `file_path:line_number` 형식의 인용을 강제한다. 인용 없는 주장은 "확인 불가"로 명시.
6. **양측 모두 red-team 강제.** Step 2.5(Claude)와 Step 3 프롬프트(Codex)에서 "본인 답이 틀릴 수 있는 시나리오 3개"를 강제 생성하여 confirmation bias를 줄인다.
7. **Codex/서브에이전트 호출 실패는 부드럽게 fallback한다.** 네트워크·인증·타임아웃 시 단계적 fallback과 함께 실패 사유를 리포트에 명시한다.
8. **이 스킬은 분석·답변만 한다.** 파일 수정·작성·실행 변경은 절대 하지 않는다.

## 워크플로우

```
질문 입력
    ↓
[Step 1] 질문 범위 확정 + 명확화 역질문(필요 시)
    ↓
[Step 2] Claude 리서치 (내부 도구로 독립 답변)
    ↓
[Step 2.5] Claude red-team (본인 답에 대한 강한 반박 시나리오 3개 → 한계·반증 보강)
    ↓
[Step 3] Codex 리서치 (CLI 호출 — 같은 질문 + red-team 강제)
    ↓
[Step 4] 비교·diff + 인용 자동 검증 (sed 추출)
    ↓
[Step 4.5] 라벨 익명화 (답변 A / 답변 B 무작위 매핑)
    ↓
[Step 5] 외부 채점 — Explore 서브에이전트가 4축 루브릭으로 익명 채점
    ↓
[Step 6] 라벨 복원 + 수렴 판정 (15% 임계값)
    ↓
[Step 7] 리포트 출력
```

## 상세 단계

### Step 1: 질문 범위 확정

사용자 질문을 파싱하여 다음 중 어느 분류인지 판단한다.

| 질문 유형 | 처리 |
|---|---|
| 코드베이스 내부 사실 확인성 (예: "주문 생성은 어디에서?", "할인 계산 분기 조건은?") | **진행** — Step 2로 |
| 외부 지식 (예: "Spring AOP는 어떻게 동작?", "JWT란?") | **거절** — "이 스킬은 코드베이스 내부만 본다. 외부 지식은 다른 도구로." |
| 코드 수정 요청 (예: "이거 리팩토링해줘") | **거절** — `refactor-advisor` 등 안내 |
| 이미 수행한 작업 리뷰 (예: "내가 한 거 봐줘") | **거절** — `/codex-review` 안내 |

**질문이 모호한 경우** — 단일 역질문으로 확정 (역질문 2회 연속 금지):

```
질문이 [구체화 필요 부분]을 특정하지 않습니다. 다음 중 어느 쪽을 의미하나요?

1. <구체화 옵션 1> — 예: "주문 생성 로직이 어디에서 시작하는지"
2. <구체화 옵션 2> — 예: "주문 생성 시 호출되는 모든 파일 목록"
3. <구체화 옵션 3> — 예: "주문 생성 중 트랜잭션 경계가 어디인지"
```

사용자가 답하지 않거나 여전히 모호하면 가장 합리적인 해석으로 진행하되, 리포트 상단에 "해석한 질문" 섹션으로 명시한다.

### Step 2: Claude 리서치 (내부 도구로 독립 답변)

자체 도구(Read, Grep, Glob)만 사용해 질문에 답한다. **이 단계에서는 Codex가 무엇을 답할지 추측하거나 의식하지 않는다** — 독립성이 중요.

산출물 형식 (Step 3과 동일하게 강제):

```markdown
### 답변
<핵심 답변 — 2~5문장>

### 근거 (코드 인용)
- `<file_path>:<line_number>` — <설명>
- `<file_path>:<line_number>` — <설명>
- ...

### 한계·반증
<반대 사례·예외·가정의 한계가 있으면 기록. Step 2.5에서 보강.>
```

**규칙**:
- 모든 주장은 인용 줄에 대응되어야 한다. 인용 없는 주장은 "확인 불가"로 명시.
- 인용한 라인은 실제로 Read로 확인한 라인이어야 한다. Grep 결과만 보고 추측 금지.
- 추측·일반론으로 답하지 않는다. 모르면 "코드베이스 내에서 확인되지 않음"이라고 명시.

### Step 2.5: Claude red-team

Step 2에서 작성한 본인의 답이 **틀릴 수 있는 가장 강한 시나리오 3개**를 명시적으로 생성한다. anchor 편향(본인 답을 만든 직후 검증 단계로 가는 흐름)을 깨기 위함이다.

각 시나리오는 다음 두 줄로 적는다:

```
시나리오 N:
  조건: <답이 깨지는 코드베이스 내 가정>
  검증: <어떤 파일·메서드를 Read하면 확인할 수 있는가>
```

**예시**:

```
시나리오 1:
  조건: 답이 OrderService 모듈만 본 결과인데, OrderFacade에서 별도 createOrder 경로가 있다면 결론이 달라짐
  검증: Grep "createOrder" 전체 → OrderFacade.java 추가 분기 확인

시나리오 2:
  조건: @Transactional이 클래스 레벨에도 부착되어 있다면 propagation이 다를 수 있음
  검증: OrderService.java:1~30 Read

시나리오 3:
  조건: AOP로 트랜잭션 경계가 가로채진다면 메서드 위치가 무관해짐
  검증: Grep "@Aspect" / proxy 설정 확인
```

생성한 시나리오 중 **검증 가능한 것은 즉시 검증**(Read·Grep)하고, 결과에 따라 Step 2의 답변을 갱신한다. 검증 후에도 살아남은 시나리오는 한계·반증 섹션에 합쳐 명시한다.

이 단계의 출력은 별도 파일이나 사용자 가시 텍스트로 내보내지 않고, Step 2 산출물의 "한계·반증" 섹션에 통합된다.

### Step 3: Codex 리서치 (CLI 호출)

`codex exec` CLI를 호출해 같은 질문에 대한 독립 답변을 받는다. **codex-review 슬래시 커맨드와 동일한 호출 패턴을 재사용**한다 (`.claude/commands/codex-review.md` 참조).

호출 직전에 사용자에게 "Codex 호출 중 — 30~60초 소요" 안내 1줄 출력.

**호출 예시**:

```bash
codex exec --sandbox read-only --skip-git-repo-check "$(cat <<'EOF'
You are conducting independent research in the current codebase. DO NOT modify any files. Use Read/Grep/Find to inspect actual code. Respond in Korean.

## 질문
<여기에 Step 1에서 확정된 질문>

## 요청
1. 코드베이스 내부 파일을 직접 읽고 답변. 추측·일반론 금지.
2. 모든 주장에 대해 `file_path:line_number` 형식의 인용을 명시.
3. 인용으로 뒷받침되지 않는 부분은 "코드베이스 내에서 확인되지 않음"이라고 명시.
4. **한계·반증 섹션에 본인 답이 틀릴 수 있는 시나리오를 반드시 3개 이상 포함**. 각 시나리오는 (조건, 검증 방법)을 1줄씩 적는다.
5. 1500자 이내. 다른 AI의 답변을 추측하거나 의식하지 말 것.

## 답변 형식 (반드시 이 형식 그대로)
### 답변
<핵심 답변 — 2~5문장>

### 근거 (코드 인용)
- file_path:line_number — 설명
- ...

### 한계·반증
시나리오 1: 조건 — 검증 방법
시나리오 2: 조건 — 검증 방법
시나리오 3: 조건 — 검증 방법
EOF
)"
```

**호출 시 주의**:
- 질문 본문이 길거나 특수문자가 많으면 heredoc 안에 그대로 박지 말고 `/tmp/parallax-codex-$$.txt`에 쓰고 `codex exec - < /tmp/parallax-codex-$$.txt` 형태로 stdin 주입한다.
- `--sandbox read-only`로 codex가 파일을 수정하지 못하게 강제한다.
- `--skip-git-repo-check`로 git 상태 무관하게 실행.

**호출 실패 시 fallback**:
- 네트워크/인증/timeout 등으로 codex가 응답하지 않으면 에러 원문을 캡처하고, **Step 4 이후를 건너뛰고** Claude 단독 답변(Step 2 + 2.5 결과) + 실패 사유를 리포트로 출력한다.
- 사용자에게 "Codex 없이 Claude 단독 답변만 출력했습니다. 재시도할까요?"를 묻는다.

### Step 4: 비교·diff + 인용 자동 검증

#### 4-A. diff 작성

Step 2(+2.5)와 Step 3의 답변을 다음 4가지 차원에서 비교한다:

1. **답변의 핵심 일치도** — 두 답이 같은 결론을 말하는가
2. **인용 출처 비교** — 양측이 동일한 파일·라인을 인용했는가, 다르게 인용했는가
3. **반증·한계의 차이** — 어느 쪽이 반증을 더 짚었는가, red-team 시나리오는 무엇이 다른가

#### 4-B. 인용 자동 검증

양측 답변의 모든 `file_path:line_number` 인용을 정규식(`[\w./-]+\.\w+:\d+(-\d+)?`)으로 파싱한다. 각 인용에 대해 Bash로 실제 줄을 추출:

```bash
# 단일 라인
sed -n 'Np' "$file"
# 라인 범위 M-N
sed -n 'M,Np' "$file"
# 파일 부재 시
[ -f "$file" ] || echo "FILE_NOT_FOUND"
```

추출 결과를 다음 형태로 정리:

```markdown
**인용 자동 검증 결과**

| 인용 | 출처(라벨링 전) | 추출 줄 (앞 80자) | 상태 |
|---|---|---|---|
| `OrderService.java:45` | A | `public OrderResult createOrder(...)` | ✅ 존재 |
| `MemberService.java:88` | B | `notifySignup(member)` | ⚠️ 답변의 "할인 분기" 주장과 비연결 |
| `Foo.java:999` | A | (FILE_NOT_FOUND or 라인 없음) | ❌ 비존재 |
```

**상태 분류**:
- ✅ 존재 — 라인이 존재하고 답변 주장과 명확히 연결됨
- ⚠️ 약한 연결 또는 비연결 — 라인은 존재하나 주장과 의미적으로 어긋남
- ❌ 비존재 — 파일 없음 또는 라인 번호가 파일 길이를 초과

**연결성 판정**은 LLM이 한다 (자동 추출은 존재성·정확성까지). 메인 Claude가 1차 판정하되, Step 5 채점자가 의심스러운 항목을 재검증한다.

#### 4-C. 비교 표 출력

```markdown
**합의점**
- 두 답변이 동일하게 주장한 내용 + 양측 공통 인용

**차이점**
- <항목>: Claude는 X, Codex는 Y. 인용 차이: ...
- <항목>: 한쪽만 언급함

**Red-team 시나리오 비교**
- Claude 시나리오: ...
- Codex 시나리오: ...
- 겹치는 시나리오 / 한쪽만 짚은 시나리오
```

### Step 4.5: 라벨 익명화

Step 5의 외부 채점자가 어느 쪽이 Claude/Codex 답인지 모르도록, Step 2(+2.5)와 Step 3의 답변을 무작위로 "답변 A / 답변 B"로 매핑한다.

**셔플 방법**:

```bash
# 50/50 무작위 결정
if [ $((RANDOM % 2)) -eq 0 ]; then echo "A=Claude,B=Codex"; else echo "A=Codex,B=Claude"; fi
```

**규칙**:
- 셔플 결과(매핑)는 메인 컨텍스트에서만 기억한다. Step 5 입력 텍스트(서브에이전트 프롬프트)에는 "Claude" / "Codex"라는 단어가 일절 등장하지 않아야 한다.
- Step 4의 인용 자동 검증 결과 표도 라벨을 "A/B"로 치환한 버전을 채점자에게 전달한다.
- 매핑은 Step 6에서 점수를 받은 직후 복원한다.

**누설 방지 체크리스트**:
- 답변 본문 안에 "Codex의 답변" 같은 문구가 자기언급 형태로 있으면 "답변 A/B"로 치환.
- 인용 자동 검증 표의 출처 컬럼도 라벨로 치환.
- 채점자에게 보내는 메타 정보(코드베이스 경로, 질문)에 모델명을 포함하지 않는다.

### Step 5: 외부 채점 (Explore 서브에이전트)

채점은 메인 Claude가 직접 수행하지 않는다. 대신 `Task` 툴로 **Explore 서브에이전트**를 호출하여 격리된 컨텍스트에서 채점한다. 메인 컨텍스트의 답변 작성 흐름과 분리되므로 self-grading bias가 구조적으로 제거된다.

**호출**:

```
Task / Agent 툴 사용:
  description: "Parallax 채점"
  subagent_type: "Explore"
  prompt: <아래 프롬프트>
```

**서브에이전트 프롬프트**:

```
당신은 cross-check 리서치의 채점자입니다. 두 답변을 4축 루브릭으로 독립 채점하세요. 어느 답변이 어떤 모델의 산출물인지는 알려지지 않습니다 — 라벨은 "답변 A"와 "답변 B"입니다. 답이 어느 모델인지 추측하거나 언급하지 마세요.

## 질문
<Step 1에서 확정된 질문>

## 답변 A
<라벨 익명화된 본문 — Step 2 또는 Step 3 결과>

## 답변 B
<라벨 익명화된 본문 — Step 2 또는 Step 3 결과>

## Step 4의 인용 자동 검증 결과 (라벨 익명화됨)
<Step 4-B 표를 그대로 복사>

## 채점 지침

1. `skills/parallax/references/rubric.md`를 Read하여 4축 정의와 밴드 기준을 확인하세요.
2. 각 답변에 대해 4축(출처 신뢰도 / 인용 정확성 / 논리 일관성 / 반증 고려) × 0~10점 채점.
3. **인용 정확성은 위 자동 검증 결과를 사용하여 mechanical하게 산출**:
   - 통과(✅) 비율 = 통과 건수 / 전체 인용 건수
   - 점수 = round(통과 비율 × 10)
   - 단, 핵심 인용(답변의 결론을 직접 뒷받침하는 인용) 1건이 ❌이면 통과 비율과 무관하게 최대 4점.
4. 의심스러운 인용이 있으면 직접 Read로 추가 검증.
5. 답변 텍스트만 보고 채점하세요. 어떤 모델의 답인지 추측하지 마세요.

## 출력 형식 (반드시 이 형식 그대로)

| 축 | 답변 A | 답변 B |
|---|---|---|
| 출처 신뢰도 | <0~10> | <0~10> |
| 인용 정확성 | <0~10> | <0~10> |
| 논리 일관성 | <0~10> | <0~10> |
| 반증 고려 | <0~10> | <0~10> |
| **합계** | **<합계>/40** | **<합계>/40** |

각 점수 옆에 1줄 사유 (rubric.md의 밴드 기준 인용).

**명백한 결함** (해당 없으면 "없음"):
- 답변 A: <인용 정확성 핵심 1건 통째로 틀림 등이 있으면 명시>
- 답변 B: <동일>
```

**호출 실패 시 fallback**:
- 서브에이전트가 응답하지 않거나 형식이 깨지면 메인 Claude가 직접 채점하되, 리포트 상단에 "외부 채점자 호출 실패 — 자체 채점 (self-grading bias 가능성)" 경고를 명시한다.
- 자체 채점 시에도 라벨 익명화는 유지한다 (Step 4.5 매핑 그대로).

### Step 6: 라벨 복원 + 수렴 판정 (15% 임계값)

Step 5에서 받은 답변 A/B 점수를 Step 4.5의 셔플 매핑으로 Claude/Codex 점수로 복원한다.

만점 40점 기준 **점수 차 6점(15%)** 을 임계값으로 사용한다.

| 점수 차 | 판정 |
|---|---|
| ≥ 6점 | **수렴** (`converged`) — 더 높은 점수의 답을 채택. 낮은 점수의 답은 차이 사유와 함께 부록으로 보존. |
| < 6점 | **양측 병기** (`split`) — 단일 결론을 내리지 않고 양측 답변을 모두 제시. 사용자에게 최종 판단을 맡김. |

**수렴 강등 규칙**: 더 높은 점수의 답에 명백한 결함(채점자가 명시한 "명백한 결함" 항목)이 있으면 사유와 함께 양측 병기로 강등한다. 점수는 신호일 뿐, 마지막 검증은 사람·다음 LLM의 몫.

### Step 7: 리포트 출력

산출물은 다음 5섹션을 **이 순서 그대로** 포함한다. 완전한 예시는 `references/report-template.md`에 있지만, 아래 인라인 명세가 우선한다.

**리포트 상단 — YAML frontmatter**

```yaml
---
question: <Step 1에서 확정된 질문>
asked_at: YYYY-MM-DD
scope: <working directory 경로>
verdict: converged | split
score_gap: <Claude 합계 - Codex 합계의 절댓값>
judge: explore_subagent | self    # 외부 채점 성공 여부
anonymized: true | false          # 라벨 익명화 적용 여부
---
```

**섹션 1: 질문**
- 사용자 원문 + (해석한 경우) 해석된 질문 한 줄

**섹션 2: 양측 답변 요약**
- ### Claude의 답변 — Step 2(+2.5) 산출물
- ### Codex의 답변 — Step 3 산출물

**섹션 3: 비교**
- Step 4의 합의점 / 차이점 / 인용 자동 검증 결과 / red-team 시나리오 비교

**섹션 4: 채점표**
- Step 5의 4축 × 양측 표 (라벨 복원 후)
- 각 점수 옆에 1줄 사유 (rubric.md 밴드 기준)
- 채점자(`explore_subagent` / `self`) 표기

**섹션 5: 결론**
- `verdict: converged`이면: 채택된 답 + 채택 사유 + 폐기된 답의 차이 부록
- `verdict: split`이면: 양측 답을 모두 제시 + "점수 차가 작아 단일 결론을 내리지 않음. 사용자가 최종 판단" 안내

**출력 방식**: 기본은 터미널 직접 출력. 사용자가 파일 저장을 요청하면 `parallax_<질문요약>_YYYYMMDD.md` 형식으로 저장. 동일 파일 존재 시 (1) 덮어쓰기 (2) `_v2` 추가 (3) 취소 중 선택 요청.

## 컨벤션 요약

| 항목 | 규칙 |
|------|------|
| 리서치 범위 | 현재 working directory **내부만**. 외부 문서·웹 검색 금지. |
| 인용 형식 | `file_path:line_number` 강제. 인용 없는 주장은 "확인 불가" 명시. |
| 독립성 | Step 2(+2.5)와 Step 3은 서로의 답을 보지 않는다. |
| Red-team 강제 | 양측 모두 한계·반증 섹션에 시나리오 3개 이상 (조건/검증 방법 1줄씩). |
| 인용 검증 | Step 4-B에서 `sed`로 자동 추출 → 존재성·정확성은 mechanical, 연결성은 LLM 판단. |
| 라벨 익명화 | Step 4.5에서 답변을 "A/B"로 무작위 매핑, Step 5 채점 종료 후 Step 6에서 복원. |
| 채점자 | `Task` 툴로 호출하는 **Explore 서브에이전트**(격리된 컨텍스트). 호출 실패 시 자체 채점 + 경고. |
| 채점 만점 | 4축 × 10점 = 40점 |
| 수렴 임계값 | 점수 차 < 6점(15%) → 양측 병기 |
| Codex CLI | `codex exec --sandbox read-only --skip-git-repo-check` (codex-review 패턴 재사용) |
| 실패 fallback | Codex 실패 → Claude 단독 / 서브에이전트 실패 → 메인 자체 채점 + 경고 |
| 사이드이펙트 | 파일 작성·수정·실행 변경 금지. 분석·답변만. |

상세 채점 기준은 `references/rubric.md`, 출력 포맷 전체 예시는 `references/report-template.md` 참조.

## Troubleshooting

**codex CLI가 설치되지 않은 경우**
- 증상: `codex: command not found`
- 해결: 사용자에게 codex 설치 안내. Claude 단독 답변(Step 2 + 2.5) + "codex 미설치로 cross-check 미수행"으로 fallback.

**codex 호출이 타임아웃되는 경우**
- 원인: 큰 코드베이스에서 codex가 Read/Grep을 많이 수행
- 해결: 60초 timeout으로 끊고 Claude 단독 fallback. 사용자에게 재호출 여부 질문.

**Explore 서브에이전트 호출이 실패하는 경우**
- 원인: Task 툴이 차단되었거나 서브에이전트가 형식이 깨진 출력을 반환
- 해결: 메인 Claude가 자체 채점으로 fallback. 리포트 frontmatter에 `judge: self`, 상단에 self-grading bias 경고. 라벨 익명화 매핑은 유지하지만 본인이 매핑을 알고 있으므로 leakage 가능성을 사용자에게 고지.

**인용 자동 검증에서 파일 부재 또는 라인 초과**
- 원인: LLM이 환각 인용을 만들었거나 코드가 변경됨
- 해결: ❌로 표시하고 채점자에게 그대로 전달. 채점자가 mechanical 산출 시 자동 감점.

**codex가 한국어 미준수 또는 red-team 시나리오 누락**
- 원인: 프롬프트의 지시 무시
- 해결: 출력을 그대로 두되 리포트의 Codex 섹션 상단에 "지시 미준수 — 원문 그대로 표시"를 명시. 누락된 항목은 한계·반증 채점 시 자동 감점으로 반영.

**Step 5 채점 결과의 라벨 누설**
- 원인: 채점자가 답변 본문에서 모델명을 추측해 언급
- 해결: 출력에서 모델명 추측 발언이 발견되면 채점 결과는 사용하되 리포트에 "라벨 누설 가능성 감지" 경고 추가. Step 4.5 누설 방지 체크리스트를 다시 확인.
