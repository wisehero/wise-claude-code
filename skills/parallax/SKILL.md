# Parallax

코드베이스 내부의 사실 확인성 질문에 대해 **두 개의 독립적인 시각**(Claude / Codex CLI)으로 리서치하고, 근거의 질을 채점하여 수렴하는 스킬. 시차(視差)로 깊이를 가늠하듯, 두 시각의 차이와 합의로 답의 신뢰도를 가늠한다.

## When to Use

다음 같은 요청에 반드시 사용한다:

- **명시적 cross-check 요청** — "교차 검증해줘", "두 번 확인해줘", "Claude랑 Codex 둘 다 봐줘"
- **인용 근거의 정확도가 중요할 때** — "이 동작의 정확한 근거 코드는?", "~ 처리는 정확히 어디에서?"
- **단일 LLM 답변에 확신이 부족할 때** — 같은 질문을 두 번째 LLM이 독립적으로 답하게 해 일치 여부를 본다
- **질문이 코드베이스 내부 사실 확인성일 때** — "~ 로직이 어떻게 구현되어 있어?", "~ 분기 조건이 정확히 뭐야?"

> **명시적 호출 경로**: auto-trigger가 발화하지 않을 때는 `/parallax <질문>` 슬래시 커맨드로 강제 호출한다. skill-creator eval에서 cross-check 의도 쿼리의 약 절반은 Claude가 자체 처리하는 쪽으로 기울어 auto-trigger가 누락되는 것이 확인됨 — 명시 호출 경로를 통해 누락을 우회한다.

## When NOT to Use

다음 경우는 다른 스킬이 더 적합하므로 이 스킬을 호출하지 않는다:

- **이미 수행한 작업의 2차 의견** → `/codex-review` 슬래시 커맨드 사용. parallax는 *리서치 질문*이 입력이고, codex-review는 *완료된 작업*이 입력이다.
- **코드베이스 전반의 구조·아키텍처 분석** → `code-analyzer` 사용. parallax는 좁고 구체적인 사실 확인성 질문 전용이다.
- **외부 라이브러리·프레임워크 사용법 / 일반론** → 이 스킬은 **외부 문서를 보지 않는다**. 코드베이스 내부에 답이 없는 질문은 거절하고 다른 도구를 안내한다.
- **단순 단일 파일 읽기** → `Read` 도구로 충분. cross-check 비용을 감수할 가치가 없다.
- **코드 수정·리팩토링·테스트 작성** → 각각 `refactor-advisor`, `junit-test-writer` 등을 사용. parallax는 분석·답변만 하고 파일을 수정하지 않는다.

## 핵심 원칙

1. **두 답변은 독립적으로 생성한다.** Codex에게 Claude의 답을 보여주지 않는다. 시각이 오염되면 cross-check의 의미가 사라진다.
2. **모든 주장은 코드 인용으로 뒷받침한다.** 양측 모두 `file_path:line_number` 형식의 인용을 강제한다. 인용 없는 주장은 "확인 불가"로 명시.
3. **Codex 호출 실패는 부드럽게 fallback한다.** 네트워크·인증·타임아웃 시 Claude 단독 답변 + 실패 사유를 안내한다.
4. **이 스킬은 분석·답변만 한다.** 파일 수정·작성·실행 변경은 절대 하지 않는다. 답변에 따른 후속 작업은 다른 스킬·커맨드로 위임.

## 워크플로우

```
질문 입력
    ↓
[Step 1] 질문 범위 확정 + 명확화 역질문(필요 시)
    ↓
[Step 2] Claude 리서치 (내부 도구로 독립 답변)
    ↓
[Step 3] Codex 리서치 (CLI 호출, 같은 질문)
    ↓
[Step 4] 비교·diff 작성
    ↓
[Step 5] 4축 루브릭 채점
    ↓
[Step 6] 수렴 판정 (15% 임계값)
    ↓
[Step 7] 리포트 출력
```

## 상세 단계

### Step 1: 질문 범위 확정

사용자 질문을 파싱하여 다음 중 어느 분류인지 판단한다.

| 질문 유형 | 처리 |
|---|---|
| 코드베이스 내부 사실 확인성 (예: "주문 생성은 어디에서?", "할인 계산 분기 조건은?") | **진행** — Step 2로 |
| 외부 지식 (예: "Spring AOP는 어떻게 동작?", "JWT란?") | **거절** — "이 스킬은 코드베이스 내부만 본다. 외부 지식은 다른 도구로." |
| 코드 수정 요청 (예: "이거 리팩토링해줘") | **거절** — `refactor-advisor` 등 안내 |
| 이미 수행한 작업 리뷰 (예: "내가 한 거 봐줘") | **거절** — `/codex-review` 안내 |

**질문이 모호한 경우** — 단일 역질문으로 확정 (역질문 2회 연속 금지):

```
질문이 [구체화 필요 부분]을 특정하지 않습니다. 다음 중 어느 쪽을 의미하나요?

1. <구체화 옵션 1> — 예: "주문 생성 로직이 어디에서 시작하는지"
2. <구체화 옵션 2> — 예: "주문 생성 시 호출되는 모든 파일 목록"
3. <구체화 옵션 3> — 예: "주문 생성 중 트랜잭션 경계가 어디인지"
```

사용자가 답하지 않거나 여전히 모호하면 가장 합리적인 해석으로 진행하되, 리포트 상단에 "해석한 질문" 섹션으로 명시한다.

### Step 2: Claude 리서치 (내부 도구로 독립 답변)

자체 도구(Read, Grep, Glob)만 사용해 질문에 답한다. **이 단계에서는 Codex가 무엇을 답할지 추측하거나 의식하지 않는다** — 독립성이 중요.

산출물 형식 (Step 3과 동일하게 강제):

```markdown
### 답변
<핵심 답변 — 2~5문장>

### 근거 (코드 인용)
- `<file_path>:<line_number>` — <설명>
- `<file_path>:<line_number>` — <설명>
- ...

### 한계·반증
<반대 사례·예외·가정의 한계가 있으면 기록. 없으면 "특이사항 없음">
```

**규칙**:
- 모든 주장은 인용 줄에 대응되어야 한다. 인용 없는 주장은 "확인 불가"로 명시.
- 인용한 라인은 실제로 Read로 확인한 라인이어야 한다. Grep 결과만 보고 추측 금지.
- 추측·일반론으로 답하지 않는다. 모르면 "코드베이스 내에서 확인되지 않음"이라고 명시.

### Step 3: Codex 리서치 (CLI 호출)

`codex exec` CLI를 호출해 같은 질문에 대한 독립 답변을 받는다. **codex-review 슬래시 커맨드와 동일한 호출 패턴을 재사용**한다 (`.claude/commands/codex-review.md` 참조).

**호출 예시**:

```bash
codex exec --sandbox read-only --skip-git-repo-check "$(cat <<'EOF'
You are conducting independent research in the current codebase. DO NOT modify any files. Use Read/Grep/Find to inspect actual code. Respond in Korean.

## 질문
<여기에 Step 1에서 확정된 질문>

## 요청
1. 코드베이스 내부 파일을 직접 읽고 답변. 추측·일반론 금지.
2. 모든 주장에 대해 `file_path:line_number` 형식의 인용을 명시.
3. 인용으로 뒷받침되지 않는 부분은 "코드베이스 내에서 확인되지 않음"이라고 명시.
4. 반대 사례·예외·가정의 한계가 있으면 별도 섹션으로 명시.
5. 1500자 이내. 다른 AI의 답변을 추측하거나 의식하지 말 것.

## 답변 형식 (반드시 이 형식 그대로)
### 답변
<핵심 답변 — 2~5문장>

### 근거 (코드 인용)
- file_path:line_number — 설명
- ...

### 한계·반증
<있으면 기록, 없으면 "특이사항 없음">
EOF
)"
```

**호출 시 주의**:
- 질문 본문이 길거나 특수문자가 많으면 heredoc 안에 그대로 박지 말고 `/tmp/parallax-codex-$$.txt`에 쓰고 `codex exec - < /tmp/parallax-codex-$$.txt` 형태로 stdin 주입한다.
- `--sandbox read-only`로 codex가 파일을 수정하지 못하게 강제한다 (프롬프트의 "DO NOT modify"와 이중 안전장치).
- `--skip-git-repo-check`로 git 상태 무관하게 실행.
- timeout이 길어질 수 있으므로 (실제 Read·Grep을 수행하므로 30~60초 소요 가능) 호출 직전에 사용자에게 "Codex 호출 중 — 30~60초 소요" 안내 1줄 출력.

**호출 실패 시 fallback** (이 부분은 Troubleshooting 절도 본다):
- 네트워크/인증/timeout 등으로 codex가 응답하지 않으면 에러 원문을 캡처하고, **Step 4 이후를 건너뛰고** Claude 단독 답변 + 실패 사유를 리포트로 출력한다.
- 사용자에게 "Codex 없이 Claude 단독 답변만 출력했습니다. 재시도할까요?"를 묻는다.

### Step 4: 비교·diff 작성

Step 2와 Step 3의 답변을 다음 4가지 차원에서 비교한다:

1. **답변의 핵심 일치도** — 두 답이 같은 결론을 말하는가
2. **인용 출처 비교** — 양측이 동일한 파일·라인을 인용했는가, 다르게 인용했는가
3. **인용 정확성 검증** — 각 답변이 인용한 라인을 **반드시 Read로 직접 확인**한다. 인용된 줄이 실제로 답변을 뒷받침하는지 검증.
4. **반증·한계의 차이** — 어느 쪽이 반증을 더 짚었는가

비교 결과를 다음 형식으로 정리:

```markdown
**합의점**
- 두 답변이 동일하게 주장한 내용 + 양측 공통 인용

**차이점**
- <항목>: Claude는 X, Codex는 Y. 인용 차이: ...
- <항목>: 한쪽만 언급함

**인용 정확성 검증**
- Claude의 인용 N개 중 M개가 실제 코드와 일치 (불일치: ...)
- Codex의 인용 N개 중 M개가 실제 코드와 일치 (불일치: ...)
```

### Step 5: 4축 루브릭 채점

각 답변을 4개 축으로 채점한다 (각 축 0~10점, 만점 40점). **상세 채점 기준은 `references/rubric.md`를 반드시 본다** — 각 축의 밴드별 정의와 검증 방법이 있다.

**4축 요약** (상세는 rubric.md 참조):

| 축 | 핵심 기준 |
|---|---|
| **출처 신뢰도** (Source Reliability) | 답변이 실제 코드 인용에 기반하는가, 추측·일반론으로 빠지지 않는가 |
| **인용 정확성** (Citation Accuracy) | 인용한 file_path:line_number가 실제 존재하고 답변을 뒷받침하는가 (Step 4의 검증 결과 반영) |
| **논리 일관성** (Logical Consistency) | 답변 내부에서 모순이 없는가, 인용과 결론이 정합하는가 |
| **반증 고려** (Counterevidence Consideration) | 반대 사례·예외·가정의 한계를 짚었는가, 단순 confirmation bias로 빠지지 않았는가 |

**채점은 양측 모두에 대해 수행한다.** 결과는 다음 형식의 표로 정리:

```markdown
| 축 | Claude | Codex |
|---|---|---|
| 출처 신뢰도 | 8 | 6 |
| 인용 정확성 | 9 | 7 |
| 논리 일관성 | 8 | 8 |
| 반증 고려 | 5 | 7 |
| **합계** | **30/40** | **28/40** |
```

각 점수는 rubric.md의 밴드 기준을 기록한다 (예: "출처 신뢰도 8 — 모든 주장에 인용이 있고 1건만 약한 인용").

### Step 6: 수렴 판정 (15% 임계값)

만점 40점 기준 **점수 차 6점(15%)** 을 임계값으로 사용한다.

| 점수 차 | 판정 |
|---|---|
| ≥ 6점 | **수렴** — 더 높은 점수의 답을 채택. 낮은 점수의 답은 차이 사유와 함께 부록으로 보존. |
| < 6점 | **양측 병기** — 단일 결론을 내리지 않고 양측 답변을 모두 제시. 사용자에게 최종 판단을 맡김. |

**수렴이라도 무조건 채택은 아니다**: 더 높은 점수의 답에 명백한 결함(예: 인용 정확성 1건이 통째로 틀림)이 있으면 사유와 함께 양측 병기로 강등한다. 점수는 신호일 뿐, 마지막 검증은 사람·다음 LLM의 몫.

### Step 7: 리포트 출력

산출물은 다음 5섹션을 **이 순서 그대로** 포함한다. 완전한 예시는 `references/report-template.md`에 있지만, 아래 인라인 명세가 우선한다.

**리포트 상단 — YAML frontmatter**

```yaml
---
question: <Step 1에서 확정된 질문>
asked_at: YYYY-MM-DD
scope: <working directory 경로>
verdict: converged | split   # converged = 수렴, split = 양측 병기
score_gap: <Claude 합계 - Codex 합계의 절댓값>
---
```

**섹션 1: 질문**
- 사용자 원문 + (해석한 경우) 해석된 질문 한 줄

**섹션 2: 양측 답변 요약**
- ### Claude의 답변 — Step 2 산출물
- ### Codex의 답변 — Step 3 산출물

**섹션 3: 비교**
- Step 4의 합의점 / 차이점 / 인용 정확성 검증 결과

**섹션 4: 채점표**
- Step 5의 4축 × 양측 표
- 각 점수 옆에 1줄 사유

**섹션 5: 결론**
- `verdict: converged`이면: 채택된 답 + 채택 사유 + 폐기된 답의 차이 부록
- `verdict: split`이면: 양측 답을 모두 제시 + "점수 차가 작아 단일 결론을 내리지 않음. 사용자가 최종 판단" 안내

**출력 방식**: 기본은 터미널 직접 출력. 사용자가 파일 저장을 요청하면 `parallax_<질문요약>_YYYYMMDD.md` 형식으로 저장. 파일 충돌 방지는 code-analyzer와 동일한 패턴 — 동일 파일 존재 시 (1) 덮어쓰기 (2) `_v2` 추가 (3) 취소 중 선택 요청.

## 컨벤션 요약

| 항목 | 규칙 |
|------|------|
| 리서치 범위 | 현재 working directory **내부만**. 외부 문서·웹 검색 금지. |
| 인용 형식 | `file_path:line_number` 강제. 인용 없는 주장은 "확인 불가" 명시. |
| 독립성 | Step 2와 Step 3은 서로의 답을 보지 않는다. |
| 채점 만점 | 4축 × 10점 = 40점 |
| 수렴 임계값 | 점수 차 < 6점(15%) → 양측 병기 |
| Codex CLI | `codex exec --sandbox read-only --skip-git-repo-check` (codex-review 패턴 재사용) |
| 실패 fallback | Codex 호출 실패 시 Claude 단독 답변 + 실패 사유 명시 |
| 사이드이펙트 | 파일 작성·수정·실행 변경 금지. 분석·답변만. |

상세 채점 기준은 `references/rubric.md`, 출력 포맷 전체 예시는 `references/report-template.md` 참조.

## Examples

### 예시 1: 명시적 cross-check 요청

```
사용자: "주문 생성 시 트랜잭션 경계가 어디인지 Claude랑 Codex 둘 다 봐줘"

동작:
  Step 1: 질문이 코드베이스 내부 사실 확인성 — 진행
  Step 2: Claude — Grep "@Transactional", OrderService 관련 파일 Read
          → "OrderService.createOrder()의 @Transactional이 경계. 인용: OrderService.java:45 등"
  Step 3: Codex CLI 호출 (30~60초)
          → Codex 답변 수신
  Step 4: diff 작성 — 합의: 메서드 위치 동일. 차이: Codex가 propagation REQUIRED를 추가 언급
  Step 5: 4축 채점 — Claude 32/40, Codex 35/40
  Step 6: 점수 차 3점 < 6점 → 양측 병기 (split)
  Step 7: 리포트 출력 (양측 답 + 비교 + 채점표 + "사용자 최종 판단" 안내)
```

### 예시 2: 인용 정확성이 결정적인 질문

```
사용자: "할인율 10%가 적용되는 조건이 정확히 뭐야? 두 번 확인해줘"

동작:
  Step 1: 사실 확인성 — 진행
  Step 2: Claude — DiscountService 분석 → "회원 등급 GOLD 이상 + 주문 금액 50000 이상.
          인용: DiscountPolicy.java:23, DiscountPolicy.java:31"
  Step 3: Codex — "회원 등급 GOLD 이상 + 첫 주문". 인용: DiscountPolicy.java:23, MemberService.java:88"
  Step 4: 인용 정확성 검증 — 두 답변이 인용한 줄을 직접 Read로 확인
          → Codex의 MemberService.java:88은 실제로는 가입 알림 로직. 인용 부정확.
  Step 5: 채점 — Claude 인용 정확성 9, Codex 인용 정확성 4 → 합계 Claude 33, Codex 22
  Step 6: 점수 차 11점 ≥ 6점 → 수렴 (converged), Claude 답 채택
  Step 7: 리포트 — Claude 답 채택 + Codex의 인용 부정확성을 부록에 기록
```

### 예시 3: 외부 지식 질문 (거절 경로)

```
사용자: "@Transactional의 propagation 옵션들 비교해줘"

동작:
  Step 1: 외부 지식 질문 (Spring 프레임워크 일반) — 거절
  응답:  "이 스킬은 코드베이스 내부 사실 확인성 질문 전용입니다.
         외부 라이브러리·프레임워크 일반론은 다른 도구를 사용하세요.
         만약 이 코드베이스에서 어떤 propagation을 쓰는지 궁금하시면
         '이 코드베이스에서 사용된 @Transactional propagation들을 찾아줘'로 다시 요청해주세요."
```

### 예시 4: Codex 호출 실패 fallback

```
사용자: "결제 실패 시 재시도 로직 어디 있는지 두 번 확인"

동작:
  Step 1: 진행
  Step 2: Claude 답변 작성 완료
  Step 3: codex exec 호출 → 60초 후 timeout
  Step 3 fallback: Codex 답변 미수신, Step 4~6 건너뜀
  Step 7: Claude 단독 답변 + "Codex 호출 실패 (timeout 60s) — cross-check 미수행" 명시
         사용자에게 "재시도할까요? (Codex 재호출 / Claude 단독으로 종료)" 질문
```

### 예시 5: 모호한 질문 (단일 역질문)

```
사용자: "주문 처리 어떻게 돼?"

동작:
  Step 1: 질문이 모호 — "주문 처리"의 범위가 불명
  단일 역질문:
    "다음 중 어느 쪽을 의미하나요?
     1. 주문 생성 로직 (어디서 시작해서 어디까지 가는지)
     2. 주문 상태 전이 (PENDING → CONFIRMED 같은 흐름)
     3. 주문 실패·취소 시 처리"
  사용자가 답하면 Step 2~7 진행. 답하지 않으면 가장 합리적 해석으로 진행 + 리포트 상단에 "해석한 질문" 명시.
```

## Troubleshooting

**codex CLI가 설치되지 않은 경우**
- 증상: `codex: command not found`
- 해결: 사용자에게 codex 설치 안내. 그 사이 Claude 단독 답변 + "codex 미설치로 cross-check 미수행"으로 fallback.

**codex 호출이 타임아웃되는 경우**
- 원인: 큰 코드베이스에서 codex가 Read/Grep을 많이 수행
- 해결: 60초 timeout으로 끊고 Claude 단독 fallback. 사용자에게 재호출 여부 질문.

**codex가 파일 수정을 시도하는 경우**
- 원인: 프롬프트의 "DO NOT modify" 무시
- 해결: `--sandbox read-only`가 1차 방어선. 만약 그래도 수정이 발생하면 즉시 변경사항 무시하고 의견 텍스트만 추출. 사용자에게 codex 출력의 어느 부분이 수정 시도였는지 알린다.

**양측 답변이 모두 부실한 경우 (각각 합계 < 20/40)**
- 원인: 질문이 코드베이스 내부에서 답할 수 없는 종류 (외부 지식, 미구현 기능 등)
- 해결: 양측 모두 인용으로 뒷받침되지 않는다는 사실을 리포트에 명시하고, "이 질문은 코드베이스만으로 답할 수 없습니다. 다른 도구를 권장합니다"로 안내. 점수 비교는 의미 없으므로 verdict는 `split`로 처리.

**Codex의 답변이 한국어가 아닌 경우**
- 원인: 프롬프트의 언어 지시 무시
- 해결: 출력을 그대로 두되 리포트의 Codex 섹션 상단에 "Codex가 한국어 지시를 따르지 않음 — 원문 그대로 표시"를 명시. 번역하지 않는다 (번역 시 인용 정확성 검증이 어려워짐).

**인용 정확성 검증 중 Read해야 할 파일이 너무 많은 경우**
- 원인: 양측이 인용한 파일이 합쳐서 20개 이상
- 해결: 핵심 인용(답변의 결론을 직접 뒷받침하는 인용)만 우선 검증하고, 보조 인용은 검증 표본을 50%로 줄인다. 검증 범위를 리포트에 명시.

**point-in-time 코드 변경**
- 원인: Step 2와 Step 3 사이에 코드가 변경됨 (사용자가 다른 터미널에서 편집 등)
- 해결: 인용 정확성 검증 시점의 파일 mtime을 기록하고, Step 2/3 답변 시점과 다르면 리포트 상단에 "리서치 중 코드 변경 감지" 경고를 추가. 결과는 그대로 출력.
