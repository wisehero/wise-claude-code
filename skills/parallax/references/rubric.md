# Parallax 채점 루브릭

각 답변(Claude / Codex)을 4개 축에 대해 0~10점으로 채점한다. 만점 40점.

> **사용 시점**: SKILL.md의 Step 5에서 이 문서를 본다. 채점은 Step 4의 인용 정확성 검증 결과를 반영해야 하므로, Step 4를 마친 뒤에 채점한다.

> **채점 원칙**: 점수는 신호일 뿐 결정은 아니다. SKILL.md Step 6의 수렴 판정에서 "더 높은 점수에 명백한 결함이 있으면 양측 병기로 강등"한다는 규칙을 같이 적용한다.

---

## 축 1: 출처 신뢰도 (Source Reliability)

### 정의

답변의 모든 주장이 코드 인용으로 뒷받침되는가, 추측·일반론으로 빠지지 않는가.

### 검증 방법

답변 본문의 각 주장(문장 또는 논리 단위)에 대해, 대응하는 인용 줄이 있는지 1:1로 매핑한다. 매핑되지 않는 주장이 몇 건인지 센다. 일반론 표현(예: "보통", "대개", "일반적으로", "프레임워크가 알아서")이 등장하면 해당 문장은 인용 부재로 간주한다.

### 밴드

| 점수 | 기준 |
|---|---|
| **9~10** | 답변의 모든 주장이 인용에 매핑된다. 일반론 표현 없음. "특이사항 없음" 같은 상위 메타 진술 외에는 모두 코드 근거. |
| **6~8** | 1~2개의 부수적 주장에 인용이 빠져 있거나 약한 연결. 핵심 주장은 모두 인용으로 뒷받침. |
| **3~5** | 핵심 주장 중 일부에 인용 부재. 일반론 표현 1~2회 등장. 답변의 신뢰도가 부분적으로만 확보됨. |
| **0~2** | 대부분의 주장이 인용 없이 일반론·추측으로 작성. 답변이 코드베이스가 아닌 LLM의 사전 지식에 의존. |

### 예시

- **9점 답변**: "주문 생성 시 `OrderService.createOrder()`(`OrderService.java:45`)가 호출되며, `@Transactional`(`OrderService.java:43`)로 트랜잭션 경계가 설정된다." — 모든 주장에 인용.
- **5점 답변**: "Spring은 `@Transactional`을 통해 트랜잭션을 관리하며, 일반적으로 서비스 레이어에 적용된다. 이 프로젝트에서도 `OrderService`에서 사용되고 있다(`OrderService.java:43`)." — 첫 두 문장이 일반론, 마지막만 인용.
- **1점 답변**: "트랜잭션은 보통 서비스 레이어에서 시작되어 리포지토리 호출까지 이어진다. Spring이 알아서 처리해준다." — 인용 0건.

## 축 2: 인용 정확성 (Citation Accuracy)

### 정의

인용한 `file_path:line_number`가 실제로 존재하고, 인용된 줄이 답변의 주장을 실제로 뒷받침하는가.

### 검증 방법

Step 4에서 양측 인용을 모두 Read로 직접 확인한 결과를 사용한다. 각 인용에 대해 다음 3가지를 점검:

1. **존재성** — 해당 라인이 실제로 그 파일에 존재하는가
2. **연결성** — 인용된 줄이 답변의 주장과 실제로 연결되는가 (주장은 "트랜잭션 경계"인데 인용 줄은 가입 알림 로직이면 비연결)
3. **정확성** — off-by-one (예: `:45` vs `:46`), 메서드명 오타 등

검증 표본 비율: 양측 합쳐 20개 이하면 전수 검증, 그 이상이면 핵심 인용(결론 직접 근거) 전수 + 보조 인용 50% 표본.

### 밴드

| 점수 | 기준 |
|---|---|
| **9~10** | 모든 인용이 존재·연결·정확 모두 통과. (또는 N≥10건 중 9개 이상 통과) |
| **6~8** | 1건의 부정확(off-by-one, 약한 연결, 부수적 인용 오류). 핵심 인용은 모두 정확. |
| **3~5** | 다수 부정확 또는 1건이라도 핵심 인용에서 비연결. 답변 결론을 인용으로 부분적으로만 뒷받침. |
| **0~2** | 핵심 인용이 잘못된 파일·줄을 가리킴. 또는 존재하지 않는 라인을 인용. |

### 예시

- **10점**: 답변에 인용 7건, 모두 Read 검증에서 존재·연결·정확 통과.
- **7점**: 인용 5건 중 1건이 off-by-one (실제는 `:88`인데 답변은 `:87`로 표기). 핵심 인용은 정확.
- **3점**: 인용 4건 중 2건이 비연결 — 답변은 "할인 분기"라고 했는데 인용 줄은 가입 분기. 핵심 인용 1건이 잘못됨.
- **0점**: 인용한 메서드가 그 파일에 존재하지 않음 (LLM 환각).

## 축 3: 논리 일관성 (Logical Consistency)

### 정의

답변 내부에서 모순이 없는가, 인용과 결론이 정합하는가, 추론 흐름이 자연스러운가.

### 검증 방법

답변 본문을 처음부터 끝까지 읽으며 다음 점검:

1. **자체 모순** — 한 문단에서 X라 하고 다른 문단에서 ¬X라고 하는가
2. **인용과 결론의 정합** — 인용된 코드의 실제 동작과 답변의 결론이 일치하는가 (예: 인용된 `if (member.grade >= GOLD)`인데 답변은 "PLATINUM 이상"이라 결론)
3. **비약** — 인용에서 결론까지의 논리 단계가 누락 없이 이어지는가

### 밴드

| 점수 | 기준 |
|---|---|
| **9~10** | 답변 흐름에 모순·비약 없음. 인용에서 결론까지의 추론이 자연스럽고 빈 칸 없음. |
| **6~8** | 1건의 약한 비약 또는 부수적 모순. 핵심 결론은 인용과 정합. |
| **3~5** | 핵심 추론에서 비약 또는 인용된 코드와 결론의 약한 연결. 독자가 의심해야 할 정도. |
| **0~2** | 답변 자체가 자체모순. 또는 인용된 코드가 답변의 정반대 결론을 가리킴. |

### 예시

- **9점**: "할인 적용 조건은 `member.grade >= GOLD` 그리고 `order.amount >= 50000`이다(`DiscountPolicy.java:23-24`). 두 조건이 AND로 결합되어 있어 한쪽만 충족하면 미적용." — 인용·논리·결론 정합.
- **6점**: "할인은 GOLD 이상에서 적용된다. 또한 첫 주문이면 추가 5%가 적용된다." — 첫 주문 추가 5% 부분에 인용은 있으나 본문 흐름에서 분리되어 있어 약한 비약.
- **2점**: 답변 본문은 "할인 미적용"이라 결론, 인용 줄은 `discountRate = 0.1`로 명백히 적용 — 인용과 정반대 결론.

## 축 4: 반증 고려 (Counterevidence Consideration)

### 정의

반대 사례·예외·가정의 한계를 짚었는가, 단순 confirmation bias로 빠지지 않았는가.

### 검증 방법

답변의 "한계·반증" 섹션 + 본문 내 예외 언급을 합쳐 다음 점검:

1. **명시적 한계 섹션** — "한계·반증" 섹션에 실질적 내용이 있는가 (단순 "특이사항 없음"인데 실제로는 예외가 존재하면 감점)
2. **엣지케이스 짚음** — 답변의 결론에 영향을 줄 수 있는 분기(null, 빈 컬렉션, 권한 분기 등)를 짚었는가
3. **가정의 한계** — 답변이 어떤 가정 위에 서 있는지 명시했는가 (예: "이 분석은 X 모듈만 본 결과")

**주의**: 반증을 짚는 것은 "확신을 줄이라"는 게 아니다. 정당한 확신은 유지하되, 답이 안 통하는 경계 조건을 짚었는가를 본다.

### 밴드

| 점수 | 기준 |
|---|---|
| **9~10** | 명시적 한계 섹션이 실질적 내용을 담고 있고, 답변의 결론에 영향을 주는 예외/엣지케이스가 본문이나 한계 섹션에서 짚어짐. |
| **6~8** | 한계·반증 언급은 있으나 부수적. 또는 1~2개 예외만 짚고 나머지를 놓침. |
| **3~5** | 한계·반증을 거의 다루지 않음. "특이사항 없음"이지만 실제로는 답변 결론에 영향을 줄 분기가 존재. |
| **0~2** | Confirmation bias — 답을 강하게 단정. 반증 고려 0건. 명백한 예외(null 분기, 권한 분기 등)를 무시. |

### 예시

- **9점**: "할인 적용 조건은 GOLD 등급 + 5만원 이상(`DiscountPolicy.java:23-24`). 다만 `applyHolidayPromo()`(`PromoService.java:67`)가 호출되면 등급 무관하게 추가 10%가 적용되므로 휴일 promo가 활성일 때는 위 조건이 단독 진실이 아님." — 본 결론 + 영향 주는 예외 명시.
- **6점**: 결론 명확 + "한계·반증: 권한 분기는 분석 안 함" 한 줄 — 짚었으나 다룬 예외가 부수적.
- **3점**: "한계·반증: 특이사항 없음" — 실제로는 `if (testMode)` 분기로 답이 달라지는 곳이 있음에도 짚지 않음.
- **0점**: "X는 무조건 Y이다." 단정형. 명백한 null 분기·권한 분기 무시.

## 채점 시 빈번한 함정

| 함정 | 방지 |
|---|---|
| 답변의 톤(자신감 있게 들림)에 채점이 휩쓸림 | 인용·검증 결과만 본다. "단정형 = 점수 높음"은 거짓. 단정형이 인용 부족이면 오히려 감점. |
| Codex가 한국어를 안 따라서 출처 신뢰도를 깎음 | 언어 준수는 별도 신호. 본 4축에는 영향 없음. SKILL.md Troubleshooting의 "한국어 미준수" 절에서 별도 처리. |
| 인용 개수가 많으면 자동 9점으로 보는 편향 | 개수가 아니라 **연결성**이 핵심. 5건 정확 > 12건 중 일부 비연결. |
| "한계·반증" 섹션에 "특이사항 없음"이라 적혀 있으면 자동 0점으로 보는 편향 | 실제로 예외가 없는 좁은 질문도 있다. 답변의 본문에서 충분히 다뤘다면 6~8점은 줄 수 있음. |
| Claude/Codex 중 어느 쪽 답인지 의식하며 채점 | 채점은 답변 텍스트만 본다. 라벨을 가리고 채점한다는 자세. |

## 점수 합계 산출

```
합계 = 출처 신뢰도 + 인용 정확성 + 논리 일관성 + 반증 고려
점수 차 = | Claude 합계 - Codex 합계 |
```

**수렴 판정** (SKILL.md Step 6과 동일):

- 점수 차 ≥ 6점(15%) → `verdict: converged`, 더 높은 합계의 답 채택
- 점수 차 < 6점 → `verdict: split`, 양측 병기

채택된 답에 명백한 결함(예: 인용 정확성 1건이 통째로 틀린 핵심 인용)이 있으면 `converged`라도 `split`로 강등하고 사유를 명시한다.
