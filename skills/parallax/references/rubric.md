# Parallax 채점 루브릭

각 답변(라벨 익명화 상태의 답변 A / 답변 B)을 4개 축에 대해 0~10점으로 채점한다. 만점 40점.

> **사용 시점**: SKILL.md의 Step 5에서 **Explore 서브에이전트가 본 문서를 Read한다**. 채점자는 답변자와 격리된 컨텍스트에 있으므로, 이 문서가 채점의 단일 ground truth다.

> **채점 원칙**: 점수는 신호일 뿐 결정은 아니다. SKILL.md Step 6의 수렴 판정에서 "더 높은 점수에 명백한 결함이 있으면 양측 병기로 강등"한다는 규칙을 같이 적용한다.

> **익명화 가정**: 채점자는 답변 A/B가 어느 모델(Claude/Codex)의 산출인지 모른다. 답변 본문에서 모델 정체성을 추측하거나 언급하지 마라. 텍스트와 인용 자동 검증 결과만으로 채점한다.

---

## 축 1: 출처 신뢰도 (Source Reliability)

### 정의

답변의 모든 주장이 코드 인용으로 뒷받침되는가, 추측·일반론으로 빠지지 않는가.

### 검증 방법

답변 본문의 각 주장(문장 또는 논리 단위)을 분리하여 인용 매핑 여부를 1:1로 점검한다. 일반론 표현(예: "보통", "대개", "일반적으로", "프레임워크가 알아서")이 등장하면 해당 문장은 인용 부재로 간주한다.

**산출 기준** (보조):

```
매핑률 = (인용에 매핑된 주장 수) / (전체 주장 수)
```

### 밴드

| 점수 | 기준 | 매핑률 가이드 |
|---|---|---|
| **9~10** | 답변의 모든 주장이 인용에 매핑된다. 일반론 표현 없음. | 매핑률 ≥ 95% |
| **6~8** | 1~2개의 부수적 주장에 인용이 빠져 있거나 약한 연결. 핵심 주장은 모두 인용으로 뒷받침. | 매핑률 70~94% |
| **3~5** | 핵심 주장 중 일부에 인용 부재. 일반론 표현 1~2회. | 매핑률 40~69% |
| **0~2** | 대부분의 주장이 인용 없이 일반론·추측. 답변이 코드베이스가 아닌 LLM 사전 지식에 의존. | 매핑률 < 40% |

매핑률이 밴드와 어긋나면 본문 정성 판단을 우선한다(예: 매핑률 95%이지만 핵심 결론이 인용 없는 추측이면 6~8 밴드).

### 예시

- **9점**: "주문 생성 시 `OrderService.createOrder()`(`OrderService.java:45`)가 호출되며, `@Transactional`(`OrderService.java:43`)로 트랜잭션 경계가 설정된다." — 모든 주장에 인용.
- **5점**: "Spring은 `@Transactional`을 통해 트랜잭션을 관리하며, 일반적으로 서비스 레이어에 적용된다. 이 프로젝트에서도 `OrderService`에서 사용되고 있다(`OrderService.java:43`)." — 첫 두 문장 일반론.
- **1점**: "트랜잭션은 보통 서비스 레이어에서 시작되어 리포지토리 호출까지 이어진다. Spring이 알아서 처리해준다." — 인용 0건.

## 축 2: 인용 정확성 (Citation Accuracy) — Mechanical 산출

### 정의

인용한 `file_path:line_number`가 실제로 존재하고, 인용된 줄이 답변의 주장을 실제로 뒷받침하는가.

### 검증 방법 — Mechanical

SKILL.md Step 4-B의 **인용 자동 검증 결과**를 그대로 사용한다. 자동 추출(`sed`)은 다음 3개 상태로 분류한다:

1. ✅ **존재 + 연결** — 라인 존재, 답변 주장과 의미 연결 명확
2. ⚠️ **약한 연결** — 라인 존재하나 주장과 의미적 거리 있음 또는 부수적
3. ❌ **비존재** — 파일 없음, 라인 번호가 파일 길이 초과, 또는 주장과 완전 무관

**점수 산출**:

```
통과율 = (✅ 건수) / (전체 인용 건수)
기본 점수 = round(통과율 × 10)
```

**강등 규칙** (이게 더 우선):
- **핵심 인용**(답변의 결론을 직접 뒷받침하는 인용) 1건이라도 ❌이면 → 최대 4점.
- ⚠️ 비율이 30% 초과면 → 최대 6점.
- 자동 검증 결과가 누락된 인용이 있으면 → 채점자가 직접 Read로 보충 검증.

**검증 표본 비율**: 자동 검증은 전수. 채점자의 추가 Read 검증은 핵심 인용 전수 + 보조 인용 50% 표본.

### 밴드

| 점수 | 기준 |
|---|---|
| **9~10** | 통과율 ≥ 90%, 핵심 인용 모두 ✅. |
| **6~8** | 통과율 60~89%. ⚠️ 1~2건 또는 부수적 ❌ 1건. 핵심 인용은 모두 ✅. |
| **3~5** | 통과율 30~59%. 또는 핵심 인용에서 ⚠️/❌ 발생. |
| **0~2** | 핵심 인용이 ❌. 또는 통과율 < 30%. |

### 예시

- **10점**: 인용 7건 모두 ✅. 핵심 인용 3건 모두 통과.
- **7점**: 인용 5건 중 1건 ⚠️ (off-by-one, 실제는 `:88`인데 `:87` 표기). 핵심은 모두 ✅.
- **3점**: 인용 4건 중 2건 ⚠️ — 답변 주장 "할인 분기"인데 인용 줄은 가입 분기. 핵심 인용 1건 ❌.
- **0점**: 인용한 메서드가 그 파일에 존재하지 않음(LLM 환각).

## 축 3: 논리 일관성 (Logical Consistency)

### 정의

답변 내부에서 모순이 없는가, 인용과 결론이 정합하는가, 추론 흐름이 자연스러운가.

### 검증 방법

답변 본문을 처음부터 끝까지 읽으며 다음 점검:

1. **자체 모순** — 한 문단에서 X라 하고 다른 문단에서 ¬X라고 하는가
2. **인용과 결론의 정합** — 인용된 코드의 실제 동작(축 2의 sed 추출 결과로 확인)과 답변의 결론이 일치하는가
3. **비약** — 인용에서 결론까지의 논리 단계가 누락 없이 이어지는가

### 밴드

| 점수 | 기준 |
|---|---|
| **9~10** | 답변 흐름에 모순·비약 없음. 인용에서 결론까지 추론 자연스럽고 빈 칸 없음. |
| **6~8** | 1건의 약한 비약 또는 부수적 모순. 핵심 결론은 인용과 정합. |
| **3~5** | 핵심 추론에서 비약 또는 인용된 코드와 결론의 약한 연결. 독자가 의심해야 할 정도. |
| **0~2** | 답변 자체가 자체모순. 또는 인용된 코드가 답변의 정반대 결론을 가리킴. |

### 예시

- **9점**: "할인 적용 조건은 `member.grade >= GOLD` 그리고 `order.amount >= 50000`이다(`DiscountPolicy.java:23-24`). 두 조건이 AND로 결합되어 한쪽만 충족하면 미적용." — 인용·논리·결론 정합.
- **6점**: "할인은 GOLD 이상에서 적용된다. 또한 첫 주문이면 추가 5%가 적용된다." — 첫 주문 추가 5% 부분 인용은 있으나 본문 흐름에서 분리되어 약한 비약.
- **2점**: 본문은 "할인 미적용" 결론, 인용 줄은 `discountRate = 0.1`로 명백히 적용 — 인용과 정반대 결론.

## 축 4: 반증 고려 (Counterevidence Consideration)

### 정의

반대 사례·예외·가정의 한계를 짚었는가, 단순 confirmation bias로 빠지지 않았는가.

### 검증 방법

답변의 "한계·반증" 섹션을 본다. SKILL.md Step 2.5(Claude) / Step 3 프롬프트(Codex)에서 **양측 모두 시나리오 3개 이상을 강제**하므로, 시나리오 개수와 질을 함께 본다.

1. **시나리오 개수** — 한계·반증 섹션에 (조건, 검증 방법) 형태의 시나리오가 3개 이상인가
2. **시나리오 질** — 답변의 결론에 실제로 영향을 줄 수 있는 분기·가정·엣지케이스를 짚었는가 (단순한 보일러플레이트가 아닌가)
3. **검증 가능성** — 각 시나리오가 어떤 파일·메서드를 보면 확인되는지 명시했는가

**주의**: 반증을 짚는 것은 "확신을 줄이라"는 게 아니다. 정당한 확신은 유지하되, 답이 안 통하는 경계 조건을 짚었는가를 본다.

### 밴드

| 점수 | 기준 |
|---|---|
| **9~10** | 시나리오 3개 이상 + 모두 답변 결론에 영향 줄 수 있는 분기/가정 + 검증 방법 명시. |
| **6~8** | 시나리오 2~3개. 실질적이지만 1개는 부수적이거나 검증 방법이 모호. |
| **3~5** | 시나리오 1개 또는 형식적("특이사항 없음") — 실제로는 결론 영향 분기가 존재. |
| **0~2** | "특이사항 없음"이 명백히 거짓 (자동 검증에서 비연결 인용이 있는데 한계로 짚지 않음). 단정형 답변. |

### 예시

- **9점**: "조건: 답이 OrderService 모듈만 본 결과인데 OrderFacade에 별도 createOrder 경로가 있다면 결론이 달라짐 / 검증: Grep 'createOrder' 전체" — 3개 모두 이런 형식.
- **6점**: 시나리오 3개이나 1개가 "코드 변경 시 답이 달라질 수 있음" 같은 일반론.
- **3점**: "특이사항 없음" — 자동 검증에서 ⚠️ 인용이 있는데도 짚지 않음.
- **0점**: 시나리오 0개 + 단정형 결론.

## 채점 시 빈번한 함정

| 함정 | 방지 |
|---|---|
| 답변의 톤(자신감 있게 들림)에 채점이 휩쓸림 | 인용·자동 검증 결과만 본다. 단정형이 인용 부족이면 오히려 감점. |
| 인용 개수가 많으면 자동 9점으로 보는 편향 | 개수가 아니라 **연결성**(축 2의 ✅ 비율)이 핵심. 5건 ✅ > 12건 중 일부 ⚠️. |
| "한계·반증: 특이사항 없음"이면 자동 0점으로 보는 편향 | Step 2.5 / Step 3 프롬프트는 시나리오 3개를 강제한다. 0개면 형식 위반 → 0~2점. 그러나 시나리오 본문이 부실(일반론)일 수도 있으므로 질을 함께 본다. |
| 답변에서 모델 정체성을 추측 | 채점자는 답변 A/B 라벨만 본다. "Codex 답으로 보임" 같은 메타 추론은 결과에서 제외하고 텍스트만 본다. |
| 자동 검증의 ⚠️/❌를 무시하고 본인 직관으로 점수 | 자동 검증은 mechanical truth. 무시하지 말고 점수에 반영. 이의가 있으면 추가 Read로 재검증한 뒤 사유 명시. |
| 한쪽 답에 더 후한 정성 평가 | 답변 텍스트 간 직접 비교는 피하고, 각 답을 **rubric 단독 적용**으로 채점한다. 비교는 Step 6 수렴 판정에서. |

## 점수 합계 산출

```
합계 = 출처 신뢰도 + 인용 정확성 + 논리 일관성 + 반증 고려
점수 차 = | 답변 A 합계 - 답변 B 합계 |
```

채점자는 합계와 점수 차까지 산출하되, **수렴/병기 판정은 메인 컨텍스트(Step 6)에서 라벨 복원 후 수행**한다. 채점자는 점수표만 반환한다.

**수렴 판정** (SKILL.md Step 6과 동일, 라벨 복원 후 적용):

- 점수 차 ≥ 6점(15%) → `verdict: converged`, 더 높은 합계의 답 채택
- 점수 차 < 6점 → `verdict: split`, 양측 병기

채택된 답에 명백 결함(예: 인용 정확성 핵심 1건 ❌)이 있으면 `converged`라도 `split`로 강등하고 사유를 명시한다. 채점자가 "명백한 결함" 항목으로 보고한 내용을 Step 6에서 검토한다.
