# Performance Profiler

Java/Spring 코드를 정적 분석하여 성능 병목을 식별하고 최적화 방안을 제시하는 스킬.

## 분석 워크플로우

### 1. 대상 파악

사용자가 지정한 파일/클래스/패키지, 또는 "전체적으로 봐줘" 같은 요청을 확인한다.
특정 성능 문제를 언급하면 (예: "API가 느려요") 해당 흐름을 우선 추적한다.

### 2. 분석 카테고리

아래 4개 영역을 순서대로 분석한다.

---

#### A. DB 쿼리 성능

가장 흔한 병목 원인. JPA/MyBatis 코드를 중심으로 분석한다.

| 패턴 | 탐지 방법 |
|------|-----------|
| **N+1 문제** | `@OneToMany`/`@ManyToOne` LAZY 로딩 + 루프 내 연관 객체 접근 |
| **인덱스 누락 가능성** | WHERE/ORDER BY에 사용되는 컬럼이 Entity에 `@Index` 없음 |
| **과도한 SELECT** | `findAll()` 무조건 호출, 페이징 없는 목록 조회 |
| **불필요한 JOIN** | 사용하지 않는 연관 관계를 EAGER로 로딩 |
| **쿼리 내 함수 사용** | WHERE 절에서 컬럼에 함수 적용 (인덱스 무력화) |
| **벌크 연산 누락** | 루프 내 단건 INSERT/UPDATE (→ `saveAll`, bulk query) |
| **카운트 쿼리 비효율** | 존재 여부만 필요한데 `count()` 사용 (→ `exists()`) |

**N+1 탐지 상세:**
```java
// 위험: LAZY 로딩 + 루프 접근
List<Order> orders = orderRepository.findAll();
for (Order order : orders) {
    order.getItems().size(); // 주문 수만큼 추가 쿼리 발생
}

// 해결: Fetch Join 또는 @EntityGraph
@Query("SELECT o FROM Order o JOIN FETCH o.items")
List<Order> findAllWithItems();
```

#### B. 알고리즘 복잡도

코드 내 비효율적 알고리즘 패턴을 탐지한다.

| 패턴 | 탐지 방법 |
|------|-----------|
| **O(n²) 중첩 루프** | 컬렉션 중첩 순회, 특히 내부에서 `contains`/`indexOf` 호출 |
| **반복 계산** | 루프 내에서 같은 값을 매번 재계산 |
| **비효율적 자료구조** | 빈번한 탐색에 List 사용 (→ Map/Set) |
| **불필요한 정렬** | 이미 정렬된 데이터 재정렬, 전체 정렬 후 Top N만 사용 |
| **스트림 오용** | 불필요한 중간 연산, 같은 컬렉션에 여러 번 스트림 |

```java
// 위험: O(n*m) - List.contains는 O(n)
for (Order order : orders) {
    if (targetIds.contains(order.getId())) { ... }
}

// 개선: O(n+m) - Set.contains는 O(1)
Set<Long> targetIdSet = new HashSet<>(targetIds);
for (Order order : orders) {
    if (targetIdSet.contains(order.getId())) { ... }
}
```

#### C. 메모리 사용

불필요한 객체 생성과 메모리 낭비 패턴을 탐지한다.

| 패턴 | 탐지 방법 |
|------|-----------|
| **대량 데이터 인메모리 로딩** | DB 전체 조회 후 Java에서 필터링 |
| **불필요한 객체 복사** | 매번 새로운 컬렉션 생성, 깊은 복사 남용 |
| **String 연결** | 루프 내 `+` 연산자로 문자열 연결 (→ StringBuilder) |
| **Autoboxing 반복** | 루프 내 primitive ↔ wrapper 변환 |
| **큰 객체 캐싱 누락** | 비용 높은 계산 결과를 매번 재생성 |
| **스트림 toList() 남용** | 중간 결과를 불필요하게 리스트로 수집 |
| **Static 컬렉션 누적** | Static 필드에 데이터가 계속 쌓이는 구조 |

---

#### D. API 응답 시간

요청-응답 흐름에서 지연을 유발하는 패턴을 탐지한다.

| 패턴 | 탐지 방법 |
|------|-----------|
| **동기 외부 호출** | 외부 API를 순차적으로 여러 번 호출 |
| **불필요한 직렬 처리** | 독립적인 작업을 순차 실행 (→ 병렬화 가능) |
| **응답에 불필요한 데이터** | 거대한 객체를 그대로 반환, 필요한 필드만 DTO로 변환 가능 |
| **캐싱 부재** | 자주 조회되지만 변경이 적은 데이터에 캐시 미적용 |
| **트랜잭션 범위 과대** | 외부 API 호출을 트랜잭션 안에서 수행 |
| **로깅 과다** | 반복문 안에서 매번 로그 출력 |

```java
// 위험: 외부 API 호출이 트랜잭션 안에 있음
@Transactional
public void processOrder(Order order) {
    orderRepository.save(order);
    notificationService.sendEmail(order); // 외부 호출 - DB 커넥션 점유
    paymentService.charge(order);         // 외부 호출 - 타임아웃 시 트랜잭션 롤백
}

// 개선: 트랜잭션과 외부 호출 분리
@Transactional
public void saveOrder(Order order) {
    orderRepository.save(order);
}

public void processOrder(Order order) {
    saveOrder(order);
    notificationService.sendEmail(order);
    paymentService.charge(order);
}
```

### 3. 영향도 평가

각 이슈에 대해 실질적 영향을 판단한다:
- **데이터 규모**: 현재/예상 데이터 양에서 실제로 문제가 되는가?
- **호출 빈도**: 자주 호출되는 경로인가, 드물게 사용되는 기능인가?
- **체감 영향**: 사용자가 느끼는 지연인가, 내부 배치인가?

소량 데이터에서 O(n²)이 문제가 안 될 수 있듯, 이론적 비효율이 아닌 실질적 영향에 집중한다.

## 심각도 기준

| 심각도 | 기준 |
|--------|------|
| **Critical** | 데이터 증가 시 장애 가능성, N+1 대량 발생, OOM 위험 |
| **Warning** | 눈에 띄는 성능 저하, 비효율적이지만 당장 장애는 아님 |
| **Info** | 사소한 최적화 기회, 대규모에서만 차이 발생 |

## 분석 원칙

- 추측이 아닌 코드 근거를 기반으로 판단한다. "느릴 수 있다"가 아니라 "N건 조회 시 N+1회 쿼리가 발생한다"처럼 구체적으로 설명한다.
- 과도한 최적화를 경계한다. 데이터 100건짜리 테이블의 O(n²)은 이슈가 아니다.
- 최적화의 트레이드오프를 반드시 명시한다. 성능 개선이 가독성이나 유지보수성을 해치면 그 비용을 밝힌다.
- 측정 가능한 개선 지표를 제시한다. "빨라진다"가 아니라 "쿼리 수가 N에서 1로 줄어든다" 같은 정량적 표현을 사용한다.
