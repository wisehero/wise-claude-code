# Performance Profiler

Java/Spring 코드를 정적 분석하여 성능 병목을 식별하고 최적화 방안을 제시하는 스킬.

## 분석 워크플로우

### Step 1: 대상과 맥락 파악

사용자 요청에서 분석 방향을 결정한다:

- **특정 문제 언급** (예: "API가 느려요", "N+1 발생"): 해당 문제의 흐름을 우선 추적
- **대상만 지정** (예: "OrderService 성능 분석"): 4개 카테고리를 영향도 순으로 분석
- **전체 분석** (예: "성능 전체적으로 봐줘"): 핵심 API 엔드포인트부터 탐색

### Step 2: 카테고리별 분석

4개 영역을 분석한다. 순서는 사용자 맥락에 따라 유연하게 조정한다.

#### A. DB 쿼리 성능

가장 흔한 병목 원인. JPA와 MyBatis 모두 대상. 상세 패턴 및 예시는 `references/db-patterns.md` 참조.

주요 탐지 대상:
- **N+1 문제**: LAZY 로딩 + 루프 내 연관 객체 접근
- **인덱스 누락 가능성**: WHERE/ORDER BY 컬럼에 `@Index` 없음
- **과도한 SELECT**: `findAll()` 무조건 호출, 페이징 없는 목록 조회
- **벌크 연산 누락**: 루프 내 단건 INSERT/UPDATE
- **카운트 쿼리 비효율**: 존재 여부만 필요한데 `count()` 사용
- **MyBatis 동적 쿼리 비효율**: `<foreach>`의 과도한 반복, 불필요한 `<if>` 분기

#### B. 알고리즘 복잡도

코드 내 비효율적 알고리즘 패턴. 상세 패턴 및 예시는 `references/algorithm-patterns.md` 참조.

주요 탐지 대상:
- **O(n²) 중첩 루프**: 특히 내부에서 `List.contains`/`indexOf` 호출
- **비효율적 자료구조**: 빈번한 탐색에 List 사용 (→ Map/Set)
- **반복 계산**: 루프 내에서 같은 값을 매번 재계산
- **스트림 오용**: 불필요한 중간 연산, 같은 컬렉션에 여러 번 스트림

#### C. 메모리 사용

불필요한 객체 생성과 메모리 낭비. 상세 패턴 및 예시는 `references/memory-patterns.md` 참조.

주요 탐지 대상:
- **대량 데이터 인메모리 로딩**: DB 전체 조회 후 Java에서 필터링
- **String 연결**: 루프 내 `+` 연산자
- **Static 컬렉션 누적**: Static 필드에 데이터가 계속 쌓이는 구조
- **큰 객체 캐싱 누락**: 비용 높은 계산 결과를 매번 재생성

#### D. API 응답 시간

요청-응답 흐름에서 지연을 유발하는 패턴. 상세 패턴 및 예시는 `references/api-patterns.md` 참조.

주요 탐지 대상:
- **동기 외부 호출**: 외부 API를 순차적으로 여러 번 호출
- **트랜잭션 내 외부 호출**: 외부 API가 트랜잭션 안에서 DB 커넥션 점유
- **캐싱 부재**: 자주 조회되지만 변경이 적은 데이터
- **응답에 불필요한 데이터**: 거대한 객체를 그대로 반환

### Step 3: 영향도 평가

각 이슈에 대해 실질적 영향을 판단한다:
- **데이터 규모**: 현재/예상 데이터 양에서 실제로 문제가 되는가?
- **호출 빈도**: 자주 호출되는 경로인가, 드물게 사용되는 기능인가?
- **체감 영향**: 사용자가 느끼는 지연인가, 내부 배치인가?

소량 데이터에서 O(n²)이 문제가 안 될 수 있듯, 이론적 비효율이 아닌 실질적 영향에 집중한다.

### Step 4: 리포트 작성

분석 결과를 아래 구조로 제시한다.

- **발견 이슈**: Critical N개 / Warning N개 / Info N개
- **가장 큰 병목**: (핵심 이슈 1-2가지)

- **위치**: `패키지.클래스#메서드` (파일:라인)
- **카테고리**: DB 쿼리 / 알고리즘 / 메모리 / API 응답
- **문제**: 무엇이 비효율적이고 왜 느려지는지
- **영향**: 데이터 N건 기준 예상 쿼리 수, 시간 복잡도 등

**현재 코드:**
(문제 코드 발췌)

**최적화 방안:**
(개선된 코드)

**트레이드오프:**
- 개선: 쿼리 N회 → 1회, O(n²) → O(n) 등

- 리팩토링 후 테스트가 필요하면: "테스트 코드 작성해줘"로 junit-test-writer 활용

## 예시 시나리오

**사용자**: "주문 목록 API가 느린데 성능 분석해줘"

**행동**:
1. 주문 목록 API의 Controller → Service → Repository 흐름 추적
2. DB 쿼리 카테고리 우선 분석 (API 지연의 가장 흔한 원인)
3. N+1, 불필요한 JOIN, 페이징 누락 등 확인
4. 나머지 카테고리(알고리즘, 메모리, 응답 데이터) 순차 분석
5. 호출 흐름 Mermaid 다이어그램으로 병목 지점 시각화
6. 리포트 제시

**사용자**: "OrderService 성능 전체적으로 봐줘"

**행동**:
1. OrderService의 모든 public 메서드 확인
2. 각 메서드에서 4개 카테고리 이슈 탐지
3. 영향도 평가로 우선순위 결정
4. 리포트 제시

## 심각도 기준

| 심각도 | 기준 | 예시 |
|--------|------|------|
| **Critical** | 데이터 증가 시 장애 가능성 | N+1 대량 발생, OOM 위험, 트랜잭션 내 외부 호출 |
| **Warning** | 눈에 띄는 성능 저하 | 비효율적 알고리즘, 캐싱 부재 |
| **Info** | 사소한 최적화 기회 | 소규모 데이터의 O(n²), 미미한 중복 계산 |

## 분석 원칙

- 추측이 아닌 코드 근거를 기반으로 판단한다. "느릴 수 있다"가 아니라 "N건 조회 시 N+1회 쿼리가 발생한다"처럼 구체적으로 설명한다.
- 과도한 최적화를 경계한다. 데이터 100건짜리 테이블의 O(n²)은 이슈가 아니다.
- 최적화의 트레이드오프를 반드시 명시한다. 성능 개선이 가독성이나 유지보수성을 해치면 그 비용을 밝힌다.
- 측정 가능한 개선 지표를 제시한다. "빨라진다"가 아니라 "쿼리 수가 N에서 1로 줄어든다" 같은 정량적 표현을 사용한다.
- 트랜잭션 관련 이슈는 **성능 관점**(커넥션 점유, 락 범위, 응답 지연)에서만 다룬다. 구조적 관점의 트랜잭션 분석은 refactor-advisor 스킬의 영역이다.
