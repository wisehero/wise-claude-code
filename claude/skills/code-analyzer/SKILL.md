# Code Analyzer

코드베이스의 구조를 파악하고 비즈니스 로직을 이해하기 쉽게 설명하는 스킬. 언어에 무관하게 동작하며, mermaid 다이어그램을 포함한 분석 리포트를 제공한다.

## When to Use

다음 같은 요청에 반드시 사용한다:

- **코드베이스 구조 파악** — "이 프로젝트 어떻게 되어있어?", "아키텍처 분석"
- **비즈니스 로직 이해** — "결제 흐름이 어떻게 동작하는지", "이 기능 뭐하는 거야"
- **온보딩용 레거시 코드 파악** — 처음 보는 모듈을 이해해야 할 때
- **PR 리뷰 전 컨텍스트 확보** — 변경 대상 주변 코드를 이해해야 리뷰가 가능할 때

## When NOT to Use

다음 경우는 다른 스킬이 더 적합하므로 이 스킬을 호출하지 않는다:

- **코드 품질 평가/개선 제안** → `refactor-advisor` 사용. 이 스킬은 분석만 하고 "좋다/나쁘다"를 판단하지 않는다.
- **성능 병목 분석** → `performance-profiler` 사용
- **테스트 코드 작성** → `junit-test-writer` 사용
- **단일 파일 단순 읽기** → `Read` 도구로 충분하다. 분석 리포트까지 필요 없는 요청에 스킬을 호출하는 것은 과잉이다.

## 핵심 원칙

1. **실제 이름을 보존한다.** 다이어그램과 자연어 설명 모두에서 실제 클래스명, 메서드명, 모듈명을 그대로 쓴다. 추상화된 이름("ServiceClass", "HelperMethod")은 금지 — 리포트를 읽고 실제 코드로 찾아갈 수 없게 된다.
2. **진입점에서 시작해 필요한 만큼만 읽는다.** 범위 내 모든 파일을 무작정 Read하지 않는다. 진입점을 먼저 식별한 뒤 import/require 그래프를 따라가며 선택적으로 읽는다. 분석 깊이 기준(1단계)을 초과하는 순간 사용자에게 범위 축소를 제안한다.

## 상세 단계

### 1단계: 분석 범위 확정

사용자의 요청에서 분석 대상을 파악한다.

**범위가 명확한 경우** — 바로 2단계로 진행:
- "src/auth 모듈 분석해줘" → `src/auth/` 디렉토리
- "UserService.java 코드 분석" → 해당 파일 + 직접 의존 파일
- "로그인 기능 코드 분석해줘" → 로그인 관련 파일을 탐색하여 특정

**범위가 애매한 경우** — **Glob 선행 후 단일 역질문으로 확정** (역질문 2회 연속 금지):

범위가 모호하면 역질문 *전에* `Glob("src/**/*")` 또는 `Glob("app/**/*")`로 파일 수와 모듈 구조를 먼저 파악한다. 그 결과를 포함해 **한 번의 질문**으로 범위를 확정한다:

```
이 프로젝트에 분석 가능한 파일이 [N]개 있습니다.

주요 모듈:
- auth/ (4개) — 인증/인가
- order/ (8개) — 주문 관리
- payment/ (6개) — 결제 처리
...

다음 중 선택해주세요:
1. 특정 모듈 깊이 분석 — 예: "주문 쪽 깊게 봐줘"
2. 특정 레이어만 분석 — 예: "Controller 레이어만 전체 훑어줘"
3. 특정 기능 흐름 분석 — 예: "주문 생성부터 결제까지 흐름"
4. 전체 아키텍처 개요 (30개 이하일 때만 권장)
```

**사용자가 "전체 해줘"를 선택한 경우의 fallback**: 30개 이하면 전체 분석 진행. 30개 초과면 "전체를 한 번에 깊이 분석하기 어렵습니다. **진입점 + 핵심 서비스 중심의 개요 리포트**로 대체하겠습니다. 세부 모듈은 추가 요청으로 나눠 분석합니다."라고 안내하고, 진입점·설정 파일 기반의 경량 개요를 제공한다.

범위 확정 후, 분석 대상의 언어와 프레임워크를 파일 확장자 및 설정 파일(package.json, build.gradle, pom.xml, composer.json 등)로 자동 감지한다.

#### 언어별 힌트 파일 로드

특정 언어/프레임워크가 감지되면, `references/` 하위의 힌트 파일을 먼저 Read한 뒤 2단계로 진행한다. 힌트 파일에는 해당 언어의 진입점 패턴, 레이어 구조, Grep 치트시트, 분석 시 주의점이 정리되어 있다.

| 감지 조건 | 로드할 힌트 파일 |
|---|---|
| `composer.json` 또는 `artisan` 또는 `.php` 파일 5개 이상 | `references/php-hints.md` (PHP 5.6 / PHP 8.3 + Laravel 10) |
| `build.gradle(.kts)` 또는 `pom.xml` 또는 `src/main/java/` 디렉터리 존재 + `.java` 5개 이상 | `references/java-spring-hints.md` (Java 17+ / Spring Boot 2.7~3.x, 레거시 Spring 5.x) |

해당 언어의 힌트 파일이 없으면 힌트 Read를 건너뛰고 바로 2단계로 진행한다.

#### 힌트 파일 vs SKILL.md 본문의 우선순위 규칙

힌트 파일을 로드한 경우, 이후 단계(Step 2~5)에서는 **힌트 파일의 지시가 SKILL.md 본문을 교체(override)**한다. 보완이 아니라 교체다. 구체적으로:

- **Step 2 Grep 패턴**: 힌트 파일의 "Grep 패턴 치트시트"가 존재하면 SKILL.md 본문의 기본 심볼/의존성 패턴을 **그대로 대체**한다. 두 세트를 병합하지 않는다.
- **진입점 식별**: 힌트 파일의 "진입점 식별" 섹션이 본문의 진입점 후보(`main`, `index`, `App`, `*Controller`)를 **대체**한다.
- **레이어 구조**: 힌트 파일의 레이어 테이블이 본문의 `controller → service → repository`를 **대체**한다.
- **섹션 4 특이사항**: 힌트 파일이 나열한 주의점(N+1, Lazy fetch, Self-invocation, `@Transactional` 경계 등)은 본문의 "순환 의존성, 사용되지 않는 심볼"에 **추가**된다. 여기만 예외적으로 병합이 맞다.
- **시퀀스 participant 스타일**: 힌트 파일의 예시 스타일(역할 괄호 병기, `participant X as "Description"`)을 따른다.

힌트 파일이 없으면 SKILL.md 본문의 기본 패턴·후보를 사용한다. 이 경우 Step 2의 언어별 기본 패턴 분기(아래 참조)를 적용한다.

#### 분석 깊이 기준

범위 내 파일 수에 따라 분석 깊이를 조절한다:

- **10개 이하**: 모든 파일을 읽고 상세 분석
- **11~30개**: 진입점 + 핵심 서비스/모델 중심으로 분석. 유틸리티, 설정 파일은 목록만 정리
- **30개 초과**: 사용자에게 범위 축소를 제안. "이 모듈에 파일이 많아서, 핵심 기능 위주로 분석할까요? 아니면 특정 레이어(controller/service/repository)를 선택해주세요."

### 2단계: 코드 탐색 및 구조 파악

아래 순서를 정확히 따른다. 각 단계의 도구 호출은 구체적이어야 하며, 가능한 호출은 **한 메시지에서 병렬로** 실행한다.

1. **디렉토리 트리 파악 (단일 호출)**
   - `Glob("{범위}/**/*")` 한 번으로 파일 목록 확보
   - 예: `Glob("src/auth/**/*")`

2. **심볼 + 의존성 병렬 탐색 (한 메시지에서 두 Grep 병렬 호출)**

   1단계에서 감지한 언어에 따라 Grep 패턴을 선택한다. **범용 패턴을 고정 사용하지 않는다** — 범용 패턴은 Java의 interface/enum/record, PHP의 trait 등을 놓친다.

   **심볼 패턴 선택표:**

   | 감지 언어 | 심볼 Grep 패턴 | 비고 |
   |---|---|---|
   | **Java/Kotlin** | `"(class\|interface\|enum\|record\|@interface) "` | `function` 키워드 없음. method는 import 그래프 + Read로 파악 |
   | **PHP** | `"(class\|trait\|interface\|function) "` | php-hints 있으면 hints 패턴 우선 |
   | **Python** | `"(class\|def) "` | |
   | **JavaScript/TypeScript** | `"(class\|function\|const .* =\|export (default\|function\|class)) "` | |
   | **Go** | `"(func\|type\|interface) "` | |
   | **기타/불명** | `"(class\|function\|def\|func\|interface\|enum\|trait) "` | 최대 포괄 fallback |

   **의존성 패턴 선택표:**

   | 감지 언어 | 의존성 Grep 패턴 |
   |---|---|
   | **Java/Kotlin** | `"^import "` |
   | **PHP** | `"^namespace \|^use "` |
   | **Python** | `"^import \|^from .* import"` |
   | **JavaScript/TypeScript** | `"(^import \|require\\()"` |
   | **Go** | `"^import "` |
   | **기타/불명** | `"(import\|require\\(\|#include\|from .* import\|^use )"` |

   두 Grep 호출(심볼 + 의존성)은 반드시 **한 메시지에서 병렬 실행**하여 라운드트립을 절반으로 줄인다.

   **힌트 파일과의 우선순위**: 해당 언어의 hints 파일이 로드된 경우, hints에 기재된 Grep 패턴이 위 기본 패턴을 **대체**한다. hints에 없는 범주(예: hints가 심볼만 다루고 의존성을 다루지 않는 경우)만 위 기본 패턴으로 **보충**한다.

3. **진입점부터 선별적 Read**
   - 진입점 후보: `main`, `index`, `App`, `*Controller`, `*Application` 등. 설정 파일(`package.json` scripts, `build.gradle` tasks)에서 entry를 확인할 수도 있다.
   - 진입점 파일을 먼저 Read한 뒤, 2단계에서 수집한 import 그래프를 따라 **호출되는 파일만** 추가 Read
   - 유틸리티/설정 파일은 Read하지 않고 Grep 결과만으로 목록화

4. **계층 식별**
   - controller → service → repository 같은 레이어 구분을 기록
   - 레이어가 불분명한 구조는 "분류 없음"으로 남기고 임의 분류를 강제하지 않는다

**토큰 효율 규칙**: Read 횟수가 1단계의 분석 깊이 기준(10/11-30/30+)을 초과하면 더 읽지 말고 사용자에게 범위 축소를 제안한다.

### 3단계: 비즈니스 로직 분석

코드가 "무엇을 하는지"를 자연어로 설명한다.

각 주요 기능에 대해:
- **목적**: 이 기능이 해결하는 문제가 무엇인지
- **흐름**: 입력 → 처리 과정 → 출력을 단계별로 설명
- **핵심 규칙**: 조건 분기, 유효성 검증, 비즈니스 규칙, 트랜잭션 경계(원자성 보장), 락 획득 등을 명시
- **데이터 흐름**: 어떤 데이터가 어디서 생성되고 어디로 전달되는지. 이벤트/큐를 통한 간접 전달도 포함

설명은 개발자가 아닌 사람도 이해할 수 있을 정도로 자연스럽게 작성하되, 코드 레벨의 정확성은 유지한다. 기술 용어를 쓸 때는 해당 코드에서 실제 사용하는 이름(클래스명, 메서드명)을 함께 언급하여 코드와 설명을 연결한다.

각 주요 기능의 핵심 메서드 본문까지 Read하여 비즈니스 규칙(조건 분기, 검증 로직, 예외 처리)을 실제 코드에서 직접 확인한다. 메서드 시그니처만 보고 추측해서 작성하지 않는다.

### 4단계: 다이어그램 생성

분석 결과를 시각화한다. 모든 다이어그램은 mermaid 문법으로 작성한다.

#### 의존성 다이어그램

구성 요소 간 의존 관계를 `graph TD`로 표현한다.
- 노드: 클래스, 모듈, 또는 주요 함수
- 화살표: 의존 방향 (A가 B를 사용하면 A → B)
- 외부 의존성(DB, API, 라이브러리)은 구분하여 표시

#### 시퀀스 다이어그램

주요 기능별로 객체 간 상호작용을 `sequenceDiagram`으로 표현한다.
- 하나의 기능 흐름(예: 주문 생성, 로그인 처리)을 하나의 시퀀스 다이어그램으로
- participant는 실제 코드의 클래스/모듈명을 사용
- 요청(->>) / 응답(-->>)을 구분
- 분기가 있으면 alt/else 블록 활용

**간접 호출 포함 규칙**: 이벤트 디스패치(`event()`, `emit()`, `publish()`), 메시지 큐(`dispatch()`, `queue()`), 콜백/리스너 등 **간접 호출**이 발견되면 시퀀스 다이어그램에 반드시 포함한다. 비동기 실행이면 `Note right of <participant>: 비동기 — 큐 워커/이벤트 루프가 처리`를 붙인다. 이벤트→리스너 매핑은 프레임워크별 등록 파일(Laravel: `EventServiceProvider`, Spring: `@EventListener`)에서 확인한다.

시퀀스 다이어그램은 분석 범위 내 주요 기능마다 각각 작성한다.

#### 다이어그램 복잡도 관리

- **노드 15개 초과** 시: 단일 다이어그램에 우겨넣지 말고 레이어별(controller/service/repository) 또는 기능별로 분리된 다이어그램을 만든다.
- 분리 시 각 다이어그램의 제목에 범위를 명시한다 (예: "주문 생성 — Service 레이어 상세").

### 5단계: 리포트 출력

리포트는 아래 4개 섹션을 **이 순서 그대로** 포함해야 한다. 완전한 예시는 `references/report-template.md`에 있지만, 아래 인라인 명세가 우선한다.

**리포트 상단 — YAML frontmatter**

```yaml
---
analyzed_at: YYYY-MM-DD
scope: [분석 범위 경로]
language: [감지된 언어/프레임워크]
mode: detailed  # detailed | overview — overview는 섹션 2/3 생략 허용
---
```

`mode` 키는 1단계 범위 협상 결과에 따라 결정한다:
- **`detailed`** (기본값) — 4개 섹션 모두 완전 작성. 섹션 2의 4소항목과 섹션 3의 시퀀스 다이어그램 모두 필수.
- **`overview`** — Step 1에서 "개요만", "리스트만", "가볍게"로 확정되었거나 Step 1의 "전체 해줘 + 30개 초과 fallback"에 걸린 경우. 섹션 1과 섹션 4만 완전 작성, 섹션 2·3은 생략 가능(사유 명시). 구조 개요·호출 흐름·참고 사항만으로도 독립적인 리포트가 되도록 작성.

**섹션 1: 구조 개요**
- 핵심 구성 요소 테이블 (컬럼 3개 고정): `| 구성 요소 | 경로 | 역할 |`
- 의존성 다이어그램 1개: mermaid `graph TD`. 노드명은 실제 클래스/모듈명, 외부 의존성(DB, 외부 API)은 별도 스타일로 구분
- 호출 흐름 순번 목록: 진입점부터 최종 호출 대상까지 `1. → 2. → 3.` 형식

**섹션 2: 비즈니스 로직 분석** (`mode: detailed`에서 필수, `overview`에서 생략 허용)
- 주요 기능마다 4개 소항목을 **반드시 모두** 포함 — 생략·추가 금지:
  - **목적**: 이 기능이 해결하는 문제
  - **흐름**: 입력 → 처리 → 출력
  - **핵심 규칙**: 조건 분기, 검증, 비즈니스 규칙
  - **데이터 흐름**: 어떤 데이터가 어디서 생성되고 어디로 전달되는지
- 기능명은 코드에서 실제 쓰는 이름 (예: `PaymentService.processPayment`)

**섹션 2 탈출 조항** — 추측 금지 원칙(3단계 말미)과 "4소항목 반드시 포함" 규칙이 충돌하면 **추측 금지가 우선**한다. 다음 조건 중 하나라도 해당하면 섹션 2 전체 또는 해당 기능 항목을 사유와 함께 **생략**한다:

- 클래스 본문이 비어있거나 `{}`·선언만 있는 stub 프로젝트
- 메서드가 한 줄 위임만 하고 분기·규칙이 전무한 단순 어댑터
- 순수 인터페이스·enum·DTO record만 있는 경로 (행위가 없음)
- 메서드 시그니처·애노테이션만 있고 본문 Read가 불가능한 상태

생략 시 섹션 2 자리에 **생략 사유**를 한 단락으로 기록한다 (예: "대상 12개 클래스가 모두 빈 stub이라 비즈니스 로직이 존재하지 않음. 추측 작성 금지 원칙에 따라 섹션 2 생략"). `mode: overview`에서 생략할 때도 동일한 사유 기록을 적용한다.

**섹션 3: 시퀀스 다이어그램** (`mode: detailed`에서 필수, `overview`에서 생략 허용)
- 주요 기능마다 `sequenceDiagram` 1개
- `participant`는 실제 클래스/모듈명 사용. `Client`, `Service`, `Controller` 같은 범용 추상명을 **라벨 없이 단독**으로 쓰지 않는다 — 단독으로 쓰면 리포트를 읽은 사람이 실제 코드에서 그 participant가 어떤 클래스인지 찾을 수 없다.
- **구체 타입이 범위 밖인 외부 호출자는 반드시 보조 라벨을 병기한다** (회피가 아니라 필수 규칙). 이 규칙은 언어 무관하게 적용된다:
  - HTTP 요청을 시작하는 쪽 → `participant Client as "HTTP Client"` 또는 `participant Browser as "Browser"`
  - 외부 시스템 콜 → `participant PaymentGateway as "External Payment API"` 또는 `participant SMTP as "SMTP Server"`
  - 메시지 큐/비동기 워커 → `participant Queue as "Job Queue"` (php-hints/java-spring-hints 예시 참조)
- **판정 규칙**: 단독 `participant Client` / `participant Controller` / `participant Service` 같이 구체 클래스가 아닌 일반 명사로 끝나는 participant가 하나라도 있으면 시퀀스 다이어그램을 다시 작성한다. 본 스킬의 "실제 이름을 보존한다" 원칙(핵심 원칙 #1)의 직접 적용이다.
- 요청 `->>`와 응답 `-->>`를 구분
- 분기는 `alt/else` 블록 사용
- 섹션 2가 탈출 조항으로 생략되었다면 섹션 3도 생략한다 (시퀀스는 흐름의 시각화이므로 흐름 분석이 없으면 의미 없음)

**섹션 4: 참고 사항**
- 순환 의존성, 사용되지 않는 심볼, 추가 분석이 필요한 지점 등 특이사항만 기록
- 특이사항이 없으면 이 섹션을 생략해도 된다

**출력 방식**
- 기본: 터미널에 리포트 직접 출력
- 사용자가 파일 저장을 요청한 경우: `분석리포트_[대상명]_YYYYMMDD.md` 형식으로 저장
- **파일 충돌 방지**: 동일 경로에 파일이 이미 존재하면 덮어쓰지 않고 사용자에게 확인한다 — "(1) 덮어쓰기 (2) 타임스탬프 추가(`_v2`) (3) 취소". 같은 날 같은 대상을 재분석하는 경우가 있으므로 묵시적 덮어쓰기는 금지.

## Examples

### 예시 1: 특정 모듈 분석

```
사용자: "src/auth 모듈 분석해줘"
동작:
  1. src/auth/ 디렉토리 범위 확정
  2. Glob("src/auth/**/*")로 파일 목록 확인 → AuthController, AuthService, TokenProvider 등 식별
  3. 진입점(AuthController)부터 Read → import 따라가며 AuthService → TokenProvider 순서로 탐색
  4. 로그인/회원가입/토큰갱신 비즈니스 로직 설명
  5. 의존성 다이어그램 + 로그인 시퀀스 다이어그램 생성
  6. 터미널에 리포트 출력
```

### 예시 2: 특정 기능 분석

```
사용자: "결제 기능 코드가 어떻게 동작하는지 분석해줘"
동작:
  1. Grep("Payment|Order|결제")로 관련 파일 탐색 → PaymentController, OrderService 등 발견
  2. 범위 확정 후 구조 파악
  3. 결제 흐름을 자연어로 설명
  4. 결제 처리 시퀀스 다이어그램 생성
  5. 터미널 출력
```

    - order/ (8개) — 주문 관리

    - product/ (4개)
    - user/ (4개)
    - notification/ (4개)
    - common/ (13개) — 공용 도메인

    다음 중 선택해주세요:
    1. 특정 모듈 깊이 분석 — 예: '주문 쪽 깊게 봐줘'
    2. 특정 레이어만 분석 — 예: 'Controller 레이어만 전체 훑어줘'

    [2단계: Glob + 두 Grep 병렬 호출]

## Troubleshooting

**분석 대상 파일이 너무 많은 경우**
- 원인: 프로젝트 전체 또는 대규모 모듈 지정
- 해결: 분석 깊이 기준(1단계)에 따라 범위를 좁히자고 제안. "이 모듈에 파일이 50개 이상인데, 핵심 기능 위주로 분석할까요?"

**언어/프레임워크를 자동 감지하지 못한 경우**
- 원인: 설정 파일 부재 또는 비표준 구조
- 해결: 사용자에게 언어와 프레임워크를 직접 확인

**mermaid 다이어그램이 너무 복잡한 경우**
- 원인: 구성 요소가 너무 많아 다이어그램 가독성 저하
- 해결: 핵심 구성 요소만 포함하고, 세부 사항은 별도 다이어그램으로 분리. 노드가 15개를 초과하면 레이어별로 분리된 다이어그램을 만든다.

**진입점을 찾을 수 없는 경우**
- 원인: `main`/`index`/`App`/`*Controller` 네이밍을 따르지 않는 프로젝트
- 해결: 설정 파일에서 entry 지정을 먼저 확인 — `package.json`의 `scripts.start`/`main`, `build.gradle`의 `mainClass`, `pom.xml`의 `<mainClass>`, `pyproject.toml`의 `scripts`. 설정 파일에도 없으면 사용자에게 "이 프로젝트의 진입점 파일을 알려주세요"라고 질문.

**순환 의존성이 발견된 경우**
- 원인: 모듈 간 A → B → A 형태의 순환 참조
- 해결: 의존성 다이어그램에 점선 화살표(`A -.->|순환| B`)로 표시하고, 섹션 4(참고 사항)에 "순환 의존성: A ↔ B — 진입점 판단 주의" 명시. 분석과 평가를 섞지 않는 원칙에 따라 "이건 나쁜 설계다"라고 쓰지는 않는다 — 사실만 기록한다.

**stub · 선언 전용 프로젝트 (본문이 비어있는 경우)**
- 원인: 스캐폴드 상태의 프로젝트, 인터페이스·DTO·enum만 모여있는 모듈, 외부 라이브러리 선언부 등 클래스 본문이 `{}`뿐인 상태
- 증상: 섹션 2 "4소항목 반드시 포함" 규칙을 지키려면 추측 작성을 해야 하는 딜레마 발생
- 해결:
  1. 샘플 2~3개 파일을 Read해 stub 여부 확정 (모든 파일을 Read하지 말 것 — 토큰 낭비)
  2. 5단계의 **섹션 2 탈출 조항** 적용 — 섹션 2·3 생략 + 사유 기록
  3. 섹션 1(구조 개요)과 섹션 4(참고 사항 + "프로젝트 상태: 스캐폴드 단계")만으로 리포트 완결
  4. 섹션 4에 "추가 분석 권장 시점: 실제 로직 채워진 뒤 모듈 1개씩 지정 재요청"을 기록

**한 파일 안에 분석 대상 언어가 아닌 코드가 섞인 경우**
- 원인: Blade/Thymeleaf/JSP 템플릿 안의 `<script>`, Kotlin + Java 혼재 모듈 등
- 해결: 주력 언어로만 분석하고 섹션 4에 "언어 혼재: {기타} 코드는 이번 분석 범위 밖"으로 기록. 힌트 파일이 주력 언어 전용이면 다른 언어 부분은 분석에서 제외.
