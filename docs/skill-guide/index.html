Claude 스킬 구축 완벽 가이드

스킬(skill)의 기초 개념부터 계획·설계·테스트·배포, 현장에서 검증된 패턴과 문제 해결까지, Claude 스킬 제작에 필요한 내용을 담은 공식 가이드의 한국어 판본입니다.

번역 버전 안내

이 페이지는 The Complete Guide to Building Skills for Claude PDF(2026년 1월 기준)의 한국어 번역본입니다. 설계 원칙·작성 규칙·패턴 같은 뼈대는 PDF를 그대로 따르되, 시간이 지나며 달라지는 배포 경로·API 베타 상태·크로스 서피스 제약은 2026년 4월 기준 공식 문서(docs.claude.com / platform.claude.com)와 대조해 갱신했습니다. 갱신된 부분에는 “2026-04 갱신” 표시가 붙어 있습니다. 운영 관련 정보의 최종 출처는 항상 공식 문서입니다.

시작하며

스킬(skill)은 폴더로 포장된 지시문 모음으로, Claude에게 특정 작업이나 워크플로를 처리하는 방법을 가르치는 도구입니다. 스킬은 Claude를 사용 목적에 맞게 커스터마이징하는 주요 수단입니다. 매 대화마다 선호, 프로세스, 도메인 지식을 다시 설명할 필요 없이 Claude에게 한 번 가르쳐두면 이후 대화에서 그 지식이 재사용됩니다.

스킬은 반복 가능한 워크플로에서 특히 유용합니다. 스펙에서 프런트엔드 디자인을 뽑아내는 작업, 일관된 방법론으로 리서치를 수행하는 작업, 팀의 스타일 가이드를 따르는 문서를 만드는 작업, 여러 단계가 연결된 프로세스를 자동으로 실행하는 작업이 대표적입니다. 스킬은 코드 실행이나 문서 생성 같은 Claude의 내장 기능과도 잘 어울립니다. MCP 연동을 구축하는 개발자에게 스킬은 특히 유용한데, 단순한 도구 접근을 신뢰성 있고 최적화된 워크플로로 바꿔주기 때문입니다.

이 가이드는 스킬 제작에 필요한 내용을 다룹니다. 계획과 구조에서 출발해 테스트와 배포까지 이어집니다. 본인용 스킬이든, 팀용 스킬이든, 커뮤니티용 스킬이든, 실전에서 검증된 패턴과 실제 사례를 접하게 됩니다.

이 가이드에서 배우게 될 것

  • 스킬 구조의 기술 요구 사항과 모범 사례
  • 단독형 스킬과 MCP 강화형 워크플로의 패턴
  • 여러 유즈 케이스에서 검증된 패턴
  • 스킬을 테스트·개선·배포하는 방법

이 가이드가 맞는 대상

  • Claude가 특정 워크플로를 일관되게 따르길 원하는 개발자
  • Claude가 특정 워크플로를 따르길 원하는 파워 유저
  • 조직 차원에서 Claude 사용 방식을 표준화하려는 팀

가이드를 읽는 두 가지 경로

단독형 스킬을 만든다면 기초, 계획과 설계, 카테고리 1~2에 집중하세요. 이미 있는 MCP 연동을 강화하는 중이라면 “Skills + MCP” 절과 카테고리 3을 참고하면 됩니다. 두 경로 모두 같은 기술 요구 사항을 공유하므로, 상황에 맞는 부분을 골라 읽을 수 있습니다.

이 가이드를 끝마쳤을 때 얻게 될 것

한 번의 작업 세션 안에서 동작하는 스킬을 만들 수 있습니다. skill-creator 스킬로 첫 스킬을 구축하고 테스트하는 데 약 15~30분이 걸립니다.

시작합시다.

Chapter 1

기초

스킬이란 무엇인가?

스킬은 다음 파일들이 들어 있는 폴더입니다.

  • SKILL.md (필수): Markdown으로 작성된 지시문 + YAML frontmatter
  • scripts/ (선택): 실행 가능한 코드 (Python, Bash 등)
  • references/ (선택): 필요할 때 불러오는 문서
  • assets/ (선택): 산출물에 쓰이는 템플릿, 폰트, 아이콘 등

핵심 설계 원칙

프로그레시브 디스클로저 (progressive disclosure)

스킬은 3단계 시스템을 사용합니다.

  • 1단계 (YAML frontmatter): 항상 Claude의 시스템 프롬프트에 로드됩니다. 각 스킬을 언제 사용할지 판단할 만큼의 정보만 담고, 본문 전체는 아직 컨텍스트에 올라오지 않습니다.
  • 2단계 (SKILL.md 본문): Claude가 현재 작업과 관련된 스킬이라고 판단하면 로드됩니다. 전체 지시문과 안내가 여기에 담깁니다.
  • 3단계 (링크된 파일): 스킬 디렉토리 안에 번들된 추가 파일들로, Claude가 필요할 때 선택적으로 탐색합니다.

이 점진적 공개 방식은 전문성을 유지하면서 토큰 사용을 최소화합니다.

컴포저빌리티 (composability)

Claude는 여러 스킬을 동시에 로드할 수 있습니다. 스킬은 자신이 유일한 능력이라고 가정하지 말고 다른 스킬들과 나란히 동작해야 합니다.

이식성 (portability)

스킬은 Claude.ai, Claude Code, API에서 동일하게 작동합니다. 한 번 만들어두면 수정 없이 모든 환경에서 돌아갑니다. 단, 스킬이 요구하는 의존성을 해당 환경이 지원해야 합니다.

MCP 빌더를 위한 이야기: Skills + Connectors

💡 Tip

MCP 없이 단독형 스킬을 만든다면 이 부분은 건너뛰고 계획과 설계로 바로 넘어가도 됩니다. 나중에 다시 돌아와 읽어도 됩니다.

이미 동작하는 MCP 서버가 있다면 어려운 부분은 끝난 셈입니다. 스킬은 그 위에 얹는 지식 계층으로, 이미 알고 있는 워크플로와 베스트 프랙티스를 포착해 Claude가 일관되게 적용하도록 합니다.

주방의 비유

MCP는 전문 주방을 제공합니다: 도구, 재료, 장비에 대한 접근권입니다.

스킬은 레시피를 제공합니다: 결과물을 만드는 단계별 지시문입니다.

둘이 함께하면 사용자는 매 단계를 스스로 궁리하지 않고도 복잡한 작업을 완수할 수 있습니다.

둘이 어떻게 맞물려 돌아가는가

MCP (연결성) Skills (지식)
Claude를 서비스(Notion, Asana, Linear 등)에 연결 Claude에게 그 서비스를 잘 쓰는 법을 가르침
실시간 데이터 접근과 도구 호출을 제공 워크플로와 베스트 프랙티스를 포착
Claude가 무엇을 할 수 있는지 Claude가 어떻게 해야 하는지

이것이 MCP 사용자에게 왜 중요한가

스킬이 없으면:

  • 사용자가 MCP를 연결하고도 다음에 무엇을 할지 모릅니다
  • “이 연동으로 X를 어떻게 하나요?” 같은 지원 티켓이 쌓입니다
  • 매 대화가 백지 상태에서 시작합니다
  • 사용자마다 프롬프트가 달라 결과가 일관되지 않습니다
  • 실제 문제는 워크플로 가이드 부재인데 사용자는 커넥터를 탓합니다

스킬이 있으면:

  • 필요한 순간에 미리 만들어둔 워크플로가 자동으로 활성화됩니다
  • 일관되고 신뢰할 수 있는 도구 사용이 이뤄집니다
  • 모든 상호작용에 베스트 프랙티스가 내장돼 있습니다
  • 연동의 학습 곡선이 낮아집니다
Chapter 2

계획과 설계

유즈 케이스에서 출발하라

코드를 한 줄이라도 쓰기 전에, 이 스킬로 해결할 2~3개의 구체적인 유즈 케이스부터 식별하세요.

잘 정의된 유즈 케이스의 예:

유즈 케이스: 프로젝트 스프린트 계획
트리거: 사용자가 "이번 스프린트 계획 좀 도와줘" 또는 "스프린트
태스크 만들어줘"라고 말함
단계:
1. Linear에서 현재 프로젝트 상태를 가져온다 (MCP 경유)
2. 팀의 속도(velocity)와 캐파를 분석한다
3. 태스크 우선순위를 제안한다
4. Linear에 적절한 라벨과 추정치를 붙여 태스크를 생성한다
결과: 태스크가 모두 생성된 완성된 스프린트

스스로에게 던져볼 질문:

  • 사용자가 달성하려는 것이 무엇인가?
  • 어떤 멀티 스텝 워크플로가 필요한가?
  • 어떤 도구가 필요한가? (내장 도구 / MCP)
  • 어떤 도메인 지식이나 베스트 프랙티스를 내장해야 하는가?

흔한 스킬 유즈 케이스 카테고리

Anthropic이 관찰한 바에 따르면 공통적으로 나타나는 세 가지 유즈 케이스가 있습니다.

카테고리 1: 문서와 자산 생성 (Document & Asset Creation)

용도: 문서, 프레젠테이션, 앱, 디자인, 코드 등 일관된 고품질 산출물을 만드는 작업에 사용됩니다.

실제 예시: frontend-design 스킬 (docx, pptx, xlsx, ppt용 스킬도 참고하세요)

“높은 디자인 품질을 갖춘, 차별화된 프로덕션급 프런트엔드 인터페이스를 만듭니다. 웹 컴포넌트, 페이지, 그래픽, 포스터, 애플리케이션을 구축할 때 사용하세요.”

핵심 기법:

  • 스타일 가이드와 브랜드 기준을 내장
  • 일관된 산출물을 위한 템플릿 구조
  • 완료 전 품질 체크리스트
  • 외부 도구 불필요. Claude의 내장 기능만으로 처리

카테고리 2: 워크플로 자동화 (Workflow Automation)

용도: 여러 MCP 서버를 가로지르는 조정을 포함해, 일관된 방법론이 필요한 멀티 스텝 프로세스에 사용됩니다.

실제 예시: skill-creator 스킬

“새 스킬을 만들기 위한 대화형 가이드. 유즈 케이스 정의, frontmatter 생성, 지시문 작성, 검증까지 사용자를 단계별로 이끕니다.”

핵심 기법:

  • 검증 게이트가 있는 단계별 워크플로
  • 자주 쓰는 구조에 대한 템플릿
  • 내장된 리뷰 및 개선 제안
  • 반복적 다듬기 루프

카테고리 3: MCP 강화 (MCP Enhancement)

용도: MCP 서버가 제공하는 도구 접근성을 끌어올리는 워크플로 가이드입니다.

실제 예시: Sentry의 sentry-code-review 스킬

“Sentry의 MCP 서버를 통해 에러 모니터링 데이터를 활용해, GitHub Pull Request에서 감지된 버그를 자동으로 분석하고 고칩니다.”

핵심 기법:

  • 여러 MCP 호출을 순서에 맞게 조율
  • 도메인 전문성을 내장
  • 매번 지정해야 할 컨텍스트를 미리 제공
  • 흔한 MCP 이슈에 대한 에러 처리

성공 기준을 정의하라

스킬이 제대로 동작하는지 어떻게 알 수 있는가?

이 기준들은 정밀한 임계치라기보다 “지향하는 목표”에 가깝습니다. 엄밀함을 추구하되, 어느 정도 “감(感) 기반” 평가가 개입된다는 점도 받아들이세요. Anthropic도 더 견고한 측정 가이드와 도구를 개발하는 중입니다.

정량 지표

  • 관련된 쿼리의 90%에서 스킬이 트리거된다
    측정 방법: 스킬을 트리거해야 하는 테스트 쿼리 10~20개를 돌려, 자동으로 로드되는 빈도와 명시적 호출이 필요한 빈도를 기록합니다.
  • X번의 도구 호출 이내에 워크플로를 완료한다
    측정 방법: 같은 작업을 스킬 활성화 상태와 비활성화 상태로 비교해 도구 호출 횟수와 총 토큰 사용량을 셉니다.
  • 워크플로당 API 호출 실패 0건
    측정 방법: 테스트 실행 중 MCP 서버 로그를 모니터링해 재시도율과 에러 코드를 추적합니다.

정성 지표

  • 사용자가 다음 단계를 Claude에게 지시할 필요가 없다
    평가 방법: 테스트 중 Claude의 방향을 재설정하거나 확인 요청에 답해야 하는 빈도를 기록합니다. 베타 사용자에게도 피드백을 받으세요.
  • 사용자 수정 없이 워크플로가 완료된다
    평가 방법: 같은 요청을 3~5번 돌려 구조적 일관성과 품질을 비교합니다.
  • 세션이 바뀌어도 결과가 일관된다
    평가 방법: 신규 사용자가 최소한의 안내만 받고 첫 시도에 작업을 완수할 수 있는지 확인합니다.

기술 요구 사항

파일 구조

your-skill-name/
├── SKILL.md              # 필수 — 스킬의 메인 파일
├── scripts/              # 선택 — 실행 가능한 코드
│   ├── process_data.py   # 예시
│   └── validate.sh       # 예시
├── references/           # 선택 — 문서
│   ├── api-guide.md      # 예시
│   └── examples/         # 예시
└── assets/               # 선택 — 템플릿 등
    └── report-template.md # 예시

반드시 지켜야 할 규칙

SKILL.md 이름 규칙:

  • 정확히 SKILL.md여야 합니다 (대소문자 구분)
  • 변형은 허용되지 않습니다 (SKILL.MD, skill.md 등)

스킬 폴더 이름 규칙:

  • kebab-case 사용: notion-project-setup ✅
  • 공백 금지: Notion Project Setup ❌
  • 언더스코어 금지: notion_project_setup ❌
  • 대문자 금지: NotionProjectSetup ❌

README.md 금지:

  • 스킬 폴더 안에 README.md를 두지 마세요
  • 모든 문서는 SKILL.md 또는 references/에 들어갑니다
  • 참고: GitHub으로 배포할 때는 사람 방문자용 레포 레벨 README는 여전히 필요합니다. 배포와 공유 장을 참고하세요.

YAML frontmatter: 가장 중요한 부분

YAML frontmatter는 Claude가 스킬을 로드할지 말지 결정하는 기준입니다. 여기를 제대로 갖추는 것이 무엇보다 중요합니다.

최소 필수 포맷

---
name: your-skill-name
description: 무엇을 하는 스킬인지. 사용자가 [구체적인 문구]를 요청할
때 사용하세요.
---

시작하는 데 필요한 건 이게 전부입니다.

필드 요구 사항

name (필수):

  • kebab-case만 허용 (소문자, 숫자, 하이픈)
  • 공백·대문자 금지
  • 폴더 이름과 일치해야 함
  • 최대 64자 (2026-04 갱신 — 공식 문서 명시)
  • 예약어 금지: “anthropic”, “claude”를 이름에 사용할 수 없습니다
  • XML 태그 금지

description (필수):

  • 반드시 다음 두 가지가 들어가야 합니다:
    • 스킬이 하는 일 (What)
    • 언제 써야 하는지, 즉 트리거 조건 (When)
  • 1024자 이내
  • XML 태그 금지 (< >)
  • 사용자가 실제로 말할 법한 구체적 표현 포함
  • 관련 파일 타입이 있다면 언급

license (선택):

  • 스킬을 오픈 소스로 공개한다면 지정
  • 자주 쓰이는 값: MIT, Apache-2.0

compatibility (선택):

  • 1~500자
  • 환경 요구 사항을 나타냄: 예컨대 대상 제품, 필수 시스템 패키지, 네트워크 접근 필요 여부 등

metadata (선택):

  • 임의의 key-value 쌍
  • 권장: author, version, mcp-server
  • 예시: 
    metadata:
  author: ProjectHub
  version: 1.0.0
  mcp-server: projecthub

보안 관련 제약

frontmatter에서 금지된 것:

  • XML 꺽쇠 괄호 (< >)
  • 이름에 “claude” 또는 “anthropic”을 포함하는 스킬 (예약어)

이유: frontmatter는 Claude의 시스템 프롬프트에 그대로 들어가므로, 악의적인 내용이 들어가면 지시문 인젝션이 발생할 수 있습니다.

테스트와 반복

스킬은 필요에 따라 여러 수준의 엄밀함으로 테스트할 수 있습니다.

  • Claude.ai에서 수동 테스트: 쿼리를 직접 돌리며 동작을 관찰합니다. 빠른 반복이 가능하고 별도 셋업이 필요 없습니다.
  • Claude Code에서 스크립트 기반 테스트: 변경 사이의 회귀를 잡기 위해 반복 가능한 검증 케이스를 자동화합니다.
  • Skills API를 통한 프로그래매틱 테스트: 정의된 테스트 세트에 대해 체계적으로 돌릴 수 있는 평가 스위트를 구축합니다.

품질 요구와 스킬의 노출 범위에 맞는 접근을 고르세요. 작은 팀이 내부용으로 쓰는 스킬과, 수천 명 엔터프라이즈 사용자에게 배포된 스킬의 테스트 기준은 다릅니다.

Pro Tip

확장 전에 하나의 과제로 반복하라. Anthropic이 관찰한 바에 따르면, 숙련된 스킬 제작자들은 Claude가 성공할 때까지 단 하나의 까다로운 과제에서 반복한 뒤, 그 “이기는 접근법”을 추출해 스킬로 만듭니다. 이는 Claude의 in-context 학습을 활용하는 방식이며, 광범위한 테스트보다 빠른 신호를 줍니다. 동작하는 토대를 갖춘 뒤, 커버리지를 위해 여러 테스트 케이스로 확장하세요.

권장 테스트 접근법

초기 경험에 비추어 보면 스킬 테스트는 보통 세 가지 영역을 다룹니다.

1. 트리거 테스트

목표: 스킬이 적절한 순간에 로드되도록 보장하는 것.

테스트 케이스:

  • ✅ 명백한 과제에서 트리거됨
  • ✅ 바꿔 말한 요청에서도 트리거됨
  • ✕ 관련 없는 주제에서는 트리거되지 않음

테스트 스위트 예시:

트리거되어야 하는 경우:
- "새 ProjectHub 워크스페이스 세팅 좀 도와줘"
- "ProjectHub에 프로젝트 하나 만들어야 해"
- "Q4 계획용 ProjectHub 프로젝트 초기화해줘"

트리거되면 안 되는 경우:
- "샌프란시스코 날씨 어때?"
- "Python 코드 작성 좀 도와줘"
- "스프레드시트 만들어줘" (ProjectHub 스킬이 시트를 다루지
않는 한)

2. 기능 테스트

목표: 스킬이 올바른 산출물을 만드는지 검증하는 것.

테스트 케이스:

  • 유효한 산출물이 생성됨
  • API 호출이 성공함
  • 에러 처리가 동작함
  • 엣지 케이스가 커버됨

예시:

테스트: 태스크 5개가 포함된 프로젝트 생성
전제: 프로젝트 이름 "Q4 Planning", 태스크 설명 5개
실행: 스킬이 워크플로를 실행
결과:
  - ProjectHub에 프로젝트가 생성됨
  - 올바른 속성을 가진 태스크 5개가 생성됨
  - 모든 태스크가 프로젝트에 연결됨
  - API 에러 없음

성공 기준을 정의하라에서 세운 지표를 활용하세요. 비교 예시는 다음과 같습니다.

skill-creator 스킬 사용하기

skill-creator 스킬은 Claude.ai의 플러그인 디렉토리에서 사용할 수 있고 Claude Code용 으로도 다운로드할 수 있습니다. 이 스킬은 스킬을 만들고 반복하는 작업을 돕습니다. MCP 서버가 있고 상위 2~3개 워크플로를 알고 있다면, 동작하는 스킬을 한 번의 세션, 보통 15~30분 안에 만들고 테스트할 수 있습니다.

스킬 만들기:

  • 자연어 설명에서 스킬을 생성
  • frontmatter를 갖춘 정상 형식의 SKILL.md 생성
  • 트리거 구문과 구조를 제안

스킬 검토하기:

  • 흔한 이슈(모호한 description, 빠진 트리거, 구조 문제)를 지적
  • 과잉/부족 트리거 위험을 식별
  • 스킬의 선언된 목적을 근거로 테스트 케이스를 제안

반복적 개선:

  • 스킬을 사용하면서 발견한 엣지 케이스나 실패 사례를 다시 skill-creator에 들고 가세요
  • 예: “이 대화에서 드러난 이슈와 해결책을 참고해, 이 스킬이 [특정 엣지 케이스]를 처리하는 방식을 개선해주세요.”

사용 방법:

"skill-creator 스킬을 사용해서
[당신의 유즈 케이스]를 위한 스킬을 만드는 걸 도와줘"

참고: skill-creator는 스킬을 설계하고 다듬는 작업을 돕지만, 자동화된 테스트 스위트를 실행하거나 정량 평가 결과를 만들지는 않습니다.

피드백에 기반한 반복

스킬은 살아 있는 문서입니다. 아래 신호에 따라 반복할 계획을 세우세요.

과소 트리거(undertriggering) 신호:

  • 스킬이 로드돼야 할 때 로드되지 않음
  • 사용자가 수동으로 스킬을 켜고 있음
  • “언제 이 스킬을 쓰느냐”는 지원 질문이 들어옴
해결

description에 디테일과 뉘앙스를 더하세요. 특히 기술 용어에 대한 키워드를 추가하면 효과가 있습니다.

과잉 트리거(overtriggering) 신호:

  • 관련 없는 쿼리에서 스킬이 로드됨
  • 사용자가 스킬을 끄고 있음
  • 스킬의 목적에 대한 혼동
해결

네거티브 트리거를 추가하고, description을 더 구체적으로 만드세요.

실행 이슈:

  • 결과가 일관되지 않음
  • API 호출 실패
  • 사용자 수정이 필요함
해결

지시문을 개선하고, 에러 처리를 추가하세요.

Claude Code에서는 별도 업로드가 필요 없습니다. 스킬을 ~/.claude/skills/(개인) 또는 .claude/skills/(프로젝트) 디렉토리에 배치하면 Claude Code가 자동으로 발견해 사용합니다.

플랜 요구 사항

  • 커스텀 스킬 업로드는 Pro, Max, Team, Enterprise 플랜에서 사용할 수 있습니다. (2026-04 갱신 — PDF에 없던 정보)
  • Free 플랜은 미리 만들어진 Anthropic 관리 스킬(pptx, xlsx, docx, pdf)만 간접적으로 사용 가능합니다.
  • Enterprise 플랜에서는 관리자가 Organization settings > Capabilities에서 Code execution / file creation을 활성화해야 합니다.

조직 레벨의 배포 — 정정

PDF 주장 ↔ 현재 상태

원본 PDF는 “관리자가 워크스페이스 전역으로 스킬을 배포할 수 있습니다 (2025-12-18 출시)”라고 적었지만, 2026년 4월 기준 공식 문서는 정반대의 내용을 명시합니다: “Claude.ai does not currently support centralized admin management or org-wide distribution of custom Skills.” 즉 Claude.ai에서는 커스텀 스킬의 중앙 관리·조직 전역 배포가 지원되지 않으며, 각 팀원이 개별적으로 업로드해야 합니다.

서피스별 공유 모델 (2026-04 기준):

  • Claude.ai: 개인 사용자 단위. 팀원이 각자 업로드해야 함. 관리자 중앙 관리 불가.
  • Claude API: 워크스페이스 전역. 업로드한 스킬을 같은 워크스페이스 구성원이 공유합니다.
  • Claude Code: 개인(~/.claude/skills/) 또는 프로젝트(.claude/skills/) 디렉토리. Claude Code Plugins를 통해 공유도 가능합니다.

크로스 서피스 주의 — 자동 싱크 없음

(2026-04 갱신 — PDF에 없던 중요한 사실) 커스텀 스킬은 서피스 간 자동으로 동기화되지 않습니다. 즉:

  • Claude.ai에 올린 스킬은 API에서 쓸 수 없고, 그 반대도 마찬가지입니다.
  • API에 올린 스킬은 Claude.ai에 표시되지 않습니다.
  • Claude Code의 스킬은 파일 시스템 기반이라 Claude.ai/API와 별개입니다.

여러 서피스에서 같은 스킬을 쓰고 싶다면 각 서피스에 개별적으로 업로드·배치 해야 합니다.

런타임 환경 제약 — 서피스별로 다름

(2026-04 갱신 — PDF에 없던 정보) 스킬이 실행되는 환경은 서피스별로 다릅니다:

  • Claude.ai: 네트워크 접근은 사용자/관리자 설정에 따라 전체·부분·없음으로 가변적입니다.
  • Claude API: 외부 네트워크 접근 없음, 런타임 패키지 설치 불가, 사전 설치된 패키지만 사용할 수 있습니다. 상세 목록은 Code Execution Tool 문서를 참고하세요.
  • Claude Code: 사용자 컴퓨터와 동일한 수준의 전체 네트워크 접근. 단, 전역 패키지 설치는 권장되지 않습니다.

열린 표준 (open standard)

Anthropic은 Agent Skills를 열린 표준으로 공개했습니다. MCP가 그랬듯 스킬 역시 도구와 플랫폼을 가로질러 이식 가능해야 한다는 판단에서입니다. 같은 스킬이 Claude든 다른 AI 플랫폼이든 동일하게 동작해야 합니다. 다만 일부 스킬은 특정 플랫폼의 기능을 최대한 활용 하도록 설계되기도 하며, 그 경우 스킬의 compatibility 필드에 이를 명시할 수 있습니다. Anthropic은 이 표준을 두고 에코시스템 구성원들과 협업해 왔고, 초기 반응에 대한 기대가 큽니다.

  • Claude Console을 통한 버전 관리

필수 베타 헤더 (2026-04 갱신)

API에서 스킬을 사용하려면 여전히 베타 헤더 3개를 요청에 포함해야 합니다. PDF는 “Code Execution Tool(베타)이 필요하다”는 한 줄만 언급하지만, 실제로는 다음이 필요합니다:

  • code-execution-2025-08-25 — 스킬이 실행되는 코드 실행 컨테이너
  • skills-2025-10-02 — Skills 기능 자체 활성화
  • files-api-2025-04-14 — 컨테이너와 파일을 주고받는 Files API

요청 형태

스킬은 Messages API의 container 파라미터 안에 배열로 지정합니다.

{
  "container": {
    "skills": [
      {
        "type": "anthropic",
        "skill_id": "pptx",
        "version": "latest"
      }
    ]
  },
  "tools": [
    {
      "type": "code_execution_20250825",
      "name": "code_execution"
    }
  ]
}
  • type: "anthropic" (사전 구축 스킬) 또는 "custom" (사용자 업로드)
  • skill_id: Anthropic 관리 스킬은 pptx, xlsx, docx, pdf 같은 문자열. 커스텀 스킬은 skill_01AbCdEf... 형태의 ID
  • version: Anthropic 스킬은 20251013 같은 날짜형, 커스텀 스킬은 에폭 타임스탬프(예: 1759178010641129) 또는 "latest"
  • 요청당 최대 8개의 스킬을 포함할 수 있습니다. (2026-04 갱신 — PDF에 없던 정보)

패턴과 문제 해결

아래 패턴들은 얼리 어답터와 내부 팀이 만든 스킬에서 드러난 것들입니다. 잘 동작함이 확인된 접근법의 모음이지, 무조건 따라야 하는 템플릿은 아닙니다.

접근 방식 고르기: 문제 우선이냐, 도구 우선이냐

Home Depot에 비유해볼 수 있습니다. “주방 찬장을 고쳐야 해요” 같은 문제를 들고 가게에 들어가면 직원이 적절한 도구를 가리키며 알려줍니다. 반대로 새 드릴을 골라 들고는 이걸 구체적인 작업에 어떻게 쓸지 물어볼 수도 있습니다.

스킬도 마찬가지로 동작합니다.

  • 문제 우선(problem-first): “프로젝트 워크스페이스를 세팅해야 해” → 스킬이 적절한 순서로 올바른 MCP 호출을 조율합니다. 사용자는 결과만 묘사하고, 스킬이 도구를 다룹니다.
  • 도구 우선(tool-first): “Notion MCP를 연결했어” → 스킬이 Claude에게 최적의 워크플로와 베스트 프랙티스를 가르칩니다. 사용자는 접근권을 가지고 있고, 스킬이 전문성을 제공합니다.

대부분의 스킬은 한쪽으로 기울어집니다. 어떤 구도가 유즈 케이스에 맞는지 파악하면 아래의 패턴 중 무엇을 고를지 결정하는 데 도움이 됩니다.

패턴 1: 순차 워크플로 오케스트레이션

언제 쓰는가: 사용자가 특정 순서대로 진행되는 멀티 스텝 프로세스를 필요로 할 때.

예시 구조:

## Workflow: 신규 고객 온보딩

### Step 1: 계정 생성
MCP 도구 호출: `create_customer`
파라미터: name, email, company

### Step 2: 결제 수단 설정
MCP 도구 호출: `setup_payment_method`
대기 대상: 결제 수단 검증

### Step 3: 구독 생성
MCP 도구 호출: `create_subscription`
파라미터: plan_id, customer_id (Step 1에서 획득)

### Step 4: 환영 이메일 발송
MCP 도구 호출: `send_email`
템플릿: welcome_email_template

주요 기법:

  • 명시적인 단계 순서
  • 단계 간 의존성
  • 각 단계별 검증
  • 실패 시 롤백 지시문

패턴 2: 여러 MCP의 협업 (Multi-MCP coordination)

언제 쓰는가: 워크플로가 여러 서비스에 걸쳐 있을 때.

예시: 디자인에서 개발로 넘기는 핸드오프

### Phase 1: 디자인 내보내기 (Figma MCP)
1. Figma에서 디자인 에셋을 export
2. 디자인 스펙 생성
3. 에셋 매니페스트 생성

### Phase 2: 에셋 저장 (Drive MCP)
1. Drive에 프로젝트 폴더 생성
2. 모든 에셋 업로드
3. 공유 가능한 링크 생성

### Phase 3: 태스크 생성 (Linear MCP)
1. 개발 태스크 생성
2. 태스크에 에셋 링크 첨부
3. 엔지니어링 팀에 배정

### Phase 4: 알림 (Slack MCP)
1. #engineering 채널에 핸드오프 요약 게시
2. 에셋 링크와 태스크 참조 포함

주요 기법:

  • 명확한 단계(phase) 분리
  • MCP 간 데이터 전달
  • 다음 단계로 넘어가기 전 검증
  • 중앙 집중식 에러 처리

패턴 3: 반복적 다듬기 (Iterative refinement)

언제 쓰는가: 반복으로 산출물 품질이 올라가는 작업일 때.

예시: 리포트 생성

## 반복적 리포트 생성

### 초안 작성
1. MCP 경유로 데이터 수집
2. 초안 리포트 생성
3. 임시 파일에 저장

### 품질 체크
1. 검증 스크립트 실행: `scripts/check_report.py`
2. 이슈 식별:
   - 누락된 섹션
   - 일관되지 않은 서식
   - 데이터 검증 에러

### 다듬기 루프
1. 식별된 각 이슈를 해결
2. 영향받은 섹션을 재생성
3. 재검증
4. 품질 임계치를 만족할 때까지 반복

### 최종화
1. 최종 서식 적용
2. 요약 생성
3. 최종 버전 저장

주요 기법:

  • 명시적인 품질 기준
  • 반복적인 개선
  • 검증 스크립트
  • 언제 반복을 멈출지 아는 것

패턴 4: 컨텍스트 인지 도구 선택

언제 쓰는가: 같은 결과를 목표로 하지만 맥락에 따라 쓰는 도구가 달라질 때.

## 스마트 파일 저장소

### 결정 트리
1. 파일 타입과 크기 확인

   - 협업 문서: Notion/Docs MCP 사용
   - 코드 파일: GitHub MCP 사용
   - 임시 파일: 로컬 스토리지 사용

### 저장 실행
결정에 따라:
- 적절한 MCP 도구 호출
- 서비스별 메타데이터 적용
- 액세스 링크 생성

### 사용자에게 맥락 제공
해당 저장 위치를 선택한 이유 설명

주요 기법:

  • 명확한 결정 기준
  • 대체(fallback) 옵션
  • 선택 이유에 대한 투명성

패턴 5: 도메인 특화 지능

언제 쓰는가: 스킬이 도구 접근 이상의 전문 지식을 더할 때.

## 컴플라이언스를 포함한 결제 처리

### 처리 전 (컴플라이언스 체크)
1. MCP 경유로 트랜잭션 상세 조회
2. 컴플라이언스 규칙 적용:
   - 제재 리스트 확인
   - 관할 구역 허용 여부 검증
   - 리스크 레벨 평가
3. 컴플라이언스 결정 기록

### 처리
IF 컴플라이언스 통과:
  - 결제 처리 MCP 도구 호출
  - 적절한 사기 탐지 체크 적용
  - 트랜잭션 처리
ELSE:
  - 검토 대상으로 플래깅
  - 컴플라이언스 케이스 생성

### 감사 이력
- 모든 컴플라이언스 체크 로깅
- 처리 결정 기록
- 감사 리포트 생성

주요 기법:

  • 로직 안에 내장된 도메인 전문성
  • 액션 전에 컴플라이언스
  • 포괄적인 문서화
  • 명확한 거버넌스

문제 해결 (Troubleshooting)

스킬이 업로드되지 않는다

에러: “Could not find SKILL.md in uploaded folder”

원인: 파일 이름이 정확히 SKILL.md가 아님.

해결
  • SKILL.md로 이름 변경 (대소문자 구분)
  • 확인: ls -la 했을 때 SKILL.md가 보여야 합니다

에러: “Invalid frontmatter”

원인: YAML 포매팅 이슈.

자주 나오는 실수:

# 잘못됨 — 구분자 누락
name: my-skill
description: Does things

# 잘못됨 — 닫히지 않은 따옴표
name: my-skill
description: "Does things

# 올바름
---
name: my-skill
description: Does things
---

에러: “Invalid skill name”

원인: 이름에 공백이나 대문자가 있음.

# 잘못됨
name: My Cool Skill

# 올바름
name: my-cool-skill

스킬이 트리거되지 않는다

증상: 스킬이 자동으로 로드되지 않음.

해결: description 필드를 수정하세요. 좋은/나쁜 예시는 앞의 “description 필드”를 참고하세요.

빠른 체크리스트:

  • 너무 모호하지 않나요? (“Helps with projects”는 동작하지 않습니다)
  • 사용자가 실제로 말할 법한 트리거 구문이 포함돼 있나요?
  • 해당하는 경우 관련 파일 타입을 언급했나요?

디버깅 팁: Claude에게 “When would you use the [skill name] skill?”이라고 물어보세요. Claude가 description을 그대로 되돌려줍니다. 부족한 부분을 토대로 조정하면 됩니다.

스킬이 너무 자주 트리거된다

증상: 관련 없는 쿼리에서도 스킬이 로드됨.

해결책:

  1. 네거티브 트리거 추가 
    description: CSV 파일을 위한 고급 데이터 분석. 통계 모델링,
회귀, 클러스터링에 사용. 단순 데이터 탐색에는 사용하지 말 것
(대신 data-viz 스킬 사용).
  2. 더 구체적으로 쓰기 
    # 너무 광범위
description: 문서를 처리합니다

# 더 구체적
description: 계약 검토를 위한 PDF 법률 문서를 처리합니다
  3. 범위(scope)를 분명히 하기 
    description: 이커머스를 위한 PayFlow 결제 처리. 온라인 결제
워크플로에 한정해 사용하며, 일반적인 금융 관련 질의에는
사용하지 않습니다.

MCP 연결 이슈

증상: 스킬은 로드되지만 MCP 호출이 실패함.

체크리스트:

  1. MCP 서버가 연결돼 있는지 확인
    • Claude.ai: Settings > Extensions > [Your Service]
    • 상태가 “Connected”로 표시돼야 함
  2. 인증 확인
    • API 키가 유효하고 만료되지 않음
    • 적절한 권한/스코프가 부여돼 있음
    • OAuth 토큰이 갱신돼 있음
  3. MCP를 독립적으로 테스트
    • Claude에게 스킬 없이 바로 MCP를 호출해달라고 요청
    • “Use [Service] MCP to fetch my projects”
    • 이것도 실패하면 문제는 MCP이지 스킬이 아닙니다
  4. 툴 이름 확인
    • 스킬이 올바른 MCP 툴 이름을 참조하는지
    • MCP 서버 문서 확인
    • 툴 이름은 대소문자를 구분합니다

지시문이 지켜지지 않는다

증상: 스킬은 로드됐지만 Claude가 지시문을 따르지 않음.

흔한 원인:

  1. 지시문이 너무 장황함
    • 지시문을 간결하게 유지
    • 글머리표와 번호 목록 사용
    • 상세 레퍼런스는 별도 파일로 이동
  2. 지시문이 묻혀 있음
    • 중요한 지시문은 상단에 배치
    • ## Important 또는 ## Critical 같은 헤더 사용
    • 필요하면 핵심 내용을 반복
  3. 모호한 언어 
    # 나쁜 예
제대로 검증하세요

# 좋은 예
CRITICAL: create_project를 호출하기 전에 다음을 확인:
- 프로젝트 이름이 비어 있지 않음
- 팀 멤버가 최소 한 명 이상 배정됨
- 시작일이 과거가 아님

    고급 기법: 중요한 검증에서는 언어로 된 지시문에 의존하는 대신 스크립트를 번들해 프로그래매틱하게 체크하는 방안을 고려하세요. 코드는 결정론적이지만 언어 해석은 그렇지 않습니다. 이 패턴의 예시는 Office skills를 참고하세요.

  4. 모델의 “게으름”
    명시적인 격려를 추가하세요. 
    ## Performance Notes
- 충분히 시간을 들여 꼼꼼히 수행할 것
- 속도보다 품질이 우선
- 검증 단계를 건너뛰지 말 것

    참고: 이런 문장은 SKILL.md보다 사용자 프롬프트에 넣을 때 더 효과적 입니다.

컨텍스트가 너무 큰 경우의 이슈

증상: 스킬이 느려지거나 응답 품질이 떨어짐.

원인:

  • 스킬 콘텐츠가 너무 큼
  • 동시에 너무 많은 스킬이 활성화돼 있음
  • 프로그레시브 디스클로저가 아니라 모든 콘텐츠가 한꺼번에 로드됨

해결책:

  1. SKILL.md 크기 최적화
    • 상세 문서는 references/로 이동
    • 인라인 대신 references/로 링크
    • SKILL.md는 5,000 단어 미만으로 유지
  2. 활성화된 스킬 줄이기
    • 동시에 20~50개가 넘는 스킬이 켜져 있는지 점검
    • 선택적 활성화를 권장
    • 관련 있는 기능은 “스킬 팩(skill pack)”으로 묶는 것을 고려

부록 A. 빠른 체크리스트

이 체크리스트로 업로드 전·후에 스킬을 검증하세요. 빠른 출발이 필요하다면 skill-creator 스킬로 초안을 만든 뒤 이 목록을 훑어 빠뜨린 것이 없는지 확인 하세요.

시작하기 전에

  • ☐ 구체적인 2~3개의 유즈 케이스를 식별했다
  • ☐ 사용할 도구를 식별했다 (내장 / MCP)
  • ☐ 이 가이드와 예시 스킬을 검토했다
  • ☐ 폴더 구조를 계획했다

개발 중에

  • ☐ 폴더 이름이 kebab-case다
  • ☐ SKILL.md 파일이 존재한다 (정확한 철자)
  • ☐ YAML frontmatter에 --- 구분자가 있다
  • ☐ name 필드: kebab-case, 공백·대문자 없음
  • ☐ description에 “무엇을”과 “언제”가 모두 들어 있다
  • ☐ 어디에도 XML 태그(< >)가 없다
  • ☐ 지시문이 명확하고 실행 가능하다
  • ☐ 에러 처리가 포함돼 있다
  • ☐ 예시가 제공돼 있다
  • ☐ 참고 자료가 명확하게 링크돼 있다

업로드 전에

  • ☐ 명백한 과제에서 트리거가 테스트됐다
  • ☐ 바꿔 말한 요청에서도 트리거가 테스트됐다
  • ☐ 관련 없는 주제에서는 트리거되지 않음을 확인했다
  • ☐ 기능 테스트를 통과했다
  • ☐ 도구 연동이 동작한다 (해당하는 경우)
  • ☐ .zip 파일로 압축했다

업로드 후에

  • ☐ 실제 대화에서 테스트한다
  • ☐ 과소/과잉 트리거를 모니터링한다
  • ☐ 사용자 피드백을 수집한다
  • ☐ description과 지시문을 반복적으로 다듬는다
  • ☐ metadata의 버전을 갱신한다
