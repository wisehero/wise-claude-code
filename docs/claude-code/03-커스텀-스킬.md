# 커스텀 스킬 만들기

> **난이도**: 중급 | **선행 문서**: [Claude Code 시작하기](01-시작하기.md), [CLAUDE.md 작성 가이드](02-CLAUDE-md-작성-가이드.md)
>
> Claude Code의 기능을 확장하는 커스텀 스킬의 구조, 작성법, 트리거 설정을 다룬다.

---

## 1. 스킬이란?

스킬(Skill)은 Claude Code에 새로운 능력을 추가하는 재사용 가능한 지시문 묶음이다. 특정 작업을 반복할 때마다 긴 프롬프트를 입력하는 대신, 스킬로 정의해두면 짧은 명령 하나로 동일한 작업을 실행할 수 있다.

스킬은 두 가지 방식으로 호출된다.

첫째, `/skill-name` 형태의 슬래시 명령어로 직접 호출한다. 사용자가 `/spec-writer`라고 입력하면 해당 스킬이 즉시 실행된다.

둘째, Claude가 대화 맥락을 보고 자동으로 감지하여 호출한다. "요구사항 명세서 작성해줘"라고 입력하면 Claude가 `spec-writer` 스킬을 자동으로 선택한다. 이 자동 감지 동작은 frontmatter의 `description` 필드가 결정한다.

스킬은 단순한 템플릿이 아니다. 도구 사용 권한, 모델 선택, 다단계 워크플로우, 외부 파일 참조까지 포함하는 독립적인 실행 단위다. CLAUDE.md가 프로젝트 전반의 행동 지침을 담는다면, 스킬은 특정 작업 유형에 특화된 절차와 지식을 캡슐화한다. 두 파일은 상호 보완적으로 작동한다.

스킬을 만들면 얻는 이점은 명확하다. 작업 품질이 일정해진다. Claude에게 매번 "SRS는 IEEE 830 기준으로, FR에는 선행 조건과 예외 흐름을 포함하고..."라고 설명하지 않아도 된다. 스킬에 이미 담겨 있다. 팀에서 스킬을 공유하면 여러 사람이 동일한 절차로 동일한 품질의 산출물을 만들 수 있다.

## 2. 스킬 디렉토리 구조

### 설치 위치

스킬은 두 곳에 설치할 수 있다.

- `~/.claude/skills/`: 모든 프로젝트에서 사용하는 글로벌 스킬
- `.claude/skills/`: 현재 프로젝트에서만 사용하는 프로젝트 스킬

프로젝트 스킬은 글로벌 스킬보다 우선 적용된다. 같은 이름의 스킬이 두 곳에 모두 있으면 프로젝트 스킬이 사용된다. 이 우선순위 덕분에 글로벌 스킬을 기반으로 깔아두고, 프로젝트마다 특성에 맞게 오버라이드할 수 있다.

이 프로젝트(`wise-claude-code`)처럼 스킬 자체를 관리하는 레포지토리라면 `skills/` 디렉토리를 루트에 두고 버전 관리한다. Claude Code는 `skills/` 디렉토리도 인식한다.

### 파일 구성

각 스킬은 이름과 같은 디렉토리 안에 구성된다.

```
skill-name/
├── SKILL.md          # 메인 지시문 (필수)
├── references/       # 템플릿, 카탈로그 등 보조 파일
└── examples/         # 예시 결과물
```

`SKILL.md`만 필수다. `references/`와 `examples/`는 스킬의 복잡도에 따라 선택적으로 추가한다. 간단한 스킬은 `SKILL.md` 하나로 완결되고, 복잡한 스킬은 `references/`에 방대한 지식 베이스를 분리하여 관리한다.

### 이 프로젝트의 실제 구조

이 프로젝트(`wise-claude-code`)의 `skills/` 디렉토리는 다음과 같이 구성되어 있다.

```
skills/
├── code-analyzer/
│   ├── SKILL.md
│   └── references/
│       └── report-template.md
├── humanizer/
│   └── SKILL.md
├── humanizer-korean/
│   └── SKILL.md
├── junit-test-writer/
│   ├── SKILL.md
│   └── references/
│       └── conventions.md
├── performance-profiler/
│   ├── SKILL.md
│   └── references/
│       ├── db-patterns.md
│       ├── algorithm-patterns.md
│       ├── memory-patterns.md
│       └── api-patterns.md
├── refactor-advisor/
│   ├── SKILL.md
│   └── references/
├── spec-writer/
│   ├── SKILL.md
│   └── references/
│       ├── srs-template.md
│       └── interview-guide.md
└── study-helper/
    ├── SKILL.md
    └── references/
        └── report-template.md
```

`humanizer`와 `humanizer-korean`은 `SKILL.md` 하나로 완결된다. AI 글쓰기 패턴 카탈로그를 `SKILL.md` 본문에 직접 포함하는 방식을 택했다. 반면 `performance-profiler`는 `references/`에 패턴 카탈로그 4개를 분리하여 관리한다. DB 쿼리, 알고리즘 복잡도, 메모리 사용, API 응답 시간 — 각 영역의 패턴이 방대하기 때문이다.

`study-helper`는 다른 스킬을 의존한다. 내부에서 `/humanizer`와 `/external-context`를 호출하는 복합 스킬이다. 스킬 간 의존 관계를 설계할 때는 `SKILL.md`의 "의존 스킬" 섹션에 명시하는 것이 관례다.

## 3. SKILL.md Frontmatter

`SKILL.md` 파일은 YAML frontmatter로 시작한다. 이 메타데이터가 스킬의 동작 방식을 제어한다.

### 필드 정리

| 필드 | 필수 여부 | 설명 |
|------|-----------|------|
| `name` | 필수 | 스킬 식별자. 디렉토리 이름과 일치시키는 것이 관례 |
| `description` | 권장 | 자동 감지의 핵심. 언제 이 스킬을 써야 하는지, 어떤 요청 표현에 반응하는지를 상세히 기술 |
| `version` | 선택 | 스킬 버전. `1.0.0` 형식의 시맨틱 버전. 공식 스펙이 아닌 프로젝트 자체 컨벤션이지만, 변경 이력 추적에 유용하다 |
| `argument-hint` | 선택 | 슬래시 명령어 자동완성 시 표시되는 인자 힌트 텍스트 |
| `disable-model-invocation` | 선택 | `true`로 설정하면 Claude가 자동 호출하지 않고 수동 슬래시 명령어로만 실행 가능 |
| `user-invocable` | 선택 | `false`로 설정하면 슬래시 명령어로 직접 호출 불가. Claude가 내부적으로만 사용 |
| `allowed-tools` | 선택 | 이 스킬이 사용할 수 있는 도구 목록을 제한 |
| `model` | 선택 | 스킬 실행에 사용할 모델. 기본값은 현재 세션 모델 |
| `effort` | 선택 | 추론 노력 수준. `low`, `normal`, `high` 중 선택 |
| `context` | 선택 | `fork`로 설정하면 현재 대화 맥락 없이 깨끗한 컨텍스트에서 실행 |
| `agent` | 선택 | `true`로 설정하면 도구 사용이 가능한 에이전트 모드로 실행 |
| `paths` | 선택 | 특정 파일 경로 패턴과 매칭될 때만 스킬 활성화 |

### 실전 예시: spec-writer

```yaml
---
name: spec-writer
version: 1.3.0
description: 시스템 요구사항 명세서(SRS)를 대화형 인터뷰를 통해 작성하는 스킬.
  IEEE 830 표준 기반으로 기능 요구사항, 비기능 요구사항(성능/보안/가용성), 인터페이스,
  제약조건을 체계적으로 정리하여 마크다운 파일로 저장한다.
  "요구사항 명세서 작성해줘", "SRS 만들어줘", "시스템 스펙 정리해줘" 같은 요청에 사용.
  "새 프로젝트 시작하는데 요구사항 정리 좀", "기능 명세 문서화해줘" 같은 간접적 요청에도
  반드시 사용한다. 단, 단순 기획서 작성, 회의록 정리, 코드 문서화(JSDoc/Javadoc),
  API 문서 자동생성(Swagger) 요청에는 사용하지 않는다.
---
```

`description`이 길다. 이는 의도적이다. Claude가 "언제 이 스킬을 써야 하는지"를 정확히 판단하려면, 긍정 예시(사용해야 할 표현)와 부정 예시(사용하지 말아야 할 경우) 모두가 필요하다. "시스템 스펙 정리해줘"와 "API 문서 자동생성(Swagger)"은 표면적으로 비슷해 보이지만 전혀 다른 스킬이 처리해야 한다. 부정 예시가 없으면 Claude는 혼동할 수 있다.

### 실전 예시: humanizer

```yaml
---
name: humanizer
description: AI가 생성한 한국어/영어 텍스트에서 AI투(AI 냄새)를 제거하고 자연스러운
  사람 문체로 교정하는 스킬. "AI투 제거해줘", "사람처럼 다듬어줘", "humanize 해줘"
  같은 요청에 사용. "이거 AI가 쓴 티 나는데", "좀 자연스럽게 바꿔줘" 같은 간접적
  요청에도 반드시 사용한다. 단, 단순 맞춤법 교정이나 번역 요청에는 사용하지 않는다.
---
```

`humanizer`에는 `version`이 없다. 아직 버전 관리가 적용되지 않은 초기 스킬이다. 스킬을 개선할 계획이라면 처음부터 `version: 1.0.0`을 추가하는 것이 좋다. 버전 없이 운영하다 뒤늦게 추가하면 "이전에 쓰던 것과 지금이 같은 버전인지" 판단하기 어려워진다.

## 4. 스킬 본문 작성

### 기본 구성

frontmatter 아래에는 마크다운으로 자유롭게 작성한다. Claude는 이 내용을 시스템 프롬프트처럼 해석하여 실행한다. 분량 제한은 없지만, 길어질수록 Claude가 핵심을 놓칠 가능성이 높아진다. 긴 내용은 `references/`로 분리하고 `SKILL.md`는 간결하게 유지하는 것이 원칙이다.

좋은 스킬 본문은 네 가지를 포함한다.

1. **핵심 원칙**: 이 스킬이 왜 이렇게 동작하는지, 판단 기준이 무엇인지. 단순한 규칙 나열보다 "왜"를 설명하면 Claude가 예외 상황에서도 올바른 판단을 내릴 수 있다.
2. **단계별 워크플로우**: Claude가 순서대로 따라야 할 작업 흐름. ASCII 흐름도와 상세 단계 설명을 함께 쓰면 효과적이다.
3. **예시**: 전형적인 사용 시나리오. Claude가 스킬의 의도를 구체적으로 이해하도록 돕는다.
4. **트러블슈팅**: 자주 발생하는 예외 상황과 처리 방법. 모든 경우를 다 다룰 필요는 없고, 실제로 자주 마주치는 상황 3-5개면 충분하다.

### 인자 사용법

스킬은 사용자가 전달한 텍스트를 인자로 받을 수 있다.

| 변수 | 의미 |
|------|------|
| `$ARGUMENTS` | 슬래시 명령어 뒤에 오는 모든 텍스트 |
| `$0` | 스킬 이름 |
| `$1`, `$2`, ... | 공백으로 구분된 개별 인자 |

예를 들어 `/code-analyzer src/auth` 라고 호출하면 `$ARGUMENTS`는 `src/auth`가 되고 `$1`은 `src/auth`가 된다. `/code-analyzer src/auth UserService.java`처럼 여러 인자를 넘기면 `$1`은 `src/auth`, `$2`는 `UserService.java`가 된다.

인자 없이 자동 감지로만 호출되는 스킬이라면 `$ARGUMENTS`를 사용하지 않아도 된다. `spec-writer`나 `humanizer`처럼 호출 맥락 자체가 입력인 경우가 그렇다.

### 동적 컨텍스트 주입

스킬 본문 안에서 느낌표와 백틱을 조합한 문법으로 셸 명령어 실행 결과를 주입할 수 있다.

```
현재 디렉토리 구조: !`ls -la`
현재 날짜: !`date`
Git 브랜치: !`git branch --show-current`
```

스킬이 로드될 때 해당 명령어가 실행되고 결과가 인라인으로 삽입된다. 이를 통해 실행 환경에 따라 동적으로 달라지는 컨텍스트를 스킬에 반영할 수 있다. 날짜가 중요한 스킬(파일명에 날짜를 포함하는 경우)이나 현재 브랜치나 프로젝트 구조를 참고해야 하는 스킬에 유용하다.

### 핵심 원칙 섹션의 중요성

여러 스킬을 보면 공통적으로 "핵심 원칙" 섹션이 가장 먼저 등장한다. `spec-writer`의 핵심 원칙 중 하나는 이렇다.

> 사용자가 모호하게 답변하면 ("적당히", "알아서 해줘", "나중에 정하자") 그냥 넘기지 않는다. 구체적인 선택지를 제시하여 명확한 답변을 유도한다.

이것은 단순한 규칙이 아니라 판단 기준이다. Claude가 실제 인터뷰 중에 모호한 답변을 받았을 때 어떻게 행동해야 하는지 알려준다. "TBD로 기록하고 넘어가야 하나, 아니면 계속 질문해야 하나?" — 핵심 원칙이 이 판단을 내려준다.

`performance-profiler`의 핵심 원칙은 분석 관점을 명확히 한다.

> 추측이 아닌 코드 근거를 기반으로 판단한다. "느릴 수 있다"가 아니라 "N건 조회 시 N+1회 쿼리가 발생한다"처럼 구체적으로 설명한다.

이런 원칙이 없으면 Claude는 일반적인 성능 조언을 나열하는 데 그친다. 원칙이 있어야 스킬이 의도한 방향으로 일관되게 동작한다.

### 단계별 워크플로우 표현

`spec-writer`의 본문 구조를 보면 워크플로우를 어떻게 표현하는지 알 수 있다.

```
## 워크플로우

요청 입력
    ↓
[1단계] 인터뷰: 프로젝트 개요
    ↓
[2단계] 인터뷰: 기능 요구사항
    ↓
[3단계] 인터뷰: 비기능 요구사항 & 제약조건
    ↓
[4단계] 인터뷰: 인터페이스 & 외부 시스템
    ↓
[5단계] SRS 문서 생성 & 파일 저장
    ↓
[6단계] 리뷰 & 보완

## 상세 단계

### 1단계: 프로젝트 개요 인터뷰

시스템의 큰 그림을 파악한다. ...
```

ASCII 흐름도로 전체 구조를 한눈에 보여주고, 각 단계의 상세 지시는 별도 섹션으로 분리한다. Claude는 이 구조를 순서대로 따라간다. 흐름도 없이 상세 단계만 있으면 Claude가 전체 맥락을 파악하는 데 더 많은 처리가 필요하다.

## 5. references/ 디렉토리 활용

### 분리하는 이유

`SKILL.md`에 모든 내용을 넣으면 파일이 지나치게 길어진다. `references/`는 스킬 본문에서 참조할 보조 파일을 분리하는 공간이다. Claude가 스킬을 실행할 때 필요한 시점에 해당 파일을 읽어 참조한다.

`performance-profiler`는 다음처럼 카테고리별로 패턴 카탈로그를 분리했다.

```
references/
├── db-patterns.md        # N+1, 인덱스 누락 등 DB 쿼리 패턴
├── algorithm-patterns.md # O(n²), 비효율적 자료구조 패턴
├── memory-patterns.md    # 메모리 낭비 패턴
└── api-patterns.md       # API 응답 지연 패턴
```

`SKILL.md`에는 "상세 패턴 및 예시는 `references/db-patterns.md` 참조"라고만 쓰고, 실제 내용은 분리된 파일에 둔다. 스킬 본문은 간결하게, 세부 지식은 별도 파일로 관리하는 방식이다. 패턴 카탈로그가 바뀌어도 `SKILL.md`를 건드리지 않아도 된다는 장점도 있다. 단, 이 경우에도 `references/` 파일이 변경되면 버전은 올려야 한다.

`spec-writer`는 두 종류의 보조 파일을 가진다.

```
references/
├── srs-template.md    # SRS 문서의 실제 형식 템플릿
└── interview-guide.md # 도메인별 맞춤 인터뷰 질문 목록
```

`interview-guide.md`에는 도메인별 특화 질문이 담겨 있다. 웹서비스인지, 모바일인지, 백오피스인지에 따라 물어야 할 내용이 다르다. 이 분기 로직을 `SKILL.md`에 모두 담으면 파일이 방대해진다. 별도 파일로 분리하면 `SKILL.md`는 "인터뷰 가이드를 참조하라"는 한 줄로 끝난다.

### 템플릿-지시문 일관성 규칙

이 프로젝트의 `CLAUDE.md`에는 다음 규칙이 명시되어 있다.

> 스킬이 `references/` 디렉토리에 템플릿 파일을 가지고 있을 경우, SKILL.md의 지시문과 템플릿의 형식이 정확히 일치해야 한다.

이 규칙이 필요한 이유는 Claude가 두 파일을 모두 읽고 실행하기 때문이다. `SKILL.md`의 지시문이 "테이블은 4개 컬럼"이라고 하는데 `srs-template.md`가 "5개 컬럼"이면 Claude는 둘 중 어느 것을 따라야 할지 헷갈린다. 결과물이 매번 달라진다. 스킬을 팀에서 쓸 때 산출물의 형식이 사람마다 달라지는 문제가 생긴다.

`spec-writer`의 `SKILL.md`는 FR(기능 요구사항, Functional Requirement) 형식을 인라인으로 명시하고, `references/srs-template.md`도 동일한 형식을 사용한다.

```markdown
#### FR-XXX: [기능 제목]

- **설명**: [기능이 무엇을 하는지]
- **선행 조건**: [이 기능이 실행되기 위한 조건]

**입력 데이터:**

| 필드명 | 타입 | 필수 여부 | 검증 규칙 | 설명 |
|--------|------|-----------|-----------|------|

**기본 흐름:**

1. [동작 1]
2. [동작 2]

**출력 데이터:**

| 필드명 | 타입 | 설명 |
|--------|------|------|

**예외 흐름:**

| 조건 | HTTP 상태 | 에러 코드 | 설명 |
|------|-----------|-----------|------|

- **후행 조건**: [기능 완료 후 시스템 상태]
- **우선순위**: 필수 / 권장 / 선택
```

이 형식은 `SKILL.md`와 `srs-template.md` 양쪽에 동일하게 정의되어 있다. 템플릿을 수정하면 지시문도 반드시 함께 수정해야 한다. 어느 한쪽만 바꾸면 산출물의 통일성이 깨진다. 규칙을 쉽게 기억하는 방법은 하나다 — 두 파일을 동시에 열어 같이 수정하는 것이다.

## 6. 버전 관리

### 시맨틱 버전 규칙

스킬은 내용이 변경될 때마다 버전을 올린다. 이 프로젝트의 `CLAUDE.md`에 정의된 규칙은 다음과 같다.

| 변경 유형 | 버전 변화 | 예시 |
|-----------|-----------|------|
| patch | 1.0.0 → 1.0.1 | 오타 수정, 문구 다듬기 등 동작에 영향 없는 변경 |
| minor | 1.0.0 → 1.1.0 | 기능 추가, 템플릿 구조 변경, 지시문 개선 등 동작에 영향 있는 변경 |
| major | 1.0.0 → 2.0.0 | 스킬의 목적이나 워크플로우가 근본적으로 바뀌는 변경 |

`spec-writer`의 현재 버전은 `1.3.0`이다. 커밋 이력을 보면 인터뷰 품질 향상 원칙 5가지 추가(minor), SRS 템플릿 대폭 개선(minor), 시스템 관점 다이어그램 예시 제거(patch) 순으로 변경이 누적되었다. 버전 번호만 봐도 이 스킬이 얼마나 성숙했는지 짐작할 수 있다.

### 버전 관리가 필요한 이유

버전 없이 스킬을 운영하면 두 가지 문제가 생긴다.

첫째, 언제 무엇이 바뀌었는지 추적하기 어렵다. "이번 SRS가 저번이랑 형식이 다른데?" 같은 상황이 생겼을 때 원인을 파악하기 어렵다. 버전 이력이 있으면 언제 템플릿이 바뀌었는지 바로 확인할 수 있다.

둘째, 팀에서 스킬을 공유할 때 혼선이 생긴다. "최신 버전 받았어요?"라는 말이 의미를 가지려면 버전이 있어야 한다. 버전이 없으면 파일을 직접 비교해야 한다.

`SKILL.md`의 변경과 `references/`의 변경 모두 버전 업 대상이다. references 파일만 고치고 `SKILL.md` 버전을 그대로 두면 버전이 실제 내용을 반영하지 못하게 된다.

## 7. 스킬 호출 제어

### 수동 호출만 허용

```yaml
disable-model-invocation: true
```

이 옵션을 설정하면 Claude가 대화 맥락을 보고 자동으로 스킬을 실행하지 않는다. 사용자가 명시적으로 `/skill-name`이라고 입력해야만 실행된다.

민감한 작업이나 실수로 트리거되면 안 되는 스킬에 적합하다. 예를 들어 파일을 대량으로 수정하거나 외부 시스템에 데이터를 전송하는 스킬이라면 자동 감지보다 명시적 호출이 안전하다. "이 파일들 정리해줘"라는 말에 자동으로 대량 삭제 스킬이 실행되면 곤란하다.

### Claude 내부 전용

```yaml
user-invocable: false
```

이 옵션을 설정하면 사용자가 슬래시 명령어로 직접 호출할 수 없다. 다른 스킬이 내부적으로 호출하는 보조 스킬에 사용한다.

`study-helper` 스킬은 내부에서 `/humanizer`와 `/external-context`를 호출한다. 이 두 스킬을 사용자가 직접 호출하는 경우도 있으므로 `user-invocable: false`는 적용하지 않았지만, 순수하게 내부 전용 유틸리티라면 이 옵션으로 외부 노출을 차단할 수 있다. 사용자에게는 보이지 않고, 스킬 간 조합만 가능한 내부 모듈이 된다.

### description이 자동 감지의 핵심

`disable-model-invocation`을 설정하지 않으면 Claude는 `description`을 읽고 현재 요청에 맞는 스킬을 자동으로 선택한다. 이 과정에서 `description`의 품질이 정확도를 결정한다.

잘 쓴 `description`의 특징은 세 가지다.

첫째, 스킬이 처리하는 작업을 한 문장으로 명확히 설명한다. 무엇을 입력으로 받고 무엇을 출력하는지가 드러나야 한다.

둘째, 사용자가 실제로 쓸 법한 표현을 구체적으로 나열한다. `humanizer`의 description을 보면 "AI투 제거해줘", "사람처럼 다듬어줘", "AI 냄새 빼줘", "humanize 해줘", "문체 교정해줘"처럼 다양한 표현을 열거하고 있다. Claude는 이 표현들과 사용자의 요청이 얼마나 유사한지 판단한다. 표현이 많을수록 다양한 방식으로 말하는 사용자를 폭넓게 커버할 수 있다.

셋째, 사용하지 말아야 할 경우를 명시한다. "단, 단순 맞춤법 교정이나 번역 요청에는 사용하지 않는다"처럼 부정 예시를 포함하면 오작동을 줄일 수 있다. 비슷해 보이지만 다른 스킬이 처리해야 할 요청을 걸러내는 역할을 한다. `spec-writer`는 "기획서 작성", "회의록 정리", "JSDoc", "Swagger"를 명시적으로 제외한다. 이 표현들이 없으면 Claude가 혼동하기 쉬운 경계 케이스들이다.

## 8. 핵심 정리

스킬을 처음 만들 때는 작게 시작하는 것이 좋다. `humanizer`처럼 `SKILL.md` 하나로 시작하고, 쓰다 보면서 `references/`가 필요한 시점이 오면 그때 분리한다. 처음부터 완벽한 구조를 만들려고 하면 오히려 시작이 늦어진다.

스킬을 만들기 전에 다음 체크리스트를 확인한다.

**구조**
- `SKILL.md`가 있는가
- 스킬 디렉토리 이름이 스킬 식별자와 일치하는가
- 보조 파일이 필요한 경우 `references/`에 분리했는가

**Frontmatter**
- `name`과 `description`이 있는가
- `description`에 긍정 예시(언제 써야 하는지)와 부정 예시(언제 쓰지 말아야 하는지)가 모두 있는가
- `version: 1.0.0`을 추가했는가
- 자동 감지가 필요 없다면 `disable-model-invocation: true`를 추가했는가

**본문**
- 핵심 원칙(왜 이렇게 동작하는지)이 명확한가
- 단계별 워크플로우가 순서대로 기술되어 있는가
- 전형적인 사용 예시(`## Examples`)가 있는가
- 자주 발생하는 문제와 해결책(`## Troubleshooting`)이 있는가

**일관성**
- `references/`에 템플릿이 있다면 `SKILL.md`의 지시문과 형식이 일치하는가
- 변경 후 버전을 올렸는가
- `SKILL.md` 변경 시 관련 `references/` 파일도 함께 수정했는가 (반대도 마찬가지)

잘 만든 스킬은 한 번 작성해두면 반복 작업을 대신한다. `spec-writer`는 SRS 인터뷰 6단계 전 과정을 처리하고, `performance-profiler`는 Java 성능 분석 4개 카테고리를 체계적으로 점검한다. `study-helper`는 노션 페이지를 가져와 AI투 제거, 팩트체크, 검수 리포트 생성까지 자동으로 이어간다. 복잡한 작업일수록 스킬로 만들 때 효과가 크다.
