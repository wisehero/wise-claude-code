## Git 연동

Claude Code는 git 작업을 자연어로 처리할 수 있다. 변경 사항 분석부터 PR(Pull Request, 풀 리퀘스트) 생성까지 터미널을 벗어나지 않고 진행된다.

### 커밋 메시지 자동 생성

```bash
claude commit
```

스테이징된 변경 사항을 분석해 Conventional Commits(컨벤셔널 커밋) 형식의 메시지를 작성하고 커밋한다. 변경된 파일의 목적과 범위를 파악해 `feat:`, `fix:`, `refactor:` 같은 타입을 자동으로 선택한다.

세션 안에서도 같은 작업을 요청할 수 있다.

```
변경사항 분석하고 적절한 커밋 메시지로 커밋해줘
```

CLAUDE.md에 커밋 메시지 형식을 명시해 두면 Claude가 팀 컨벤션을 따른다. 예를 들어 "커밋 메시지는 한국어로 작성한다"고 적어두면 매 세션에서 별도로 지시하지 않아도 된다.

### PR 생성

```
변경사항 커밋하고 PR 열어줘
```

Claude가 스테이징된 변경 사항을 커밋하고, 브랜치를 원격 저장소에 푸시한 뒤, PR 제목과 본문을 작성해 생성한다. PR 본문에는 변경의 목적, 주요 변경 파일, 테스트 방법이 자동으로 포함된다.

`gh` CLI(GitHub CLI)가 설치되어 있어야 이 기능을 사용할 수 있다. `gh auth login`으로 먼저 인증한다.

### 코드 리뷰 요청 및 피드백 반영

PR을 생성하고 리뷰를 받은 뒤 피드백을 반영하는 과정도 Claude와 함께 진행할 수 있다.

```
PR #42 리뷰 코멘트 가져와서 피드백 반영해줘
```

Claude가 PR의 리뷰 코멘트를 읽고 각 항목을 코드에 반영한다. 반영이 완료되면 변경 사항을 정리해 알려준다.

### 브랜치 관리

```
feature/payment 브랜치 만들고 거기서 작업 시작해줘
```

```
main 브랜치와 현재 브랜치의 차이점을 요약해줘
```

브랜치 생성, 전환, 비교 등 일상적인 git 작업을 자연어로 처리한다. 복잡한 git 명령을 외울 필요 없이 의도를 전달하면 된다.

## Plan Mode 활용

Plan Mode(계획 모드)는 Claude가 실제 변경을 가하지 않고 읽기 전용으로 코드베이스를 탐색하며 작업 계획을 세우는 모드다. 대규모 작업을 시작하기 전에 Claude가 어떤 파일을 어떻게 수정할지 먼저 파악하는 용도로 사용한다.

### Plan Mode 진입

세션 중 `Shift+Tab`을 눌러 모드를 순환한다. `default → plan → auto → default` 순서로 전환된다. 현재 활성 모드는 프롬프트 옆에 표시된다.

### 읽기 전용 탐색에서 구현으로

Plan Mode의 전형적인 사용 패턴은 다음과 같다.

1. Plan Mode 진입
2. "인증 모듈을 OAuth 2.0으로 교체하려면 어떤 파일을 수정해야 해?"와 같이 탐색 요청
3. Claude가 관련 파일을 읽고 변경 범위를 분석해 계획을 제시
4. 계획 검토 후 `Shift+Tab`으로 default 모드로 전환
5. "계획대로 구현해줘"

계획 단계에서 실수를 발견하면 구현 전에 방향을 수정할 수 있다. 잘못된 파일을 대규모로 수정한 뒤 되돌리는 것보다 비용이 훨씬 적다.

### 계획을 텍스트 에디터에서 편집

Plan Mode에서 Claude가 계획을 제시한 뒤 `Ctrl+G`를 누르면 현재 계획을 텍스트 에디터에서 열 수 있다. 에디터에서 직접 계획을 수정하거나 보완한 뒤 저장하면 Claude가 수정된 계획을 기반으로 구현을 진행한다.

자동화 환경에서 Plan Mode를 강제하려면 다음 플래그를 사용한다.

```bash
claude --permission-mode plan "인증 모듈 리팩토링 계획 세워줘"
```

## 멀티 세션과 워크트리

독립적인 작업을 동시에 진행해야 할 때 멀티 세션과 git worktree(워크트리)를 활용한다.

### 여러 터미널에서 독립 세션 실행

Claude Code 세션은 서로 독립적이다. 터미널 탭을 추가로 열고 `claude`를 실행하면 별개의 컨텍스트를 가진 새 세션이 시작된다.

```bash
# 터미널 1: 프론트엔드 작업
claude
> 결제 UI 컴포넌트 만들어줘

# 터미널 2: 백엔드 작업
claude
> 결제 API 엔드포인트 구현해줘
```

두 세션은 컨텍스트를 공유하지 않는다. 한쪽의 긴 작업이 다른 쪽 세션의 응답 속도나 컨텍스트에 영향을 주지 않는다.

### 워크트리로 브랜치 격리

git worktree는 하나의 로컬 저장소에서 여러 브랜치를 동시에 체크아웃하는 기능이다. Claude Code와 함께 사용하면 각 브랜치를 완전히 격리된 디렉토리에서 독립적으로 작업할 수 있다.

```bash
# feature/auth 브랜치를 별도 디렉토리에 체크아웃
git worktree add ../my-project-auth feature/auth

# 해당 디렉토리에서 Claude Code 세션 실행
cd ../my-project-auth
claude
```

`claude --worktree` 플래그를 사용하면 워크트리 생성과 세션 시작을 한 번에 처리한다.

```bash
claude --worktree feature/auth
```

### 병렬 개발의 장점

워크트리 기반 병렬 세션의 실질적인 이점은 세 가지다.

첫째, 컨텍스트가 완전히 분리된다. 한 세션에서 대규모 리팩토링을 진행하더라도 다른 세션의 버그 수정 작업에 영향을 주지 않는다.

둘째, 브랜치 전환 비용이 없다. `git stash`나 `git checkout`으로 작업 중인 변경을 임시 저장하고 전환할 필요가 없다.

셋째, 각 세션이 독립된 컨텍스트를 유지하므로 응답이 빠르다. 컨텍스트가 한 작업에 집중되어 있어 불필요한 정보로 인한 혼선이 줄어든다.

## 컨텍스트 관리

컨텍스트 관리는 Claude Code를 실무에서 효과적으로 사용하기 위한 가장 중요한 기술이다. 컨텍스트 창이 가득 차면 Claude의 응답 품질이 눈에 띄게 떨어진다.

### 컨텍스트 가득 참 신호

다음 증상이 나타나면 컨텍스트가 한계에 달했다는 신호다.

- 응답이 짧아지거나 요청의 일부만 처리된다
- 이전 대화에서 결정한 사항을 반복 확인하거나 잊는다
- 수정 중인 파일과 관련 없는 파일을 참조한다
- "이전에 말씀하신 것처럼..." 같은 표현과 함께 맥락 없는 내용을 언급한다

### /clear: 전체 리셋

```
/clear
```

현재 대화 컨텍스트를 전부 삭제하고 빈 상태로 시작한다. 작업 중인 파일의 변경 사항은 디스크에 그대로 남는다. 새로운 작업을 시작하거나 대화가 산만해졌을 때 사용한다.

### /compact: 대화 압축

```
/compact
```

전체 대화를 요약해 컨텍스트를 압축한다. 현재 작업의 핵심 내용은 유지하면서 불필요한 중간 과정을 제거한다. 작업을 완전히 버리지 않고 계속 이어가야 할 때 유용하다.

특정 내용을 압축 요약에 반드시 포함하도록 지시할 수 있다.

```
/compact 현재 진행 중인 인증 모듈 리팩토링 계획과 이미 수정한 파일 목록을 반드시 포함해
```

### Esc+Esc로 부분 요약

메시지를 보내기 전 `Esc`를 두 번 누르면 "Summarize" 옵션이 나타난다. 현재까지의 대화를 요약한 뒤 새 메시지를 이어서 보낸다. `/compact`와 달리 요약 범위를 더 세밀하게 조절할 수 있다.

### /btw: 컨텍스트를 소비하지 않는 사이드 질문

```
/btw 이 라이브러리가 ESM을 지원하나?
```

`/btw` 명령은 현재 작업 컨텍스트에 영향을 주지 않는 가벼운 질문을 처리한다. 주 작업의 흐름을 방해하지 않고 간단한 정보를 조회할 때 사용한다. `/btw`로 주고받은 내용은 이후 대화의 컨텍스트에 포함되지 않는다.

### 큰 파일은 필요한 부분만 요청

파일 전체를 읽도록 요청하면 컨텍스트를 빠르게 소진한다. 필요한 함수나 섹션만 명시적으로 지정한다.

```
# 비효율적
payment.service.ts 파일 읽어줘

# 효율적
payment.service.ts에서 processRefund 함수만 읽어줘
payment.service.ts의 150-200번째 줄만 읽어줘
```

Claude가 자동으로 전체 파일을 읽으려는 경향이 있다면 "필요한 함수만 읽고 전체 파일은 읽지 마"라는 지시를 CLAUDE.md에 추가한다.

## 서브에이전트 활용

서브에이전트(Sub-agent)는 Claude Code가 복잡한 작업을 처리할 때 자동으로 생성하는 독립 실행 단위다. 탐색, 계획, 구현을 각기 다른 에이전트에 분리해 메인 컨텍스트를 보호하는 방식으로 동작한다.

### 자동 서브에이전트 생성

Claude Code는 다음 상황에서 자동으로 서브에이전트를 생성한다.

- 여러 디렉토리를 동시에 탐색해야 하는 경우
- 독립적인 하위 작업이 병렬로 처리 가능한 경우
- 메인 컨텍스트를 소비하지 않고 특정 파일을 탐색해야 하는 경우

명시적으로 서브에이전트 사용을 요청할 수도 있다.

```
서브에이전트를 사용해서 src/ 디렉토리 전체 구조를 탐색하고 보고해줘
```

### Ctrl+T: 작업 목록 확인

`Ctrl+T`를 누르면 현재 실행 중인 작업과 서브에이전트의 상태를 확인할 수 있다. 각 서브에이전트가 어떤 작업을 처리 중인지, 완료 여부가 표시된다.

### Ctrl+B: 백그라운드 전환

시간이 오래 걸리는 작업이 진행 중일 때 `Ctrl+B`를 누르면 해당 작업을 백그라운드로 전환하고 새로운 요청을 입력할 수 있다. 백그라운드 작업이 완료되면 알림이 표시된다.

## 검증 자동화

Claude Code는 코드 작성과 검증을 하나의 흐름으로 처리할 수 있다. 테스트 실행, 스크린샷 비교, CI/CD(Continuous Integration/Continuous Deployment, 지속적 통합·배포) 연동까지 모두 세션 안에서 다룬다.

### 테스트-커밋 통합 패턴

```
테스트 작성하고 실행해서 통과하면 커밋해줘
```

Claude가 구현 코드에 대한 테스트를 작성하고, 테스트를 실행한 뒤, 모든 테스트가 통과하면 커밋한다. 실패한 테스트가 있으면 원인을 분석하고 코드를 수정한 뒤 다시 실행한다. 사람이 개입하지 않아도 이 과정이 자동으로 반복된다.

### 스크린샷 비교를 통한 디자인 구현

디자인 이미지를 대화에 붙여넣으면 Claude가 이를 참고해 UI를 구현한다.

```
[디자인 이미지 붙여넣기]
이 디자인대로 React 컴포넌트 만들어줘. 완성되면 실행해서 스크린샷 찍어서 비교해줘
```

Claude가 컴포넌트를 구현하고, 브라우저에서 실행한 뒤, 스크린샷을 찍어 원본 디자인과 비교한다. 차이가 있으면 수정하고 다시 비교하는 과정을 반복한다.

### CI/CD 통합

비대화형(non-interactive) 환경에서 Claude Code를 사용하면 CI 파이프라인에 통합할 수 있다.

```bash
claude -p "lint 에러 고쳐줘" --permission-mode auto
```

`-p` 플래그는 단일 작업을 처리하고 종료하는 print 모드다. `--permission-mode auto`는 사용자 확인 없이 자율적으로 작업을 처리하도록 설정한다. 이 조합을 사용하면 GitHub Actions나 Jenkins 같은 CI 환경에서 Claude를 실행할 수 있다.

```yaml
# GitHub Actions 예시
- name: Fix lint errors
  run: claude -p "lint 에러 고쳐줘" --permission-mode auto
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
```

## 효과적인 작업 지시 패턴

Claude Code에서 효율적인 결과를 얻으려면 지시 방식이 중요하다.

### 구체적으로 지시한다

모호한 요청은 모호한 결과를 낳는다. 파일명, 함수명, 예상 동작을 명시할수록 Claude가 의도에 맞는 결과를 내놓는다.

```
# 모호한 지시
로그인 기능 개선해줘

# 구체적인 지시
src/auth/login.ts의 authenticate 함수에서 비밀번호 해싱을 bcrypt 대신 argon2로 교체해줘.
인터페이스는 그대로 유지하고 내부 구현만 변경해.
```

### 반복 수정 시 /clear 후 재시작

같은 요청을 두세 번 반복 수정했는데도 원하는 결과가 나오지 않는다면 대화 히스토리가 방해가 되는 경우가 많다. `/clear`로 컨텍스트를 초기화하고 더 명확한 프롬프트로 새로 시작하는 편이 낫다.

이전 시도에서 "이렇게 하면 안 된다"는 사실을 확인했다면, 재시작할 때 그 내용을 함께 전달한다.

```
/clear
payment.service.ts의 refund 로직을 수정해줘.
주의: stripe SDK의 refund() 메서드를 직접 호출하지 말고
내부 RefundQueue를 통해 처리해야 해.
```

### 큰 작업은 분할한다

한 번의 요청에 너무 많은 작업을 담으면 Claude가 중요한 세부 사항을 놓치거나 부분적으로만 처리한다. 하나의 요청은 하나의 관심사에 집중한다.

```
# 좋지 않은 방법: 한 번에 너무 많은 요청
인증 모듈 전체를 JWT로 교체하고, 관련 테스트 모두 작성하고,
API 문서도 업데이트하고, CHANGELOG도 써줘

# 좋은 방법: 단계적 처리
1. "인증 모듈을 JWT 기반으로 교체해줘"  →  완료 후 검토
2. "방금 수정한 인증 모듈에 대한 테스트 작성해줘"  →  완료 후 검토
3. "변경 사항을 API 문서에 반영해줘"  →  완료
```

## 일일 워크플로우 체크리스트

실무에서 Claude Code를 사용하는 일반적인 하루의 흐름이다.

**작업 시작 전**
- [ ] 작업 브랜치 생성 또는 전환
- [ ] 필요시 워크트리로 격리 환경 구성
- [ ] Claude Code 세션 시작
- [ ] 규모가 큰 작업이면 Plan Mode로 먼저 계획 수립

**작업 중**
- [ ] 컨텍스트 가득 참 신호 주시
- [ ] 필요에 따라 `/compact` 또는 `/clear`로 컨텍스트 관리
- [ ] 구현 완료 후 테스트 실행 요청
- [ ] 테스트 통과 확인 후 커밋

**작업 완료 후**
- [ ] `claude commit`으로 변경 사항 정리 커밋
- [ ] 필요시 PR 생성 및 리뷰 요청
- [ ] 다음 작업이 다른 컨텍스트라면 `/clear` 또는 새 세션 시작

## Claude Code로 할 수 있는 것: 빠른 참조

| 작업 | 지시 예시 |
|---|---|
| 커밋 | `claude commit` 또는 "변경사항 커밋해줘" |
| PR 생성 | "커밋하고 PR 열어줘" |
| 코드 리뷰 반영 | "PR #42 리뷰 피드백 반영해줘" |
| 테스트 작성 및 실행 | "테스트 작성하고 통과하면 커밋해줘" |
| 브랜치 생성 | "feature/oauth 브랜치 만들고 시작해줘" |
| 계획 수립 | Plan Mode 진입 후 "이 기능 어떻게 구현할지 분석해줘" |
| 컨텍스트 초기화 | `/clear` |
| 대화 압축 | `/compact` |
| 사이드 질문 | `/btw 이 라이브러리 최신 버전은?` |
| lint 오류 자동 수정 | `claude -p "lint 에러 고쳐줘" --permission-mode auto` |
| 디자인 구현 | 이미지 붙여넣기 후 "이 디자인대로 만들어줘" |

## 핵심 정리

- `claude commit`은 스테이징된 변경 사항을 분석해 커밋 메시지를 자동 생성한다. CLAUDE.md에 형식을 명시하면 팀 컨벤션을 일관되게 유지한다.
- Plan Mode(`Shift+Tab`)로 대규모 작업 전에 변경 범위를 먼저 확인하고, `Ctrl+G`로 계획을 에디터에서 직접 편집할 수 있다.
- git worktree와 멀티 세션을 조합하면 독립된 컨텍스트에서 여러 브랜치를 동시에 작업할 수 있다.
- 응답이 짧아지거나 엉뚱한 파일을 참조하면 컨텍스트 한계 신호다. `/clear`로 전체 초기화하거나 `/compact`로 압축한다.
- 서브에이전트는 탐색과 구현을 분리해 메인 컨텍스트를 보호한다. `Ctrl+T`로 진행 상황을, `Ctrl+B`로 백그라운드 전환을 제어한다.
- "테스트 작성하고 통과하면 커밋해줘" 패턴으로 작성·검증·커밋을 하나의 흐름으로 처리한다.
- 반복 수정이 통하지 않으면 `/clear` 후 더 구체적인 프롬프트로 재시작한다.
