# 시스템 프롬프트 설계

> **난이도**: 중급 | **선행 문서**: [프롬프트 기초](01-프롬프트-기초.md)
>
> Claude의 행동과 성격을 정의하는 시스템 프롬프트의 설계 원칙과 모범 사례를 다룬다.

---

## 들어가며

API를 통해 Claude를 호출할 때, 사용자의 메시지와는 별개로 사전에 제공할 수 있는 지시 영역이 있다. 이것이 시스템 프롬프트(system prompt)다. 시스템 프롬프트는 Claude가 어떤 역할을 맡고, 어떤 방식으로 응답하며, 무엇을 해야 하고 무엇을 하면 안 되는지를 규정한다.

사용자 메시지가 매번 달라지는 변수라면, 시스템 프롬프트는 고정된 기반이다. 잘 설계된 시스템 프롬프트는 개별 사용자 메시지의 품질과 무관하게 일관된 결과를 보장한다.

---

## 1. 시스템 프롬프트의 역할

시스템 프롬프트는 Claude의 기본 행동과 성격을 정의하는 첫 번째 레이어다. API 호출에서 시스템 프롬프트는 사용자 메시지(user message)보다 먼저 처리되며, 우선순위가 더 높다. 사용자가 시스템 프롬프트와 충돌하는 요청을 해도 Claude는 시스템 프롬프트의 지시를 따르는 방향으로 응답을 조율한다.

Python SDK(소프트웨어 개발 도구 모음)에서 시스템 프롬프트를 전달하는 방법은 다음과 같다.

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system="당신은 B2B SaaS 스타트업을 위한 기술 지원 전문가입니다. "
           "답변은 항상 한국어로 작성하며, 단계별 해결 방법을 제시합니다. "
           "코드 예시가 필요할 때는 Python을 기본으로 사용합니다.",
    messages=[
        {"role": "user", "content": "API 호출이 자꾸 타임아웃이 나요."}
    ]
)
```

`system` 파라미터에 문자열로 전달된 내용이 시스템 프롬프트다. `messages` 배열 안에 넣는 사용자 메시지와 달리 별도의 파라미터로 분리되어 있다는 점이 중요하다. 이 분리가 우선순위 관계를 명확히 한다.

---

## 2. 설계 원칙

### 원칙 1: 명확한 역할 정의

역할을 정의할 때 세 가지를 명시한다. 전문 분야, 대상 사용자 수준, 그리고 핵심 관심사다.

막연한 역할 설정은 일관성 없는 응답을 낳는다.

```
나쁜 예:
"당신은 전문가입니다."

좋은 예:
"당신은 스타트업 창업자를 위한 재무 어드바이저입니다.
독자는 재무 지식이 거의 없는 비전공 창업자이며,
모든 설명은 실제 예시와 함께 제공합니다."
```

대상 사용자 수준을 명시하면 Claude가 설명의 깊이와 어휘 선택을 자동으로 조정한다. "전문가 대상"이라고 쓰면 배경 설명을 생략하고, "비전공자 대상"이라고 쓰면 개념을 풀어서 설명한다.

```python
# 전문가 대상 역할 설정
system = (
    "당신은 시니어 백엔드 엔지니어 대상의 코드 리뷰어입니다. "
    "언어별 관용 표현, 성능 특성, 동시성 모델에 집중합니다. "
    "기본 개념 설명은 생략하고 핵심 트레이드오프만 짚어줍니다."
)

# 비전공자 대상 역할 설정
system = (
    "당신은 IT 비전공 팀장을 위한 기술 번역가입니다. "
    "개발팀의 기술적 결정을 비즈니스 언어로 설명하며, "
    "전문 용어가 나오면 반드시 괄호 안에 한 줄 설명을 덧붙입니다."
)
```

### 원칙 2: 행동 지침 명시

행동 지침은 두 가지 방향으로 명시한다. 항상 해야 할 것과 절대 하면 안 될 것이다.

이 두 방향을 명확히 분리하면 Claude가 각 상황에서 판단해야 할 범위가 줄어든다.

```python
system = (
    "당신은 의료 정보 안내 챗봇입니다.\n\n"
    "항상 해야 할 것:\n"
    "- 증상 설명을 들은 후 관련 의학 정보를 제공한다\n"
    "- 정보 출처의 신뢰도를 언급한다\n"
    "- 전문의 상담을 권장하는 문장으로 마무리한다\n\n"
    "절대 하면 안 되는 것:\n"
    "- 특정 약물을 처방하거나 복용량을 지정하지 않는다\n"
    "- '당신은 ~병에 걸렸습니다'처럼 진단을 내리지 않는다\n"
    "- 의사의 지시를 무시하라고 권유하지 않는다"
)
```

출력 형식도 행동 지침에 포함한다. 응답 길이, 마크다운 사용 여부, 언어 설정 등을 미리 정해두면 매번 사용자 메시지에서 형식을 지정할 필요가 없다.

```python
system = (
    "응답 형식:\n"
    "- 최대 300단어로 작성한다\n"
    "- 코드 블록은 항상 언어 레이블을 붙인다 (예: ```python)\n"
    "- 본문에 마크다운 헤딩(#, ##)을 사용하지 않는다\n"
    "- 영어 전용 환경이므로 모든 응답은 영어로 작성한다"
)
```

### 원칙 3: 톤과 스타일 설정

톤은 응답의 전달 방식 전체를 결정한다. 동일한 정보라도 캐주얼한 톤과 격식 있는 톤은 완전히 다른 경험을 만든다.

**캐주얼 톤**: 친근하고 구어체적인 언어를 사용하며, 설명 중간에 공감 표현을 자연스럽게 섞는다. 주로 소비자 대상 서비스나 커뮤니티 플랫폼에 적합하다.

```python
system = (
    "당신은 개발자 커뮤니티 Slack 봇입니다. "
    "짧고 직설적으로 답하되, 친근한 어투를 유지합니다. "
    "가능하면 실제 경험담처럼 들리는 예시를 써주세요. "
    "너무 격식 차리지 않아도 됩니다."
)
```

**전문적 톤**: 정확한 용어를 사용하고 감정적 표현을 자제한다. 법률, 금융, 의료, 기업 내부 도구에 적합하다.

```python
system = (
    "당신은 법인 설립 절차를 안내하는 행정 도우미입니다. "
    "공식적이고 중립적인 어투를 유지합니다. "
    "법적 판단이 필요한 내용은 반드시 '전문가 확인 필요'라고 표시합니다. "
    "구어체 표현과 감탄사를 사용하지 않습니다."
)
```

**교육적 톤**: 개념을 단계별로 풀어주고, 이해를 확인하는 질문을 포함하며, 학습자의 페이스에 맞춘다.

```python
system = (
    "당신은 프로그래밍 입문 강사입니다. "
    "개념을 설명할 때 '왜(why)'부터 시작합니다. "
    "예시는 항상 현실 세계의 비유로 먼저 설명한 후 코드를 보여줍니다. "
    "설명이 끝나면 '이해가 됐나요? 궁금한 점이 있으면 물어보세요'로 마무리합니다."
)
```

### 원칙 4: 출력 구조 지정

시스템 프롬프트에서 응답의 기본 구조를 지정하면 모든 대화에서 일관된 형식을 얻는다. 이는 특히 API 응답을 파싱(parsing — 텍스트를 기계가 처리할 수 있는 구조로 변환하는 과정)하거나 UI에 렌더링(rendering — 데이터를 화면에 표시하는 과정)해야 하는 경우에 중요하다.

마크다운 구조 고정:

```python
system = (
    "고객 문의에 답할 때 항상 다음 구조를 따릅니다:\n"
    "1. **핵심 답변**: 한두 문장으로 요점을 먼저 제시합니다\n"
    "2. **상세 설명**: 필요하면 단계별로 풀어서 설명합니다\n"
    "3. **다음 단계**: 사용자가 취해야 할 행동을 제시합니다\n\n"
    "각 섹션은 마크다운 굵은 글씨 레이블로 시작합니다."
)
```

JSON 출력 고정:

```python
system = (
    "텍스트 분석 요청에는 항상 JSON 형식으로 응답합니다.\n"
    "형식:\n"
    "{\n"
    '  "sentiment": "positive|negative|neutral",\n'
    '  "confidence": 0.0~1.0,\n'
    '  "key_topics": ["주제1", "주제2"],\n'
    '  "summary": "한 문장 요약"\n'
    "}\n\n"
    "JSON 외의 텍스트는 포함하지 않습니다."
)
```

## 3. 모범 사례

### 구체적이고 측정 가능하게 작성한다

"좋은 응답을 제공하세요"는 Claude가 실행할 수 없는 지시다. 반면 "응답은 500단어 이내로, 한국어로, 마지막에 관련 자료 링크 하나를 포함해서 작성하세요"는 각 조건이 충족됐는지 측정할 수 있다.

### 맥락과 배경을 시스템 프롬프트에서 제공한다

사용자가 매번 배경을 설명하게 하는 것은 불편하다. 서비스의 성격, 사용자 층, 제약 환경을 시스템 프롬프트에 미리 담아두면 사용자는 핵심 질문만 던지면 된다.

```python
system = (
    "이 서비스는 한국 중소기업의 수출 서류 작성을 돕는 도구입니다. "
    "사용자는 영어 서류에 익숙하지 않은 중소기업 직원입니다. "
    "인코텀즈(Incoterms — 국제 무역 거래 조건을 표준화한 규칙)처럼 "
    "무역 전문 용어가 등장하면 반드시 괄호 안에 설명을 추가합니다."
)
```

### 제외할 내용을 명확히 한다

포함해야 할 내용만큼 제외해야 할 내용도 중요하다. 특히 Claude가 기본적으로 포함하는 내용 중 서비스에 맞지 않는 것이 있다면 명시적으로 금지해야 한다.

```python
system = (
    "응답에 포함하지 않는 것:\n"
    "- '물론입니다', '좋은 질문이네요' 같은 불필요한 앞말\n"
    "- 다른 AI 도구 추천\n"
    "- 회사 내부 정책이나 가격에 대한 추측\n"
    "- 해결책이 없을 때의 사과 이상의 과도한 공감 표현"
)
```

### 다양한 사용자 수준에 대응하는 방법을 지정한다

단일 서비스가 다양한 사용자 수준을 수용해야 하는 경우, 시스템 프롬프트에서 수준 감지와 대응 방법을 함께 지정할 수 있다.

```python
system = (
    "사용자의 질문 방식으로 전문성 수준을 판단합니다:\n"
    "- 전문 용어를 자연스럽게 쓰면 전문가 수준으로 응답합니다\n"
    "- 기초 개념을 물어보면 입문자 수준으로 설명합니다\n"
    "- 불명확하면 '어느 정도 배경 지식이 있으신가요?'라고 확인합니다"
)
```

## 4. 안티패턴

### 너무 길거나 장황한 지시

시스템 프롬프트도 토큰(token — LLM이 텍스트를 처리하는 최소 단위)을 소비한다. 불필요하게 긴 시스템 프롬프트는 응답에 사용할 수 있는 토큰을 줄이고 비용을 높인다. 또한 지시가 너무 많으면 Claude가 어떤 지시를 더 우선시해야 하는지 판단하기 어려워진다.

중요하지 않은 지시는 과감히 제거한다. 매 응답에 영향을 주지 않는 내용이라면 시스템 프롬프트가 아니라 사용자 메시지에서 필요할 때만 전달하는 방식을 택한다.

### 모호한 표현

"최고의 결과를 제공하세요", "사용자에게 도움이 되는 방향으로 응답하세요", "전문적으로 처리하세요" 같은 표현은 Claude가 실행할 기준이 없다. 이미 Claude는 도움이 되려고 최선을 다한다. 이런 표현을 추가해도 동작이 달라지지 않으며, 토큰만 낭비된다.

나쁜 예:

```
최대한 도움이 되는 응답을 제공하고, 사용자의 질문에 최고의 방식으로 답하세요.
```

좋은 예:

```
응답마다 실행 가능한 다음 단계를 반드시 포함하세요.
```

### 과도한 역할극

"당신은 절대 실수하지 않는 전능한 AI입니다"처럼 과장된 페르소나 설정은 실용성을 떨어뜨린다. Claude는 캐릭터를 유지하려다 정확성을 희생할 수 있고, 환각(hallucination — 사실이 아닌 내용을 자신 있게 생성하는 현상)이 늘어날 위험이 있다.

역할은 실제 전문성과 행동 방식을 기술하는 데 집중해야 한다. 극적인 설정보다는 실무적인 묘사가 더 신뢰할 수 있는 결과를 낳는다.

### 상충하는 지시

시스템 프롬프트 내에서 서로 모순되는 지시가 있으면 Claude는 둘 중 하나를 임의로 선택하거나 두 지시 사이에서 어정쩡한 응답을 만든다.

```
나쁜 예:
"응답은 간결하게 작성합니다." (첫 번째 지시)
"모든 항목에 상세한 배경 설명과 예시를 포함합니다." (세 번째 지시)
```

이 두 지시는 실제로 충돌한다. 시스템 프롬프트를 작성한 후 각 지시를 읽으며 서로 충돌하는 쌍이 있는지 확인하는 것이 중요하다.

## 5. Claude Code와의 연결

Claude Code에서 `CLAUDE.md` 파일은 사실상 시스템 프롬프트 역할을 한다. Claude Code가 실행될 때 `CLAUDE.md`를 읽어 프로젝트 맥락, 코딩 컨벤션, 금지 사항 등을 파악한다. 사용자가 별도로 지시하지 않아도 `CLAUDE.md`에 적힌 내용은 모든 작업에 자동으로 적용된다.

API 시스템 프롬프트와 `CLAUDE.md`의 차이는 다음과 같다.

| 비교 항목 | API 시스템 프롬프트 | CLAUDE.md |
|---|---|---|
| 적용 범위 | 해당 API 호출 세션 | Claude Code 실행 전체 |
| 작성 방식 | 코드 내 문자열 | 마크다운 파일 |
| 갱신 방법 | 코드 수정 후 재배포 | 파일 편집 후 즉시 반영 |
| 주요 용도 | 프로덕션 서비스 설정 | 개발 환경 설정, 프로젝트 컨벤션 |

결국 같은 원칙이 적용된다. 명확한 역할, 구체적인 행동 지침, 모순 없는 지시, 적절한 출력 형식. `CLAUDE.md`를 잘 작성하는 것은 API 시스템 프롬프트를 잘 설계하는 것과 동일한 사고방식을 요구한다.

`CLAUDE.md`의 상세한 작성법은 [claude-code/02-CLAUDE-md-작성-가이드.md](../claude-code/02-CLAUDE-md-작성-가이드.md)에서 다룬다.

## 6. 핵심 정리

### 4가지 설계 원칙 체크리스트

시스템 프롬프트를 작성하고 나서 아래 항목을 점검한다.

**역할 정의**
- 전문 분야가 구체적으로 명시되어 있는가?
- 대상 사용자 수준이 정의되어 있는가?
- 핵심 관심사나 우선순위가 담겨 있는가?

**행동 지침**
- "항상 해야 할 것" 목록이 있는가?
- "절대 하면 안 되는 것" 목록이 있는가?
- 출력 형식과 분량 제한이 명시되어 있는가?

**톤과 스타일**
- 의도한 톤이 명확한가? (캐주얼, 전문적, 교육적)
- 톤 설정이 대상 사용자와 서비스 성격에 맞는가?

**구조와 일관성**
- 지시 간에 모순이 없는가?
- 불필요하게 장황한 내용이 없는가?
- 모호한 표현이 구체적인 기준으로 대체되어 있는가?

### 좋은 시스템 프롬프트의 구조 템플릿

```
[역할 정의]
당신은 {대상 사용자}를 위한 {전문 분야} 전문가입니다.
{핵심 관심사나 우선순위를 한 줄로 기술합니다.}

[행동 지침]
항상 해야 할 것:
- {구체적인 행동 1}
- {구체적인 행동 2}

절대 하면 안 되는 것:
- {금지 행동 1}
- {금지 행동 2}

[출력 형식]
- 언어: {한국어 / 영어}
- 분량: {최대 N단어 / N줄}
- 구조: {자유 형식 / 마크다운 / JSON}
- 톤: {캐주얼 / 전문적 / 교육적}

[배경 맥락]
{서비스 성격, 사용자 환경, 특수 제약조건을 간결하게 기술합니다.}
```

이 템플릿의 모든 항목을 채울 필요는 없다. 서비스 성격에 맞는 항목만 선택해서 작성한다. 중요한 것은 각 지시가 측정 가능하고 모순이 없으며, 불필요한 내용이 없다는 것이다.
