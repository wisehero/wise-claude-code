# 프롬프트 캐싱

> **난이도**: 중급~심화 | **선행 문서**: [시스템 프롬프트 설계](03-시스템-프롬프트-설계.md), [모델 선택 가이드](04-모델-선택-가이드.md)
>
> 시스템 프롬프트와 대용량 컨텍스트의 비용을 크게 줄이는 Prompt Caching의 원리와 활용법을 다룬다.

---

## 1. Prompt Caching이란?

Prompt Caching(프롬프트 캐싱)은 API 호출 시 반복되는 입력을 캐시에 저장해 후속 요청에서 재사용하는 기능이다. 캐시에 저장된 토큰은 읽기 비용만 발생하며, 이 비용은 원래 입력 비용의 10%에 불과하다. 즉, 최대 90%까지 비용을 절감할 수 있다.

비용 절감 외에도 성능 향상이 있다. 캐시된 토큰은 처리 시간이 단축되어 응답이 더 빠르게 시작된다. 대용량 시스템 프롬프트나 긴 문서를 반복적으로 처리하는 경우 체감 차이가 크다.

### 언제 효과적인가

캐싱은 같은 프리픽스(prefix — 요청의 앞부분)가 여러 요청에서 반복될 때 효과적이다.

- **긴 시스템 프롬프트**: 시스템 프롬프트가 길고 모든 API 호출에서 동일하게 사용되는 경우
- **Few-shot 예시**: 동일한 예시 세트를 반복적으로 포함하는 경우
- **대용량 문서 분석**: 같은 문서에 대해 여러 질문을 순차적으로 하는 경우
- **멀티턴 대화**: 대화가 길어질수록 이전 턴의 내용이 반복 전송되는 경우
- **도구 정의**: 같은 도구 세트를 매 요청에 포함하는 경우

반대로 매 요청마다 입력이 완전히 달라지는 경우에는 캐시 히트가 발생하지 않으므로 효과가 없다.

---

## 2. 동작 원리

캐싱은 요청의 앞부분(프리픽스)을 기준으로 작동한다. Claude API는 요청을 처리할 때 이전 요청과 동일한 프리픽스가 있는지 확인하고, 일치하는 부분은 캐시에서 읽는다.

```
요청 1: [시스템 프롬프트] + [도구 정의] + [사용자 메시지 A]
         ────────── 캐시 저장 ──────────

요청 2: [시스템 프롬프트] + [도구 정의] + [사용자 메시지 B]
         ────────── 캐시 히트 ──────────   ── 새로 처리 ──
```

요청 2에서 시스템 프롬프트와 도구 정의 부분은 캐시에서 읽으므로 비용이 90% 절감된다. 사용자 메시지 B만 새로 처리된다.

### 캐시 수명

기본 캐시 TTL은 5분이다. 5분 이내에 같은 프리픽스로 다시 요청하면 캐시가 갱신되어 추가 5분이 연장된다. 5분 동안 사용하지 않으면 캐시가 만료되고, 다음 요청에서 새로 캐시가 생성된다.

1시간 TTL 옵션도 있다. 캐시 쓰기 비용이 기본 입력 비용의 200%(5분 TTL의 125%보다 높음)이지만, 요청 간격이 길어도 캐시를 유지할 수 있다. 배치 작업 간격이 5분을 초과하는 경우에 유용하다.

### 최소 캐시 크기

캐싱이 적용되려면 프리픽스가 일정 크기 이상이어야 한다.

| 모델 | 최소 토큰 수 |
|---|---|
| Opus 4.6 | 4,096 토큰 |
| Sonnet 4.6 | 2,048 토큰 |
| Haiku 4.5 | 4,096 토큰 |

시스템 프롬프트가 이 기준보다 짧으면 캐싱이 적용되지 않는다.

## 3. API 사용법

캐싱을 적용하려면 캐시 경계를 지정하는 `cache_control` 블록을 추가한다.

### 시스템 프롬프트 캐싱

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": "당신은 한국 법률 전문 상담사입니다. 다음은 참고할 법률 조문입니다.\n\n"
                    "[여기에 긴 법률 조문 텍스트... 수천 토큰 분량]",
            "cache_control": {"type": "ephemeral"}
        }
    ],
    messages=[
        {"role": "user", "content": "임대차 계약 해지 시 보증금 반환 기한은?"}
    ]
)
```

`cache_control: {"type": "ephemeral"}`을 추가하면 해당 블록까지의 내용이 캐시 대상이 된다. `ephemeral`은 현재 유일한 캐시 타입으로, 5분 TTL(Time To Live)을 의미한다.

### 도구 정의 캐싱

도구 정의에도 캐시를 적용할 수 있다. 도구 목록의 마지막 항목에 `cache_control`을 추가한다.

```python
tools = [
    {
        "name": "search_laws",
        "description": "법률 조문을 검색한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "query": {"type": "string"},
                "category": {"type": "string"}
            },
            "required": ["query"]
        }
    },
    {
        "name": "get_precedent",
        "description": "관련 판례를 조회한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "case_number": {"type": "string"}
            },
            "required": ["case_number"]
        },
        "cache_control": {"type": "ephemeral"}  # 도구 목록 전체를 캐시
    }
]
```

### 대화 히스토리 캐싱

멀티턴 대화에서 이전 턴의 내용을 캐시하면 대화가 길어질수록 비용 절감 효과가 커진다.

```python
messages = [
    {"role": "user", "content": "한국 민법의 계약 해제 조항을 설명해줘."},
    {
        "role": "assistant",
        "content": [
            {
                "type": "text",
                "text": "[이전 턴의 긴 응답 내용...]",
                "cache_control": {"type": "ephemeral"}
            }
        ]
    },
    {"role": "user", "content": "그중 손해배상 부분을 더 자세히 알려줘."}
]
```

## 4. 비용 구조

캐싱의 비용 구조는 세 가지 상태로 나뉜다.

| 상태 | 비용 | 설명 |
|---|---|---|
| 캐시 쓰기 (cache write) | 기본 입력 비용의 125% | 캐시에 처음 저장될 때 |
| 캐시 읽기 (cache read) | 기본 입력 비용의 10% | 캐시된 내용을 재사용할 때 |
| 캐시 미스 | 기본 입력 비용의 100% | 캐시가 없어 일반 처리될 때 |

첫 번째 요청에서 캐시 쓰기 비용(125%)이 발생하지만, 두 번째 요청부터 캐시 읽기 비용(10%)만 발생한다. 같은 프리픽스로 3회 이상 요청하면 확실히 비용이 절감되는 구조다.

### 비용 절감 예시

1,000 토큰 길이의 시스템 프롬프트를 100회 요청하는 경우를 비교한다.

**캐싱 없이**: 1,000 토큰 × 100회 = 100,000 토큰 비용

**캐싱 사용**: 1,000 토큰 × 1.25 (첫 요청, 쓰기) + 1,000 토큰 × 0.1 × 99회 (나머지, 읽기) = 1,250 + 9,900 = 11,150 토큰 비용

약 **89% 비용 절감**.

## 5. 캐시 히트를 극대화하는 전략

### 전략 1: 변하지 않는 내용을 앞에 배치

캐싱은 프리픽스 기반이므로, 변하지 않는 내용이 앞에 있어야 캐시 히트가 발생한다.

```
[시스템 프롬프트 - 불변]
[도구 정의 - 불변]
[Few-shot 예시 - 불변]
[이전 대화 턴 - 매 턴마다 누적]
[현재 사용자 메시지 - 매번 변경]
```

이 순서를 지키면 시스템 프롬프트, 도구, 예시 부분은 항상 캐시에서 읽힌다.

### 전략 2: cache_control 위치를 신중하게 결정

`cache_control`은 캐시 경계를 지정한다. 이 경계까지의 모든 내용이 캐시 대상이다. 경계를 너무 좁게 잡으면 캐시 효과가 줄고, 너무 넓게 잡으면 변경되는 부분까지 캐시에 포함되어 캐시 미스가 발생한다.

```python
# 좋은 예: 불변 부분만 캐시
system=[
    {
        "type": "text",
        "text": "[긴 시스템 프롬프트]",
        "cache_control": {"type": "ephemeral"}  # 여기까지 캐시
    }
]

# 나쁜 예: 자주 바뀌는 내용을 캐시에 포함
system=[
    {
        "type": "text",
        "text": f"[시스템 프롬프트] 현재 시간: {datetime.now()}",  # 매번 달라짐
        "cache_control": {"type": "ephemeral"}
    }
]
```

### 전략 3: 5분 TTL을 고려한 요청 간격

캐시는 5분간 유지된다. 요청 간격이 5분을 초과하면 캐시가 만료되어 다시 쓰기 비용이 발생한다. 배치 작업을 설계할 때는 요청을 5분 이내 간격으로 보내는 것이 유리하다.

## 6. 응답에서 캐시 상태 확인

API 응답의 `usage` 필드에서 캐시 관련 정보를 확인할 수 있다.

```python
response = client.messages.create(...)

print(response.usage)
# Usage(
#     input_tokens=50,                    # 캐시되지 않은 입력 토큰
#     output_tokens=150,                  # 출력 토큰
#     cache_creation_input_tokens=1000,   # 새로 캐시에 쓴 토큰
#     cache_read_input_tokens=0           # 캐시에서 읽은 토큰
# )
```

두 번째 요청부터는 `cache_read_input_tokens`에 값이 채워지고, `cache_creation_input_tokens`는 0이 된다. 이 값을 모니터링하면 캐싱이 제대로 작동하는지 확인할 수 있다.

## 7. 핵심 정리

### 도입 체크리스트

- [ ] 시스템 프롬프트가 최소 캐시 크기(Sonnet 4.6: 2,048, Opus 4.6/Haiku 4.5: 4,096 토큰) 이상인가?
- [ ] 같은 프리픽스가 여러 요청에서 반복되는가?
- [ ] 불변 내용이 요청의 앞부분에 배치되어 있는가?
- [ ] `cache_control`을 불변 블록의 마지막에 추가했는가?
- [ ] 요청 간격이 5분 이내인가?
- [ ] 응답의 `usage`에서 `cache_read_input_tokens`를 모니터링하고 있는가?

### 빠른 참조

| 항목 | 내용 |
|---|---|
| 최대 비용 절감 | 90% (캐시 읽기 = 기본 비용의 10%) |
| 캐시 쓰기 비용 | 기본 비용의 125% |
| 캐시 TTL | 5분 (기본, 사용 시 갱신) / 1시간 (쓰기 비용 200%) |
| 최소 캐시 크기 | Opus 4.6/Haiku 4.5: 4,096 토큰, Sonnet 4.6: 2,048 토큰 |
| 캐시 경계 지정 | `cache_control: {"type": "ephemeral"}` |
| 손익분기점 | 같은 프리픽스로 3회 이상 요청 |
