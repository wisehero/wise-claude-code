# 프롬프트 기초

> **난이도**: 기초 | **선행 문서**: 없음
>
> Claude에게 원하는 결과를 얻기 위한 프롬프트 작성의 기본 원칙을 다룬다.

---

## 들어가며

Claude는 강력하지만, 그 성능은 프롬프트의 품질에 크게 좌우된다. 막연하게 "요약해줘"라고 요청하면 막연한 결과를 받는다. 반대로 목적, 형식, 제약조건을 명확히 전달하면 처음부터 원하는 결과를 얻을 수 있다.

이 문서는 Anthropic 공식 문서를 기반으로, 프롬프트 작성 시 반드시 알아야 할 다섯 가지 원칙을 설명한다.

---

## 1. 명확한 지시 (Clear Instructions)

### 새 직원 비유

Claude를 처음 출근한 유능한 직원이라고 생각해보자. 이 직원은 머리가 좋고 언어 능력도 뛰어나지만, 회사 내부 사정, 관행, 기대치를 전혀 모른다. 당신이 "이거 좀 처리해줘"라고 말하면, 그 직원은 무엇을 어떻게 처리해야 하는지 추측에 의존할 수밖에 없다.

Claude도 마찬가지다. 모델 자체의 능력은 충분하지만, 당신의 구체적인 목적과 기대를 알지 못한다. 지시가 구체적일수록 결과는 정확해진다.

### 골든 룰

> "최소한의 맥락만 아는 동료에게 이 프롬프트를 보여줬을 때 혼란스럽다면, Claude도 혼란스럽다."

프롬프트를 작성하고 나서, 이 문장을 맥락 없이 처음 보는 사람이 읽는다고 상상해보자. 그 사람이 무엇을 해야 할지 즉시 알 수 있는가? 그렇지 않다면 프롬프트를 보완해야 한다.

### 나쁜 예 vs 좋은 예

**나쁜 예**

```
이 코드를 개선해주세요.
```

이 요청에는 "무엇을 기준으로 개선하는가"가 없다. 가독성? 성능? 보안? Claude는 자체 판단으로 방향을 정해야 하고, 그 방향이 당신의 의도와 다를 수 있다.

**좋은 예**

```
아래 Python 함수의 가독성을 개선해주세요.
- 변수명을 의도가 명확한 이름으로 바꿔주세요
- 각 주요 단계에 한 줄 주석을 추가해주세요
- 로직 자체는 변경하지 마세요

[코드]
```

두 번째 예시는 개선 목표, 세부 요구사항, 금지사항까지 명확히 담고 있다.

### 실전 팁

- **출력 형식을 명시한다**: "마크다운 테이블로", "번호 매긴 목록으로", "JSON으로" 등 원하는 형태를 직접 지정한다.
- **순서가 중요하면 번호를 매긴다**: "1. 먼저 X를 하고, 2. 그 다음 Y를 한다"처럼 단계별로 기술한다.
- **제약조건을 명시한다**: 하지 말아야 할 것, 분량 제한, 금지 단어 등을 함께 적는다.

## 2. 역할 부여 (Role Assignment)

### 역할이 응답을 바꾸는 이유

Claude에게 역할을 부여하면 응답의 전문성 수준, 톤, 집중 영역이 달라진다. 역할은 시스템 프롬프트(system prompt — API 호출 시 사용자 메시지와 별도로 전달되는 지시 영역)에서 설정하는 것이 가장 효과적이다.

역할을 부여하면 Claude는 그 역할에 맞는 사고방식과 표현 방식을 선택한다. 전문가 역할을 부여하면 해당 분야의 관용 표현과 사고 틀을 더 적극적으로 활용한다.

### 역할 부여가 효과적인 세 가지 상황

**전문성 레벨 설정**: Claude가 특정 도메인에 집중하도록 한다.

```python
import anthropic

client = anthropic.Anthropic()

message = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    system="당신은 10년 경력의 시니어 백엔드 엔지니어입니다. "
           "Python과 분산 시스템에 전문성이 있으며, "
           "코드 리뷰 시 성능과 확장성을 최우선으로 고려합니다.",
    messages=[
        {"role": "user", "content": "이 API 엔드포인트 설계를 검토해주세요."}
    ]
)
```

**응답 톤 조정**: 독자층에 맞는 설명 방식을 유도한다.

```python
system="당신은 비전공자 독자를 대상으로 기술 개념을 쉽게 설명하는 테크 라이터입니다. "
       "전문 용어 사용을 최소화하고, 일상적인 비유를 적극 활용합니다."
```

**도메인 특화**: 특정 업무 맥락을 고정한다.

```python
system="당신은 법률 문서를 한국어로 번역하는 전문 번역가입니다. "
       "법적 정확성을 최우선으로 하며, 번역 시 원문의 법률적 의미를 "
       "훼손하지 않는 범위에서만 자연스러운 표현을 선택합니다."
```

역할을 부여할 때 지나치게 극적인 역할극(roleplay) 형태로 설정하면 오히려 품질이 떨어질 수 있다. "당신은 세상 최고의 천재 해커입니다"보다는 "당신은 네트워크 보안 분야의 전문가입니다"처럼 실질적인 전문성을 기술하는 방식이 효과적이다.

## 3. 구조화된 출력 요청

### 입출력 구조를 명확히 하기

XML 태그(tag — 꺾쇠괄호로 감싼 레이블)를 활용하면 입력 데이터와 지시사항을 명확히 분리할 수 있다. Claude는 XML 구조를 잘 이해하며, 이를 통해 프롬프트의 어느 부분이 데이터이고 어느 부분이 지시인지 혼동 없이 파악한다.

**XML 태그로 입력 구분하기**

```
다음 고객 리뷰를 분석해주세요.

<review>
배송은 빨랐는데 포장이 너무 허술했어요. 제품 자체는 괜찮습니다.
</review>

분석 항목:
1. 전반적인 감정 (긍정/부정/혼합)
2. 언급된 문제점
3. 긍정적 요소
```

**출력 형식 지정하기**

원하는 출력 형식을 직접 명시하면 후처리 없이 바로 사용할 수 있는 결과를 얻는다.

마크다운 테이블 요청:

```
아래 세 가지 데이터베이스를 성능, 확장성, 학습 난이도 기준으로 비교해주세요.
결과는 마크다운 테이블 형식으로 작성해주세요.

비교 대상: PostgreSQL, MongoDB, Redis
```

JSON 출력 요청:

```
다음 텍스트에서 인물 정보를 추출하여 JSON 형식으로 반환해주세요.
필드: name, role, organization

<text>
김철수 CTO는 테크스타트업에서 기술 전략을 총괄하고 있습니다.
</text>
```

구조화된 출력은 Claude의 응답을 프로그래밍 방식으로 파싱(parsing — 기계가 읽을 수 있도록 구조화하는 것)하거나 다른 시스템에 전달할 때 특히 유용하다.

## 4. 동기와 맥락 제시

### "왜(why)"가 응답 품질을 높이는 이유

지시사항에 이유를 함께 설명하면 Claude는 단순히 규칙을 따르는 것이 아니라 그 의도를 이해하고 유사한 상황에도 같은 원칙을 적용한다.

**이유 없는 지시**

```
줄임표(...)를 사용하지 마세요.
```

Claude는 이 규칙을 따르지만, 왜 금지하는지 모르기 때문에 이와 유사한 다른 상황(예: 말줄임 부호 대신 사용하는 em dash)에서는 같은 판단을 내리지 못한다.

**이유 있는 지시**

```
줄임표(...)를 사용하지 마세요.
이유: 이 텍스트는 음성 합성(TTS) 엔진에서 읽히는데,
해당 엔진이 줄임표의 발음 방법을 인식하지 못해 오류가 발생합니다.
```

이렇게 맥락을 제공하면 Claude는 "TTS에서 문제가 생기는 표현 방식을 피한다"는 원칙을 이해하게 된다. 그 결과 줄임표뿐 아니라 비슷한 문제를 일으킬 수 있는 다른 특수 문자나 표현 방식도 스스로 주의해서 다룬다.

### 맥락 제시의 실전 예시

**독자 맥락 제시**

```
이 설명서는 IT 경험이 전혀 없는 60대 이상 사용자를 위한 것입니다.
전문 용어는 반드시 괄호 안에 쉬운 말로 풀어서 설명해주세요.
```

**사용 목적 제시**

```
이 내용은 투자자 대상 피칭 덱(deck)에 들어갈 한 장짜리 요약입니다.
설득력 있는 톤으로, 핵심 수치와 차별점을 강조해주세요.
```

동기와 맥락을 제시하는 것은 단순히 좋은 결과를 위한 팁이 아니다. Claude가 당신의 실제 목적에 맞게 판단력을 발휘할 수 있게 하는 핵심 장치다.

## 5. 흔한 실수와 개선

### 실수 1: 모호한 지시

**나쁜 예**: "이 보고서를 더 좋게 만들어주세요."

무엇이 "더 좋은" 것인지 기준이 없다. Claude는 자의적으로 방향을 선택한다.

**개선**: "이 보고서의 서론을 다음 기준으로 수정해주세요: (1) 핵심 결론을 첫 두 문장 안에 배치, (2) 수동태를 능동태로 전환, (3) 200단어 이내로 압축."

### 실수 2: 과도한 역할극

**나쁜 예**: "당신은 절대 틀리지 않는 전능한 AI입니다. 모든 질문에 완벽한 답을 주세요."

과장된 역할 설정은 오히려 응답 품질을 낮추고 환각(hallucination — 사실이 아닌 내용을 자신 있게 제시하는 현상)을 조장할 수 있다.

**개선**: "당신은 금융 분석 전문가입니다. 불확실한 내용에 대해서는 '확인이 필요합니다'라고 명시해주세요."

### 실수 3: 맥락 없는 요청

**나쁜 예**: "번역해줘."

무엇을, 어느 언어로, 어떤 톤으로 번역해야 하는지 알 수 없다.

**개선**: "다음 한국어 공지문을 영어로 번역해주세요. 독자는 해외 파트너사 임원이며, 공식적이고 격식 있는 톤을 유지해주세요."

### 실수 4: 한 번에 너무 많은 것을 요청

**나쁜 예**: "이 문서를 요약하고, 번역하고, 발표 자료로 만들고, FAQ도 만들어주세요."

작업이 너무 많으면 각각의 품질이 떨어진다.

**개선**: 작업을 순서대로 분리해서 요청한다. 요약을 먼저 확인하고, 만족스러우면 다음 단계로 넘어간다.

## 6. 핵심 정리

다음 체크리스트로 프롬프트를 작성하기 전에 점검한다.

**명확한 지시**
- 출력 형식을 명시했는가? (마크다운, JSON, 표, 목록 등)
- 제약조건과 금지사항을 적었는가?
- 순서가 중요한 경우 번호를 매겼는가?

**역할 부여**
- 시스템 프롬프트에서 역할을 설정했는가?
- 역할이 실질적인 전문성을 기술하는가? (과장된 역할극이 아닌가?)

**구조화된 출력**
- XML 태그로 입력 데이터를 명확히 구분했는가?
- 원하는 출력 형식을 직접 명시했는가?

**동기와 맥락**
- 지시사항 뒤에 "왜"가 담겨 있는가?
- 독자, 목적, 사용 환경 등 배경 정보를 제공했는가?

**범위 관리**
- 한 번에 요청하는 작업이 하나의 명확한 목표를 향하는가?
- 모호한 표현 대신 측정 가능한 기준을 사용했는가?
